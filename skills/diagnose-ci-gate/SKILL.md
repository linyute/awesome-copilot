# 診斷 CI 閘道 (Diagnose CI Gate)

紅燈檢查只是一項宣稱，並非診斷。在修改程式碼或按下重新執行之前，必須先從證據中確立三件事：究竟是什麼失敗了、它屬於哪一種類型的失敗，以及是否是由本次變更所引起。

本技能適用於 Pull Request 或分支上失敗的必要檢查。若要全面降低 CI 成本，請使用 `github-actions-efficiency` 技能。對於特定領域的不穩定測試套件，請在本次分級分類之後使用該工具專屬的技能（例如 `cypress-flake-fixer`）。

## 何時使用此技能

- Pull Request 上的必要檢查失敗，且你需要釐清是否是由你的變更造成
- 作業在本機通過但在 CI 中失敗，或僅在部分執行中失敗
- 有人說「那個失敗與本次無關，按重新執行就好」
- 建構已重試數次且持續失敗
- 你正打算編輯工作流程檔案以讓檢查通過

## 先決條件

- `gh` CLI 已驗證身分，或由使用者貼上原始記錄
- 具有基準分支及其近期執行的讀取權限
- 失敗步驟中的命令，以便能夠進行重現

若記錄被截斷、不完整或只有摘要，請停止並要求提供完整記錄。切勿根據摘要檢查的最後幾行文字進行診斷。

## 工作流程

### 1. 取得失敗的作業，而非檢查摘要

```bash
gh pr checks <pr-number>                     # 哪一項檢查、什麼狀態
gh run list --branch <branch> --limit 10     # 目前與近期的執行
gh run view <run-id> --log-failed            # 僅檢視失敗的步驟
gh run view <run-id> --job <job-id> --log    # 單一作業的完整記錄
```

記錄受測的認可 SHA、執行器 (runner) 映像檔與時間。舊 SHA 上的失敗與目前 head 上的失敗是不同的問題。

### 2. 從第一個錯誤開始讀取

讀取失敗步驟的開頭，而非結尾。第一個錯誤通常才是根本原因；其後的所有內容皆為該原因引發的連鎖反應或執行器放棄執行所導致。

引用精確的行數，並指明產生該錯誤的命令。若記錄僅顯示摘要行（`Process completed with exit code 1`），請找出發出該訊息的步驟並讀取該步驟的輸出。

### 3. 將失敗分類

| 類別 | 跡象 | 確認方式 |
| --- | --- | --- |
| **Bug (錯誤)** | 每次執行皆發生相同失敗，輸入具確定性 | 重新執行會在相同的判斷提示處以完全相同的方式失敗 |
| **Flaky (不穩定)** | 有時通過，與時間/順序/網路/共用狀態有關 | 相同的 SHA 在同一個作業上至少有一次綠燈執行，或本機迴圈測試中不定時失敗 |
| **Environment (環境)** | 工具版本、遺漏機密、執行器映像檔、快取、磁碟或記憶體 | CI 中的版本與本機不同，或該步驟在執行任何專案程式碼之前就已失敗 |
| **Pipeline (管線)** | 工作流程本身有誤：錯誤的路徑篩選器、錯誤的工作目錄、遺漏相依性安裝、YAML 語法錯誤，或檢查所斷言的目標是 Pull Request 無法產生的（例如尚未合併之頁面的正式環境 URL） | 命令針對 Pull Request 自身的建構產物執行成功，且工作流程行或其目標經證明是錯誤的 |

各用一句話寫下類別及其依據。無法分類的失敗尚未具備修復的條件。

### 4. 判定是否由本次變更所引起

在對歸屬做出任何宣稱之前，先與基準分支進行比較：

```bash
gh run list --branch main --limit 10
git merge-base HEAD origin/main
```

若相同的作業在基準分支上，或在基準分支近期的執行中也失敗，則屬於既有問題。請指明這點並附上該執行的連結。

某些作業僅在 Pull Request 上執行，因此不存在基準分支的執行記錄。在那種情況下，請如實說明而非暗示已做過比較，並使用 diff 來確立本次變更增加了什麼。

若要直接測試基準分支而不影響現有工作樹，請建立一個唯一的拋棄式工作樹，並在完成後將其移除：

```bash
base_dir="$(mktemp -d)"
git worktree add "$base_dir" "$(git merge-base HEAD origin/main)"
( cd "$base_dir" && <failing command> )
git worktree remove --force "$base_dir"
```

`mktemp -d` 會傳回全新的路徑，因此並行執行不會發生衝突。`--force` 在此處是安全的，因為該目錄是為了本次檢查而建立的，且失敗的命令可能已將建構輸出寫入其中。切勿將此指向包含工作進度的路徑，並使用 `git worktree remove` 移除工作樹，而非手動刪除目錄。若目錄已被手動刪除，請執行 `git worktree prune`。

此範例為 POSIX Shell。在 Windows 上，請從 Git Bash 執行，或使用 PowerShell：

```powershell
$baseDir = Join-Path $env:TEMP ("ci-base-" + [guid]::NewGuid())
git worktree add $baseDir (git merge-base HEAD origin/main)
Push-Location $baseDir; <failing command>; Pop-Location
git worktree remove --force $baseDir
```

若在基準分支通過但在 head 失敗，請指明引入該問題的認可、檔案與行數。若變更是相依性升級，請檢查鎖定檔案 (lockfile) 的 diff 與工具版本，而不僅僅是原始碼 diff。

### 5. 使用 CI 的版本進行重現

使用 CI 所使用的版本、在相同的工作目錄下、使用相同的環境變數與相同的安裝步驟執行失敗的命令。請從記錄中讀取版本，而非從你的本機機器。

若無法重現，請如實陳述並列出你發現的每一項差異：作業系統、執行階段版本、相依性解析、環境變數、時區、平行處理、快取狀態。「無法重現」是一項調查發現，而非失敗。

### 6. 選擇確切的一項行動

- **重試 (Retry)** — 僅在你已有證據證明該失敗屬於不穩定測試時使用。指出相同 SHA 在同一個作業上的綠燈執行記錄。
- **修復程式碼 (Fix the code)** — 指明檔案、行數與變更內容。這是確定性錯誤的預設處理方式。
- **修復管線 (Fix the pipeline)** — 指明工作流程檔案與行數。這適用於管線錯誤，而非用來掩蓋真正的失敗。

對於不穩定的測試，請執行後續追蹤工作，而非無休止地重新執行：

1. 重複執行並記錄失敗率：`for i in $(seq 1 20); do <command>; done`
2. 找出其背後的共用狀態、時間假設或順序相依性
3. 將其修復，或在指派負責人與移除日期的情況下進行隔離 (quarantine)，並指明是哪一種處理方式

### 7. 驗證並回報

修復後重新執行檢查並展示結果。對於不穩定的測試，展示重複執行的統計結果。

請依此格式回報：

```text
Check:      <name> on <SHA>
First error: <quoted line> (<step>, <command>)
Class:      bug | flaky | environment | pipeline
Ownership:  introduced by <commit/file:line> | pre-existing (<run link>)
Reproduced: yes (<command>) | no (<differences>)
Action:     retry | fix code | fix pipeline
Result:     <run link, or the repeated-run tally>
```

## 驗證檢查清單

- [ ] 引用的錯誤來自真實記錄，並指明步驟與命令
- [ ] 失敗已被分類，且附有該類別的證據
- [ ] 在宣稱問題歸屬之前，已檢查基準分支與近期執行
- [ ] 已使用 CI 版本重現失敗，或已列出差異
- [ ] 建議的行動為重試、修復程式碼或修復管線之一，並附上理由
- [ ] 修復後已重新執行檢查，並展示了結果

## 規則

- 在沒有證據證明失敗屬於不穩定之前，絕不建議重新執行
- 在未與基準分支比較之前，絕不稱失敗與本次變更無關
- 絕不跳過、刪除或削弱失敗的測試來讓檢查通過
- 絕不加入 `continue-on-error`、`if: always()` 或路徑篩選器來隱藏真正的失敗
- 絕不將通過重試視為根本原因已消除的證明；說明改變了什麼
- 當完整記錄可用時，絕不根據摘要行進行診斷

## 驗證案例

[`references/validation.md`](references/validation.md) 記錄了此技能應用於公開存放庫上真實失敗檢查的案例：作業記錄、分類、歸屬證據、重現嘗試以及建議的行動。

第一個情境是來自 GitHub Copilot CLI 的記錄副本，僅提供失敗的作業記錄，且在簽出環境中失敗的命令可正常通過。它傳回了下方的報告格式，將失敗分類為管線問題，並將其歸因於父認可而非受測的變更。這兩項發現隨後皆獲得證實，且深度為 1 的簽出環境能夠重現該失敗。該情境旨在展示報告如何在面對本機綠燈執行時保持客觀診斷，而非退縮為「無法重現，可能是不穩定」。

## 限制

- 記錄存取權限取決於授權。若無權限，請要求提供記錄而非盲目猜測
- 私有執行器與自行託管的基礎架構可能因記錄未顯示的原因而失敗
- 僅在負載下或真實硬體上才能重現的失敗可能需要類似正式環境的基礎架構
- 本技能負責診斷與提出建議。它不決定是否允許略過檢查；這是存放庫擁有者的策略決策
