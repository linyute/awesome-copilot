# 架構選型與互動合約 (Architecture Selection and Interaction Contract)

在選擇或重新檢視執行做法時閱讀。僅將委派與長時間互動的小節套用於相關任務。從可用情境建構決策卡；依據 [discovery-protocol.md](discovery-protocol.md) 解決實質未知項，而不要將其變成問卷調查。

## 1. 依任務屬性選擇

| 屬性 | 選型後果 |
|---|---|
| 輸入與規則已明確定義 | 一般自動化可能已足夠；僅在需要模稜兩可的解讀時才需要 LLM |
| 回答前所有資料皆已具備 | 考慮採用單次呼叫並進行輸出驗證 |
| 順序與允許的轉換皆已知 | 包含必要 LLM 步驟的預定義工作流程 |
| 新觀察決定下一步 | 有界限的代理人迴圈；識別其所解決的不確定性 |
| 存在獨立工作串流或所需情境／權限隔離 | 比較單一代理人與委派做法；循序依賴關係會限制平行處理的效益 |
| 存在共享可變狀態與外部副作用 | 指派變更與整合負責人；更多工作者會增加協調成本 |
| 長時間工作、暫停、事件或串流 | 需要互動與復原合約，而非自動增加另一個代理人 |
| 團隊、環境或模型能力受限 | 考量現有執行階段、可用工具與支援；在任務上展現模型的適合度 |

針對重大決策，比較基準方案與一至兩個合理的替代方案：`選項 → 涵蓋需求 → 預期效益 → 成本／風險 → 選擇或拒絕原因 → 檢查 → 重新考量觸發條件`。顯而易見的小型任務僅需要簡短理由，無需刻意製作表格。若使用者將某種拓撲結構指定為需求，請保留它並說明取捨。

在相同任務、資料存取、條件以及針對每個工作者、重試與整合步驟的**總額**預算下比較拓撲結構。工作者平均分配的限制並不意味著系統總預算相同。考量最終輸出品質、延遲、每個已接受任務的成本以及人工勞力。若無測量數據，效益仍屬假設；現在應交付條件式架構與比較計畫。實驗並非初步設計的先決條件。切勿從他人的基準測試匯入擴充規模閾值。

### 從功能到代理人邊界

首先從運作案例中衍生出功能，包含輸入、輸出、方法、狀態、負責人與權限。接著選擇執行形式，最後才確定持久化元件的邊界。職位名稱或獨立 API 本身並不能構成代理人邊界。

| 形式 | 充分的選型理由 |
|---|---|
| 確定性流程 | 規則定義轉換；個別 LLM 步驟不需要由模型控制整個流程 |
| 工具 | 具備合約與權限的有界限操作；其呼叫者擁有目標與結果驗收權限 |
| 技能／指示 | 具有指定輸入、情境、步驟與可驗證結果的可重複領域方法；單純指示不需要獨立執行階段 |
| 臨時子代理人 | 有界限的子任務；獨立情境、平行處理或權限可提供可驗證的效益；父層接受並整合結果 |
| 持久化代理人／設定檔 | 獨立職責與合理的執行邊界；明確的狀態與生命週期負責人、隔離原因以及協調成本 |

針對持久化元件，檢查穩定的輸出／決策類別、執行間的狀態、獨立啟動／暫停／復原，以及劃分理由：權限、資料、情境、負載或失敗網域。這些是決策因素，而非通用公式：隔離或擴充彈性可作為無狀態工作者的合理理由，而共享的擁有服務可擁有狀態。未知項並不能證明複雜性的必要。識別更簡單的替代方案以及再次合併元件的條件。

協調是個獨立決策：誰負責擁有整體結果、相依性、資源與衝突？一般排程器／路由器可處理固定轉換。透過對情境選取與驗證其決策的實際需求，來證明模型協調者的合理性。多個設定檔不會自動需要協調器；代理人規劃者可選取工具而無需持久化子設定檔。切勿將平台定義泛化為通用禁令。

依據人工工作與資料分別選取管理介面與儲存庫。首先檢查現有聊天、Jira、CLI 或 API 的能力。透過對共享佇列、結構化確認、搜尋／比較或相異權限的具體需求，來證明新儀表板的合理性。針對持久性、並行寫入、交易、搜尋、保留與可用支援來選擇儲存庫；檔案／SQLite／PostgreSQL 都是選項，而非強制階梯。語意搜尋需要其專屬任務，而非僅僅因為代理人的存在。

## 2. 若存在委派

填入一份真實的交接合約，然後識別其他角色的差異：

`負責人／接收者 → 目標與邊界 → 輸入、版本與允許來源 → 所需產物與就緒條件 → 權限 → 總預算／期限份額 → 停止與部分輸出 → 佐證／來源 → 驗證與整合`。

分開識別最終決策與共享資源的負責人。定義由誰解決衝突結果、防止重複副作用以及接受部分結果。委派特定工作與不受限制的對等通訊具有不同的協調規則；切勿以此代彼。A2A、佇列、圖形與監督者服務並非強制要求。

檢查限制傳遞、遞迴與巢狀預算、遺失／重複交付、衝突的共享寫入、逾期，以及取消後的延遲結果。在一個範例中追蹤 `已指派 → 已接受 → 已完成／部分完成／已拒絕 → 已驗證 → 已整合`。子層權限不得超過父層獲授權的範圍。來自共享情境的數個相同模型結論並不是獨立佐證；整合者檢查的是依據與矛盾，而不僅僅是投票數。

## 3. 若互動隨時間延續

依需求選擇：同步回應、背景任務、事件／排程、串流或語音。描述可觀察的行為：任務接受、進展、等候、部分結果、錯誤、取消與最終結果。若無背景工作，對應的狀態即不適用。

連結任務、對話、個別執行與外部動作識別碼。恢復執行可能會建立新執行，同時保留與任務及先前副作用的連結；請在最新文件中驗證具體 SDK 欄位。定義延遲與重複事件的處理方式。

當使用者變更目標時，標記新舊意圖之間的邊界：哪些未啟動的動作停止、哪些已發送且需要對帳、保留何種部分結果，以及必須重新計算哪些參數／權限。取消並不會復原已完成的動作，且絕不能允許在過時目標下產生新副作用。在範圍未變更的情況下，切勿再次請求仍有效的權限。

驗證前串流傳輸的文字皆屬暫態。若需求禁止揭露特定資料，事後串流驗證器就太遲了：在發布這些片段之前必須實施控制。展示正常完成以及一個取消／更正情境，而非僅僅列出狀態清單。
