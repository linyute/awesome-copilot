# 引導式訪談與佐證充分性 (Guided Interview and Evidence Sufficiency)

本通訊協定決定調查深度，而非固定的提問數量。具備現成規格的簡單案例兩輪即可涵蓋；而二十個回答也無法解決未知的外部副作用合約。請分別追蹤達到首個有用設計的時間、需求涵蓋範圍以及實作交接就緒度。

## 1. 可見路徑

初步簡要展示當前階段與最近成果：**任務與真實案例 → 運作邊界 → 架構決策 → 完整性檢查與交付**。針對診斷：**對象與症狀 → 實際路徑 → 鑑別檢查 → 結論與關閉計畫**。從符合可用情境的階段開始。這是方向指引，而非四個強制的循序問卷。

初步設計有助於獲得回饋。在情境足夠時應立即交付，否則最遲不應超過第三個回答。此限制僅涉及等待第一個設計的時間：它既不會結束訪談，也不會確認完整性。若連目標都不明確，請展示理解圖以及帶有單一關鍵缺口的條件式選項，而非憑空捏造拓撲結構。決定後續輪次的是未解決的實質問題，而非計數器。

在實質區塊之後，顯示簡要檢查點：已獲知何事、何項決策發生改變、哪些實質主題仍待決，以及下一個區塊之後將準備就緒的內容。當實質缺口仍存在時，切勿承諾「最後一個問題」。切勿從填寫的資料列虛構就緒百分比。進入下一階段無需額外權限。

## 2. 一輪對話——給對話者的單一明確任務

選擇其回答對邊界、輸出、安全性、成本或可行性影響最大的問題。簡要將其與先前的回答連結：**我所理解的內容 → 仍未知的內容 → 取決於回答的決策 → 問題**。切勿將此變成四個重複的標題。

- 預設情況下，僅詢問單一決策或運作情節。相關的釐清是可以接受的；依使用者偏好或回答自然匯聚時，詢問多個問題亦屬可接受。切勿將期限、伺服器、預算與值班負責人打包成單一編號項目。
- 計算獨立的資訊請求次數，而非數字或問號。若要評估訪談，請保留對話輪數、獨立主題數、已知事實的重複次數以及對決策無影響的問題數。
- 索取最新的真實案例。若不存在，詳細演練一個明確模擬的案例，並識別在實作前由誰以及如何驗證。切勿強求虛構的統計資料。
- 若開始回答有困難，可提供選用的回答範例。「用您自己的話說／我還不知道」是可以接受的；選取建議選項並不能證明已做出架構決策。
- 當客戶需要描述期望行為時，切勿向其詢問架構、資料庫結構描述或防護隔離。架構師應提出技術機制、透過經授權的來源驗證 API 事實，或向技術負責人請教。
- 「我不知道」會將問題移至登錄表，並附帶負責人與驗證方法。僅在新來源或矛盾出現後才重複該問題，而非僅僅為了填寫範本。

具連結性的範例：「已修正的檔案絕不能自動執行。經理如何識別需再次檢查的版本？」在回答之後，記錄確切訊號與版本；切勿在同一輪對話中新增託管與招募問題。

## 3. 設計涵蓋範圍

維護一份精簡的地圖；文件與先前的回答會直接填入其中，無需重複提問。針對實質資料列：**依據 → 決策／限制 → 知識狀態 → 誰以何物關閉缺口**。切勿將 SKILL.md 的知識狀態替換為通用的「已討論」。「不適用」必須提供理由。不存在每列一題的要求。

| 領域 | 決策的充分依據 |
|---|---|
| 變更與第一範圍 | 當前工作、所需成果與接收者、為何現在開始、納入／推遲的範圍；可觀察的成功條件 |
| 運作案例與方法 | 針對實質任務類別：觸發條件、具體輸入、實質決策、動作、交接、輸出與驗證；一般案例與重大例外 |
| 資料與權限 | 單一事實來源、存取與禁止事項、代表誰的身分執行、確切確認主體；未知權利並非授權 |
| 狀態與失敗 | 執行後何者存留、狀態負責人、重試／取消／副作用對帳、復原與問題負責人；視適用情況 |
| 人工工作 | 任務在何處指派、何處檢視佇列／錯誤、確認或更正與恢復執行於何處發生；回應期限與無回應行為 |
| 可行性 | 期望的試點期限、可用實作者／支援、現有環境、預算／負載限制；影響第一範圍的未知項 |
| 選型與驗收 | 合理解釋的執行做法、能力／輸出合約、重大替代方案、成功／不可接受結果檢查、驗收負責人 |

一個典型範例無法涵蓋相異的權限、使用者或外部副作用類別。按風險與多樣性選取額外案例，並解釋選取理由。切勿為了一場「完整的訪談」而設計整個推遲的積壓工作。

在檢查點，分開處理剩餘項目：

- **阻礙決策／實作：** 回答會改變強制能力、資料／權限邊界、維運擁有權或期限可行性。繼續進行具體釐清，或明確限制相關部分的就緒度。
- **需要工程師驗證：** 例如，管線重新執行合約。識別負責人／角色、確切材料與條件；在未取得存取權前，切勿將驗證描繪為已完成。
- **可提議並進行校準：** 內部逾時或集區大小。展示後果與調校方法；切勿稱其為已達成共識。
- **推遲／不適用：** 理由以及需要時的重新檢視觸發條件。

當宣告範圍內的實質領域具備充分依據時、當進一步進展需要不可用的來源／負責人時，或當使用者停止提問時，即結束調查。在後兩種情況下，現在應交付實質的條件式成果以及確切的剩餘驗證項目。切勿持續提出重複性問題、無期限等待或宣告缺口已關閉。SKILL.md 的停止指示具優先權。

## 4. 診斷：路徑涵蓋範圍而非問卷涵蓋範圍

僅詢問可用材料無法提供的內容。初步擬定 **預期 → 觀察到的差異 → 物件／版本／環境 → 可用佐證**。針對一般稽核，按強制情境與風險選取具代表性的路徑；切勿虛構症狀。

驗證地圖：`義務／路徑 | 具版本資訊的佐證 | 實際檢查了什麼以及如何檢查 | 結論／未知項 | 下一個鑑別檢查與負責人`。視適用情況包含正常、失敗、重試／恢復執行、並行性、替代進入點以及外部副作用邊界。未檢查的路徑不會繼承相鄰路徑的成功。

區分 **負責人斷言／靜態佐證／執行觀察／重現結果**。訪談用以重建預期並尋找來源；它不能取代追蹤記錄、下游合約或測試。README 內容不能證實強制執行。

在每次重大檢查之後，更新假設狀態與涵蓋範圍。若下一個檢查能區分原因且在授權範圍內可用，請執行該檢查；兩輪提問並非停止的理由。若缺乏來源或權限，請交付帶有確切邊界的部分結論，而非斷定性的原因。假設與關閉方法請參閱 [diagnostic-review.md](diagnostic-review.md)。

## 5. 就緒度與交接

陳述三種獨立狀態：

1. **知識：** 涵蓋地圖中的已確認、提議與未知。
2. **協議：** 條件式設計／供核准的架構／使用者已核准。最後一項需要對特定版本或決策的實際確認。
3. **交接：** 草圖／帶有阻礙的詳細內容／足以實作所述範圍。最後一項僅在沒有關鍵未知項、開發者無需捏造主要方法、且已定義權限／職責、介面、結果驗證與可行性限制時才允許。核准並不能證明技術就緒度；技術細節並不意味著已獲得核准。

帶有負責人的待決問題仍屬待決。詳細的隔離部分可在帶有明確邊界的情況下進行交接；這並不會使整個專案具備就緒度。維運品質需透過已實作系統的測試另外確認。

針對稽核，陳述 **在宣告範圍內完成／部分完成**、已檢查路徑以及未確定的原因。完整的稽核並不意味著沒有缺陷，亦不代表在其範圍之外已證實安全。切勿從填寫的欄位計算通用的「理想度」分數。
