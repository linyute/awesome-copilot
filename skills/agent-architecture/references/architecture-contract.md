# 架構交付物合約 (Architecture Deliverable Contract)

這些是單一設計的多個檢視表，可合併為一份 Markdown 文件。請依任務規模調整深度：切勿無故建立空白章節或獨立檔案。每個適用的項目都必須具備決策、佐證或明確標記的待決問題。「不適用」必須提供簡短理由。

## 1. 任務與條件

使用者、價值、情境、輸出格式、例外狀況、現有替代方案以及負責人。表格：`R-ID | 需求 | 來源與狀態 | 決策 D-ID | 檢查 E-ID`。識別關鍵未知項，以及在品質、時間、成本與自主性之間所選擇的取捨。

針對價值卡與人工決策圖，使用 [design.md](design.md) 的第 3 節。說明代理人提供何種變更、假設如何驗證，以及整個流程需要多少人工參與；成功執行與展現出的影響力是不同的兩件事。

## 2. 結構與邊界

系統類型與選擇原因。元件與職責：介面、執行階段／協調機制、模型、領域規則、工具、來源與儲存庫、檢查以及可觀察性。切勿繪製不存在的元件。顯示信任與資料擁有權邊界。若有助於解釋關聯性，簡單的 Mermaid 元件圖即可滿足需求。

使用 [architecture-selection.md](architecture-selection.md) 的適用小節進行拓撲結構合理解釋、委派以及時間互動合約。代理人數量不能取代職責圖。

領域實質內容為必要項目：使用 [capability-design.md](capability-design.md) 繪製主要能力、其方法與輸出。針對選定的技能，提供填入資料的規格與實質結構；針對現有平台，說明何者為重複使用、設定、建構以及仍未驗證的項目。簡單的拓撲結構不會降低行為的完整性。當不需要獨立技能時，規則可存在於單一指示中。

## 3. 執行、狀態與停止

描述執行順序：輸入 → 檢查 → 情境收集 → 模型／工作流程決策 → 動作驗證 → 工具 → 結果觀察 → 狀態記錄 → 回應。將環境的四項功能配置給現有或提議的負責人：

| 功能 | 必須定義且可驗證的項目 |
|---|---|
| 轉譯 (Translation) | 意圖、限制與來源如何轉化為任務與實際載入的情境；當條件衝突或遺失時會發生什麼事 |
| 執行 (Execution) | 誰將模型的提議轉換為具型別的呼叫，並強制執行權限、配額與隔離 |
| 觀察 (Observation) | 工具回應與外部狀態如何轉化為可驗證的結果、事件與後續情境；如何區分錯誤、成功與未知 |
| 修正 (Correction) | 誰選擇繼續、有界限的重試、停止、復原或呈報；需要何種佐證與授權 |

這是職責圖，而非四個新服務。針對每項功能，顯示輸入／輸出、負責人、失敗與檢查；小型助理僅需要精簡且填入資料的路徑。確定性邊界並不會使模型的領域回答變得具確定性或正確。

將**整合**（可從中選取工具的可用能力、結構描述與配接器）與**強制執行**（每個可達呼叫的強制准入檢查）分開。這些是邏輯職責，可存在於單一處理程序中。MCP／工具目錄本身並不強制執行政策；模型不會自行選擇是否通過准入。領域擴充在沒有其負責人決策的情況下，不得削弱基準限制。檢查透過新工具／處理常式、直接呼叫與恢復執行的繞過行為；控制細節如下所述。

針對具有暫停與副作用的任務，描述狀態、允許的轉換、轉換負責人、持久化資料與恢復執行。區分提議的結果、授權的動作、已傳送、已確認、副作用未知、錯誤與已取消。「已取消」並不意味著已完成的副作用已經復原。

**迴圈或重試必須提供限制表格：**

| 欄位 | 記錄內容 |
|---|---|
| 反覆運算與巢狀層級 | 全任務與子任務限制；誰負責計數強制執行 |
| 時間 | 整體期限、個別呼叫逾時、人工等候、取消 |
| Token 與費用 | 包含推理、重試與工作者的任務預算；需要時的使用者／租戶配額 |
| 工具 | 頻率／次數限制；重複的相同引數與缺乏進展 |
| 停止結果 | 部分結果、解釋、人工佇列或受控的繼續執行 |
| 校準 | 數值／範圍、狀態「提議／已測量／已同意」、用於選取閾值的情境 |

執行階段負責強制執行限制。提示中的指示可能有助於行為，但並非限制機制。即使是固定的工作流程也需要逾時、有界限的重試以及錯誤結果；代理人迴圈的缺失僅會使對應的欄位不適用。

針對重大控制措施，填入：`需求 → 強制執行點 → 涵蓋路徑／工具類別 → 相對於副作用的時序 → 失敗／逾時 → 重放／恢復 → 取消／並行 → 檢查`。保護防護名稱或 SDK 設定並不能證明涵蓋了 Shell、託管工具與替代處理常式。在動作之後才完成的平行檢查並不能強制執行事前禁止措施。識別關閉每條必要路徑的機制。

區分目標花費、允許已啟動呼叫超支的限制，以及下一個操作的嚴格准入。在請求前檢查累積成本可能會允許在完成後發生超支。針對嚴格的總額限制，指定准入／保留負責人、成本上限估計，以及並行工作者之間剩餘預算的協調；若無法取得上限，則嚴格上限未經證實。切勿將相同的完整預算配置給每個工作者。

從可驗證的儲存庫復原狀態，而非對話承諾。外部動作與本機記錄之間的失敗需要對帳路徑；單靠檢查點並不能確保單一外部副作用。

釐清寫入何時變為持久化：在繼續之前、非同步、或在完成時；當機時會遺失何種進度，以及哪些步驟會重放。檢查點屬性與外部 API 保證是不同的合約。測試復原期間「副作用已完成，本機寫入未完成」的缺口以及過期的權限。

針對長時間執行的任務、暫停以及跨工作階段的工作，請使用 [execution-continuity.md](execution-continuity.md)：檢查點／交接、儲存層級、具備復原目標的監督者、跨時間範圍的預算、非同步人工參與以及競爭任務排程。展示填入資料的正常轉換與實質失敗、適用性以及現有平台機制。這些是環境職責，而非對獨立服務或檔案的要求。

## 4. 情境、知識與記憶體

- 每個情境部分的來源、讀取者權限、新鮮度、連結／版本，以及發生衝突或缺失時的行為。
- 預算：系統指示、歷程記錄、工具定義、結果、擷取、保留給回應與所需推理的配額。選取、將大型資料移出情境、壓縮以及隨需載入的策略；在真實格式與語言上的測量數據。
- 壓縮會保留目標、限制、主要來源連結、確認事項與副作用識別碼。授權與副作用狀態保留在壓縮文字之外的執行階段中。測試壓縮後的繼續執行。
- 若需要 RAG：語料庫準備與更新、具結構感知的區塊劃分、搜尋方法、重新排序條件、產生情境、引述、空結果與過期文件。在資料到達模型之前檢查 ACL；索引與快取需考慮刪除與撤銷存取的情況。
- 若需要記憶體：工作記憶體、情節記憶體、語意記憶體、程序記憶體——目的、使用者／租戶範圍、來源、時間戳記／生命週期、讀取／寫入、並行性、更正／刪除以及事實驗證。不需要全部四種類型。
- 區分權威狀態、原始佐證與衍生摘要。對照來源驗證摘要；既有編寫的 Wiki 不會自動變成「僅僅是快取」。財務／商業副作用的強制記錄不能推遲為選用的背景記憶體。

若代理人變更記憶體或程序，描述 `觀察 → 候選者 → 驗證版本 → 啟用程序`：來源、適用性、新鮮度、衝突解決、變更權限、驗證與復原。已儲存、已建立索引、可供選取、實際載入與行為已驗證是不同的狀態。不受信任的經驗或一次成功的執行不會自動成為規則。准入可由人工或在其範圍內預先商定的政策執行；不需要對每個記憶體進行全面的人工核准。行為變更條件請參閱 [evaluation-design.md](evaluation-design.md)。

## 5. 工具合約與權限

針對每個重大工具：目的與使用時機、輸入／輸出結構描述與欄位意義、先決條件、領域限制、副作用類型、委託人／租戶權限、錯誤、逾時、重試准入、結果限制與副作用確認。

檢查選取介面：相鄰工具是否能透過名稱／說明進行區分、ID、單位與引數數值是否明確、以及錯誤與允許的後續步驟是否清晰？為重大工具展示填入資料的呼叫與回應、正向選取範例，以及切勿選取該工具的案例。不需要為每個 API 端點提供獨立的包裝器；若不隱藏副作用與必要檢查，領域層級的聚合操作是可以接受的。結果需支援篩選／分頁／截斷指示器，並保留必要的識別碼、來源與完整性。簡潔絕不能讓部分資料看似完整。

針對寫入操作，還需指定：操作識別碼、接收系統的等冪性保證與有效期限、重試與模稜兩可回應的語意、讀回／對帳、補償或不可逆性。若沒有伺服器處理合約，「具有等冪性金鑰」是不夠的。兩個刻意相異的操作若具有相同參數，並不會使其變成同一個請求。

針對人工確認：確切動作、目標、參數、委託人與授權到期時間；參數變更、權利撤銷、重複使用與恢復執行時的行為。未獲許可前，不得執行重大動作。已商定的自主性政策可能允許特定動作類別；模型不得自行擴充該政策。

將情境准入表示為 `動作 → 資源／環境 → 委託人／租戶 → 權限與條件 → 檢查機制 → 允許／拒絕／呈報`。在任務內測試資源、租戶、參數與操作規模的變更。自主性層級不能取代此表格：權利不是透過減去抽象分數來計算的，也不會隨著模型信心度而增加。自動轉換僅在先前已接受的政策內才有可能。

## 6. 威脅與失敗

簡短表格：`情境／資產 → 信任邊界 → 控制機制 → 檢查 → 殘餘風險／負責人`。

檢查訊息、文件、工具 metadata 與結果中不受信任的指示；跨租戶存取；透過回應／日誌／工具的外洩；過多權限；核准後的參數替換；記憶體投毒；無效的模型輸出。注入分類器並不能取代授權與隔離，亦無法證明不存在攻擊。

若存在程式碼執行、Shell、瀏覽器或不受信任的擴充功能，請顯示實際的隔離邊界：代理人處理程序、內部／外部工具、網路、檔案系統、認證、租戶與產物傳回。針對單一工具的容器無法隔離主機工具；虛擬檔案系統與匯入篩選器並不能證明具備安全沙箱。根據所需風險比較受限的本機執行、遠端環境或全處理程序隔離，而不需要對文字助理要求容器。擁有該 API 的實體保留其專屬授權。未知的設定是佐證缺口，而非已證實的漏洞利用。

針對每個相依性：失敗、逾時、速率限制、無效／空回應、重試與復原。為每個操作選擇阻擋、可接受的降級或呈報。「唯讀」並不允許在 ACL 檢查失敗時暴露他人的資料。後備機制不得繞過存取、確認或資料落地（data residency）要求。

針對長時間執行與並行的任務：重複交付、單一任務有兩個處理常式、背壓（backpressure）、使用者停止、核准過期，以及外部副作用後的當機。佇列、斷路器與區域備援僅在需求能證明其成本合理時才需要。

## 7. 品質驗證、經濟效益與維運

針對重大失敗情境，使用 [diagnostic-review.md](diagnostic-review.md) 進行分析：失敗在何處顯現、必須區分哪些原因、以及何種訊號能防止假性成功。在全新設計中，這是在測試架構假設；審查執行中的代理人則需要實際佐證。切勿根據思想實驗就將設計標記為行為已驗證。

評估計畫：真實經授權／去識別化的情境、領域負責人標籤、一般與困難案例、無答案、衝突來源、不安全輸入、失敗與恢復執行。將調校資料與獨立驗證分開。測量輸出與動作的正確性、適用時的基礎／擷取品質、錯誤阻礙、呈報率、延遲以及每個已接受任務的成本。模型評審是帶有誤差的測量工具，而非證明。

使用 [evaluation-design.md](evaluation-design.md) 制定評估合約、強制閘門、涵蓋範圍與測量誤差。切勿將獨立的品質軸向合併為會隱藏強制限制違規的平均值。

使用 [validation-loop.md](validation-loop.md) 建立驗證迴圈與佐證組合包（Evidence Bundle）。定義七項功能的適用性、配置與裁決後果；獨立服務並非強制要求。針對實質結論，連結需求、輸出版本、已執行的檢查與佐證。若存在守護者／審查者（Guardian/Reviewer），請描述其專屬合約與誤差；事後觀察並非事前禁止。

記錄模型、提示、工具結構描述、語料庫以及周遭執行階段版本以進行可比較的執行。單一層級的變更需要重新測試受影響的情境。不需要模型內部的思維鏈：調查需要的是可用的事件、已遮蔽機密資訊的輸入／輸出、政策決策與動作結果。

成本計算包含每次 LLM 呼叫與重試、分開計費的 token（無重複計算）、擷取與外部 API、基礎架構與支援。說明假設與依任務長度／分支劃分的範圍；切勿將單次呼叫的成本呈現為已完成任務的成本。

可觀察性：關聯的任務／執行／工具／動作 ID、階段與持續時間、預算與停止原因、工具選取品質、成功／空白／失敗的結果、來源版本與實際動作成果。排除機密資訊；定義追蹤記錄存取、保留與刪除。針對每個重要指標，說明其觸發何種決策或回應。

維運計畫：負責人、受控試點、准入與復原條件、停止新動作、復原以及事件分析。這是提議的計畫，而非已完成的發行。

**複合版本與生命週期。** 將模型、提示／技能、工具、政策、執行階段與實質資料連結為可識別的代理人版本。針對變更，識別受影響的情境、准入、持續任務的相容性與復原。還原程式碼／提示並不會復原外部副作用，也無法保證新狀態與舊版本的相容性。先診斷漂移；切勿自動開出微調的處方。

針對具有持久化狀態／背景動作的代理人，定義淘汰流程：負責人與觸發條件 → 禁止新執行、排程與重新交付 → 完成／取消／轉移作用中任務 → 對帳已發起的副作用 → 撤銷存取權限 → 依適用規則處理記憶體、產物與日誌 → 替代流程與關機佐證。停用 HTTP 端點並不會停止 cron、佇列或執行中的工作者。存取撤銷順序必須保留經授權的對帳，同時不允許產生新副作用；若無法進行安全對帳，請明確移交給負責人。測試停用後的延遲事件。一次性本機助理僅需要適用的更新與停止規則。

使用 [evaluation-design.md](evaluation-design.md) 規劃改進週期、受保護的不變量、比較預算以及接受／復原規則。針對技能，測試正確程序的選取以及無需該程序的案例。結構化檔案驗證不能取代行為測試。

## 8. 決策與就緒度

知識、協議與交接的涵蓋範圍與獨立狀態定義於 [discovery-protocol.md](discovery-protocol.md)。在指派「供實作」之前，檢查第一範圍期限、建構／支援可用性、預算限制與技術相依性。指派了負責人的未知項並不算已關閉。提議的實作即使存在阻礙也可以是具實質內容的，但阻礙會限制就緒度。

### 人工路徑與重大設定

包含填入資料的使用者／操作者路徑：**事件 → 人員在何處得知該事件 → 他們看到的內容 → 可用動作與權利 → 變更內容 → 如何繼續 → 無回應時會發生什麼事**。針對非同步工作，展示具體的佇列資料列、負責人以及通知／回應範例，而不僅僅是內部狀態。現有介面即可滿足需求；新儀表板需要提出合理解釋。

例如，在合成 Jira 流程中：`CAT-42 | 等候檔案 | 經理 | 原因：兩個 CSV | 透過留言命令選取確切附件 | 檢查權限與版本後重新排入佇列`。技術失敗則分開處理：`CAT-43 | 驗證失敗 | 管線負責人 | 安全日誌連結 | 修復原因並明確重試`；針對已關閉的 Jira issue，定義可存取的摘要介面，而非承諾一個看不見的內部佇列。未指派的負責人或不可用的管道屬於待決問題。切勿將此範例呈現為另一專案已確認的需求。

針對重大數值決策，提供 `數值／範圍 | 狀態與依據 | 使用者後果 | 替代方案 | 校準方法與決策負責人`。切勿將每個內部常數製成表格。例如，「每天 10 次重試」伴隨 50 次失敗，意味著即使沒有新失敗，至少也需要五天才能清除積壓工作；請將其與期限進行比較。考慮採用優先處理已修正任務的共享預算或其他模式，而非選擇一個不考慮後果的數字。未知的持續時間／成本需要測量，而非產能承諾。試點時間表與可用人力是獨立於執行階段預算的限制。

關鍵決策：`D-ID | 情境 | 選擇 | 替代方案 | 後果 | 重新考量觸發條件`。

完成前檢查實質就緒度：

- 每個主要情境都具有能力、具體方法、所需資料與輸出合約；選定的技能需具備實質描述，而非僅僅列出名稱。
- 指示／材料結構需說明載入內容與原因；平台貢獻與提議的新增項目分開。
- 透過填入的資料詳細演練一個常見案例與一個重大失敗案例，直至使用者回應；結果佐證與所需的人工判斷皆清晰可見。
- 需求具可追溯性，執行／失敗路徑一致，且關鍵邊界／合約、限制與檢查皆已定義。
- 開發者可以在無需新領域設計的情況下實作約定的行為。元件清單、空白範本或未提供方法的「由 LLM 分析」會讓結果停留於草圖階段。

當開放式數值設定或實驗的影響與關閉方法明確時，這些設定是可接受的。未知的核心方法、權限或基本拓撲結構屬於特定的就緒度缺口；請交付帶有該限制的完成套件，而非自動重啟問卷。分別說明成果深度（草圖／帶有限制的套件／供實作的套件）、使用者協議以及實際測量所得。套件完整性、其核准狀態以及維運品質是相異的屬性。

## 9. 最終交付格式

分別檢查實質架構就緒度與匯出就緒度。標準最終交付物為依據 [result-delivery.md](result-delivery.md) 所產生帶有轉譯 Mermaid/C4 圖表、可編輯文字與圖表原始碼的 PDF。該檔案亦定義了使用者要求的例外狀況與匯出不可用時的行為。報告需保留實際架構狀態，切勿將設計轉變為已確認的實作。
