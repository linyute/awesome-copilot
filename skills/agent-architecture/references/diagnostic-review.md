# 失敗診斷與修正審查 (Failure Diagnosis and Fix Review)

適用於觀察到的失敗與回歸。針對未實作的架構，使用相同的提問作為紙上情境檢查：這是風險預測，而非重現。此程序用以完善稽核；它不授權變更代理人或執行外部動作。自行執行可用的安全讀取；將不可用的測試表示為具備預期成果的具體計畫。

## 1. 記錄案例與知識邊界

建立簡短卡片：任務／驗收條件 → 預期結果 → 實際結果 → 輸入／材料狀態 → 版本／近期變更 → 可用事件／產物 → 影響。識別來源：使用者回報、檢查過的程式碼、追蹤記錄、執行的檢查。切勿將轉述的追蹤稱為自身的觀察。

簡短的轉述或提示片段並不能證明完整指示、技能或其他元件缺少領域方法。在確認真實執行路徑之前，切勿將其不完整性列為獨立的重要發現。這是待檢查的假設；請獨立記錄已證實的輸出／驗證器缺陷。

記錄已知失敗次數與檢驗案例總數；切勿將可用追蹤外推至其他案例。另外檢查「成功」案例是否確實符合領域條件。沒有追蹤記錄意味著原因未知；這尚不能證明全系統缺乏日誌記錄。

從外部可觀察的資料建立簡短鏈條：輸入 → 選定的方法與實際載入的情境 → 工具請求／回應 → 轉換 → 儲存的輸出 → 檢查 → 使用者回應。找出第一個**可觀察**的差異。錯誤起源可能更早；下游為空以及遺漏該問題的驗證器可能是個別的缺陷。不需要隱藏的模型思維鏈。

在保留失敗條件的同時將範例最小化：情境長度、事件順序、租戶／權利、版本、並行性、重試／恢復執行、外部服務狀態。縮短後失敗消失是觸發條件的佐證，而非任務定義不佳的證明。切勿將單次嚴重失敗斥為雜訊；兩次重複並不能證明原因。按風險與可用預算成比例規劃機率性重複測試。

## 2. 選取層級與競爭解釋

表格提供搜尋方向，而非現成的診斷。症狀可能跨越多個層級；模型本身也可能是原因或互動參與者。

| 層級 | 鑑別檢查 |
|---|---|
| 目標與領域方法 | 使用者需求、驗收條件與實際選取的程序是否一致？是否涵蓋所需能力？ |
| 指示與情境 | 何者可用、找到、選取、截斷以及實際傳送給模型？比較組裝前後，包含版本／存取範圍 |
| 狀態與延續性 | 讀取了哪個檢查點、還原了什麼、決策／版本／權利是否改變；當機／重新交付後會發生什麼事？ |
| 工具與環境 | 參數是否符合任務、存取／資料是否符合預期、原始回應是否符合配接器輸出；HTTP 200 內的空白、分頁與領域錯誤是否已處理？ |
| 模型與協調機制 | 在正確輸入下，輸出合約是否遭到破壞；在受控比較中路由、停止、重試與品質是否改變？ |
| 驗證與成功回報 | 領域輸出／外部副作用是否經過檢查、真實路徑是否通過控制、能否拒絕看似合理的錯誤答案？ |
| 可觀察性 | 版本、事件與輸出是否能在不含機密資訊的情況下連結至單次執行；佐證確切中斷在何處？ |
| 指標與誘因 | 有用輸出是否有改善，或僅是分數／自我評估提高；是否存在隱藏錯誤、重做、獨立案例上的失敗？ |
| 測量系統 | 執行／評估了多少任務；困難案例是否在執行器、評審／剖析器或歸納器中遺失；資料集／評分器版本是否相符？ |
| 委派與整合 | 接收者是否看到目標、限制、版本與剩餘總預算；收到的產物是否符合整合輸出，並保留依據／衝突？ |
| 累積與成本 | 工作階段之間何者在增加：載入的情境、過期規則、重做、歷程記錄／快取；測量是否證實增長來源？ |

針對重大未釐清原因，通常選擇 2-4 個合理假設，而非表格中的每一列。格式：`假設 → 支持／反對佐證 → 剩餘未知項 → 最小鑑別檢查 → 支持或削弱它的結果`。已證實的缺陷不需要刻意尋找替代方案。依據解釋的鑑別力、風險與成本來選擇下一個讀取／測試，而非依據熟悉的技術棧。

針對情境遺失，檢查冷啟動或恢復執行：從**實際可用且已載入**的材料中，代理人能否重建目標／使用者、工作／驗證方法、當前進展／下一步、當前決策以及完成條件。依領域調整具體細節：linter 命令對寫程式的代理人很重要，但非適用於所有代理人。比較來源 → 可定址性／存取 → 載入器選取 → 組裝的情境 → 觀察到的回答。檔案的存在不能證明已載入；錯誤的回答不能證明檔案不存在。修正可能在於讀取路徑、新鮮度或模型。

## 3. 檢查檢查本身

使用 [validation-loop.md](validation-loop.md) 檢查完成／檢查器合約；使用 [execution-continuity.md](execution-continuity.md) 檢查一致的快照／交接。依觀察到的症狀選取額外的鑑別案例：

| 症狀 | 比較與允許的結論 |
|---|---|
| 所有階段皆完成，無效益 | 需求達成度、初始價值假設、基準、測量窗口。定義不良、缺乏副作用與資料不足是不同的成果 |
| 人員精疲力竭或代理人永遠在等候 | 標註必要／不必要的請求、決策材料的完整性、人員可用性、輸入流。區分代理人行為與佇列過載 |
| 完整的文件套件給出假性成功 | 輸出／檢查版本與內容、副作用狀態、遺失／錯誤／未知處理。清單完整並不能證明佐證具相關性 |
| 長工作階段品質劣化 | 分開檢查全新工作階段、累積歷程記錄、壓縮、交接與當機；確保最小化保留了觸發因素 |
| 進度檔案存在，繼續執行卻錯誤 | 權威記錄 → 檢查點識別碼／完整性 → 載入器 → 實際提供的情境 → 下一步。區分部分寫入、不良載入與不良決策 |
| 控制器在寫入後才拒絕 | 裁決時序相對於副作用、可達的事前控制、控制器不可用處理；切勿將防止之功歸於觀察者 |
| 復原後權利改變 | 確切動作、當前委託人／租戶／資源／參數／核准；新工作階段不會從摘要繼承權限 |
| 已停用的代理人持續採取動作 | 觸發來源：端點／cron／佇列／重試／工作者；副作用開始相對於停用時序。區分舊動作的延遲收據與新禁止動作 |
| 歸檔使繼續執行緩慢／錯誤 | 補水（Rehydration）延遲、遷移 ID／版本／完整性、當前 ACL／刪除、快速復原套件。切勿將不可用的歸檔與模型錯誤混淆 |
| 處理程序重新啟動，承諾的復原卻未出現 | 宣稱的 RTO/RPO 範圍／起點、偵測／佇列／載入／對帳時間、實際持久化進度遺失；檢查點間隔不是 RPO 測量值 |
| 重新啟動花費金錢或超出總限額 | 任務／工作階段／時間範圍連結、窗口邊界的保留／延遲成本、並行准入、重新啟動限制、斷路器狀態 |
| 聊天反應迅速，背景任務永未完成 | 負載／優先級設定、租戶配額、佇列年齡、期限、資源匱乏、安全先佔；將資源等候與卡住的代理人分開 |
| 批次決策遺失或過度授權 | 事件 ID、確切版本／動作列表、變更項目、過期／重新交付；人工等候絕不能佔用工作者或自動授權 |

針對修正審查，重現受影響的轉換與允許的對照控制案例。修正「完成」的回報並不能解決錯誤結果的原因；成功停止新任務並不能證明已發送操作的命運。

儲存庫、監督者、預算、非同步決策與排程合約位於 [execution-continuity.md](execution-continuity.md) 的第 5–9 節。當另一元件可證實地執行該功能時，缺乏獨立服務並非一項發現。使用實際設定／追蹤診斷機制；「環境比模型更重要」並不排除模型或互動缺陷。

追蹤 `需求 → 已檢查結果 → 單一事實來源 → 真實驗證器／閘門 → 負向結果處理 → 使用者狀態／回應`。區分：無檢查；檢查未執行；在另一路徑上執行；無法區分對／錯；結果被忽略；檢查了過期的產物。CI 檔案、hook 或 lint 命令既不能證明執行，也不能證明實質涵蓋。

針對品質主張，套用 [evaluation-design.md](evaluation-design.md)：強制准入、有效的替代軌跡、測量失敗、涵蓋範圍、可比較性。涵蓋範圍下降伴隨分數上升並不能證明代理人改進。針對執行控制，依據 [architecture-contract.md](architecture-contract.md) 第 3 節檢查時序與涵蓋路徑：檢查可能執行正確但為時已晚；檢查點可能儲存了狀態但允許重複的外部動作。診斷應指出違反的義務與機制，而不僅僅是缺失的元件。

針對實質條件，提供正確範例與看似合理的錯誤範例：錯誤時期、空資料、另一租戶、不存在的連結、帶有 `done=true` 的不完整輸出。檢查必須依獨立依據區分它們。負向控制必須周遊接受調查的相同閘門／路徑；對人工錯誤執行獨立 linter 並不能證明正式環境閘門有效。刻意製造的缺陷僅屬於經授權的隔離複本／測試資料；否則應提出測試提議而不執行它。

模型自我評估與 HTTP 200 不能為成果提供保證。程式化後置條件檢查可形式化的屬性；人工可對照明確量表與來源資料評估含義／領域實用性。LLM 評審同樣需要在標記的良好／不良案例上進行驗證以及測量假性接受／拒絕率。獨立評審、端對端或單一整體分數不能取代所有佐證類型。檢查代理人是否能替換條件、測試資料或最終狀態以獲取全綠檢查。

## 4. 設計比較與最小修正

首先將原因定位與遏制已證實的危害分開。即使分析為空的原因仍未知，防止假性成功仍屬必要。這並未解決資料遺失的原因。修正已確立的機制；新記憶體、圖形、評審代理人或模型需要可測試的效益假設，並與更簡單的選項進行比較。

為了進行比較，固定基準版本、任務、狀態／資料／工具回應、條件、設定與限制。一次變更一個因素；當模型與情境組裝器同時變更時，盡可能比較全部四種組合以暴露互動效應。虛擬工具回應可定位下游行為，但無法測試正確的請求建構或即時整合。記錄該限制。若無舊基準，切勿自信地將回歸歸咎於某個元件。

停用某個元件是輔助性假設實驗。沒有變更可能意味著備援、未被使用或樣本薄弱；效能惡化顯示在這些條件下的貢獻，並不自動代表系統的主要瓶頸。切勿為了診斷而停用真正的 ACL、核准、成本限制或其他強制控制。切勿根據少數一般成功的任務提議移除它們；需要已接受的合約與相關邊界檢查。

比較領域正確性、假性成功／拒絕、使用者心力、時間與已完成任務的成本。保留先前成功的回歸案例以及調校之外的獨立案例。切勿強加通用的執行次數或將強制替換模型作為最後步驟：佐證、影響與檢查成本決定順序。

## 5. 變更審查與完成

針對每次重大修正，檢查：它是否關閉已確立的因果鏈條 → 在每條受影響路徑上（包含繞過／恢復執行）→ 不削弱強制控制 → 何者證明已關閉 → 哪種結果需要復原。將消除原因、遏制後果以及額外可觀察性分開。在達成協議前，將負責人與數值閾值標註為提議性質。

報告必須能立即採取行動：已確認的缺陷／最小修正，或帶有預期成果的下一個鑑別檢查。狀態：`已確認 / 在已檢查條件下遭駁回 / 假設 / 檢查不可用`。針對修正審查，區分 `已設計 / 依程式碼實作 / 行為已驗證`；實驗計畫不是其成果。當僅關閉了假性成功回報時，切勿承諾已解決整個回歸問題。

當重大發現具備佐證、關閉計畫或包含下一個最小檢查的精確缺口時即停止。不要為了完整性而檢視每個層級，或在沒有新鑑別問題的情況下持續進行實驗。將後續審查限制在先前發現與變更路徑上；更廣泛的重新考量需要新的實質佐證，而非遺留的檢查清單項目。
