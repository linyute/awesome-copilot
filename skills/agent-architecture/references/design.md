# 逐步設計 (Step-by-Step Design)

## 1. 理解任務

閱讀提供的文件與可用情境。首先記錄：

- 誰使用該系統、他們目前如何工作，以及應改善何處；
- 已知的限制、已接受的決策，以及業務規則負責人；
- 現存項目、可用資料，以及單一事實來源位於何處；
- 會改變安全性、邊界、成本或執行做法的未知項。

若幾乎沒有請求細節，從一個真實案例開始：「誰來找代理人、帶著什麼，以及他們認為何種結果算成功完成工作？」切勿從選擇資料庫、模型或工具清單開始。

## 2. 進行適應性訪談

遵循 [discovery-protocol.md](discovery-protocol.md)：可見階段、單一實質問題、涵蓋範圍圖，以及分開的就緒狀態。下表是選取下一個實質缺口的參考，而非強制提問佇列。從期望的變更與最新的真實案例開始；初步設計並不會結束調查。主題可附帶理由標註為「不適用」。

| 主題 | 欲發掘的內容與實用問題 | 取決於回答的決策 |
|---|---|---|
| 使用者與價值 | 誰是使用者、客戶與規則負責人？目前如何解決任務？損失在何處？採用後有何改變？ | 是否根本需要 AI、產品邊界、基準 |
| 情境與輸出 | 詳細演練真實的一般、困難與禁止案例。輸入是什麼？良好輸出是什麼？誰接受它？ | 輸出合約與驗收情境 |
| 錯誤與優先順序 | 哪些錯誤令人不悅對比不可接受？發生衝突時，何者更重要：準確度、完整性、速度、成本、自主性？ | 品質條件、呈報、控制層級 |
| 領域與邊界 | 術語、實體、生命週期、規則、合理例外。排除哪些相鄰任務？誰修改規則？ | 領域不變量、負責人、相依性 |
| 授權 | 讀取、提議、儲存草稿或執行？代表誰？哪些動作需要人工，他們確切確認什麼？ | 動作矩陣與授權政策 |
| 人工參與 | 誰可用、何時、多快？如何取消、更正、拒絕、繼續？隔夜或核准過期時會發生什麼事？ | 真實而非名義上的呈報 |
| 情境與知識 | 哪些資料對決策是強制的？資料在哪裡、誰擁有它、多常變更？哪些來源優先以及如何處理衝突？ | 直接 API、搜尋、RAG、情境組裝 |
| 範例與資料權限 | 是否提供經授權的輸入、回答與錯誤回答範例？標籤、去識別化、語言、格式、資料量、存取限制？ | 可測試假設、語料庫、評估集 |
| 記憶體 | 任務內、跨工作階段、跨使用者必須記住什麼？誰可寫入、更正、刪除？如何區分意見與事實？ | 各種記憶體類型的需求與生命週期 |
| 工具 | 實際需要哪些系統／操作？API 合約、負責人、錯誤、限制、允許的重試、副作用驗證？ | 配接器與工具邊界 |
| 負載與互動 | 聊天、事件、排程、批次？尖峰並行量、任務持續時間、串流、等候、重新交付？ | 同步／非同步、佇列、狀態、背壓 |
| 非功能性需求 | 目標延遲／可用性、每個已接受任務與時期的預算、配額、預期增長？何處可簡化？ | 限制、容量、經濟效益 |
| 機密性與信任 | 誰的資料、哪些租戶、誰能看到什麼？外部文件、檔案、個人資料、允許的提供者／地區、保留／刪除？ | 信任邊界、隔離、機密、外洩 |
| 維運 | 誰支援、調查、復原？團隊技能與現有技術棧？如何變更模型、規則、工具、來源？ | 解決方案規模、可觀察性、發行 |
| 第一範圍可行性 | 試點期限、實際可用於建構／支援的人力、允許的花費？依影響分開釐清；將「未知」路由至負責人 | 試點範圍、可用相依性、資源驗證計畫、交接阻礙 |

在獲得回答後，首先判定是否依據 SKILL.md 交付或更新設計。若仍需訪談，簡要說明目前已知內容以及下一個問題能解鎖何種決策。切勿向使用者要求技術術語：學習期望的行為並將其轉譯為架構。當架構師能夠提出合理解釋的提議時，切勿將內部機制選型轉嫁給客戶。

需求登錄表：`ID | 陳述 | 來源／範例 | 優先順序 | 驗收條件 | 狀態`。針對待決問題，加入影響、回答負責人與驗證方法。切勿將每個問題都變成獨立文件。

## 3. 形成可測試的需求

本節及後續各節描述架構師在交付物上的工作。切勿讓使用者替您填寫。使用 discovery-protocol.md 釐清實質缺口；獨立制定技術提議並驗證可用來源。

將強制性與期望性分開。小型代理人需要少數幾個端對端條件；複雜專案需要包含可衡量成果的精簡集合。

使用 [evaluation-design.md](evaluation-design.md) 制定驗收合約，包含強制閘門與測量涵蓋範圍。

填入價值卡：`問題 → 基準 → 預期變更 → 測量 → 觀察期 → 負責人 → 重新考量條件`。價值可以是非財務性的。將其連結至領域能力；正確完成工作、展現出效益以及評估效益的佐證不足是不同的成果。說明何者能證偽該假設，以及在已接受政策下應採取的決策；未證實的效益不需要自動復原。切勿將卡片變成另一份問卷或強制性的 PRFAQ。

範例：代理人準備了一份正確的報告，MAU 成長了 10%，但價格與獲客管道也發生了變化。計算已確認；實驗的因果貢獻尚未確立。需要適當的比較方法與觀察期；負向或不具決定性的研究結果也可以是實用的任務成果。

針對重大的人工決策，繪製：`決策 → 負責人 → 佐證／選項 → 確切確認 → 等候期限 → 無回應行為`。估計佇列資料量與可用的人工時間。若代理人準備了 100 個項目而負責人只有 30 分鐘，提出優先順序排序、進流限制或特定版本的允許批次審查；更快的產生並不意味著整個流程更快。依據 evaluation-design.md 評估必要與不必要的呈報品質。

拆解「99% 品質」：成功定義、分母、允許的錯誤、類別／語言、自動化比例、標註者、資料集與測量週期。僅針對已回答請求的準確度可能會隱藏廣泛的拒答情況。模型信心度的自我評估不能取代經校準的條件。

分開處理：

- 對照權威狀態檢查且帶有明確例外的領域規則；
- 需要範例、測量與錯誤容忍度的啟發式與品質判斷；
- 仍屬提議性質的未確認目標。

切勿將提議的指標、預算或 SLA 描繪為使用者需求。當資訊不足時，解釋何者可進行條件式設計，何者不能視為具備實作就緒度。

## 4. 比較架構選項

閱讀 [architecture-selection.md](architecture-selection.md) 並填入與任務成比例的選型卡：基準、合理的替代方案、效益／成本、驗證、重新考量條件。僅在存在時才制定委派與長時間互動合約。

具體分支：

- **知識：** 請求資料、直接 API、全文檢索、RAG；行為微調無法取代新鮮的權威事實。向量資料庫並非准入要求。
- **記憶體：** 任務狀態與對話歷程記錄並非長期知識。「不需要」對每種類型皆有效。
- **MCP：** 作為合適客戶端／系統的整合邊界相當實用；少數穩定功能可能僅需要一般呼叫。協定本身不賦予任何權限。
- **服務拓撲結構：** 為了實際的職責、隔離或擴充邊界而劃分處理程序／服務。代理人數量不決定微服務數量。
- **模型：** 首先是能力、資料、格式、成本、延遲與後備要求。接著是包含最新來源的精選名單，以及使用相同情境與周遭執行階段的比較計畫。

## 5. 設計領域能力

閱讀 [capability-design.md](capability-design.md)。將主要使用者情境轉化為能力圖、職責配置以及所需技能的規格。描述工作方法、情境選取規則與輸出範例。這是架構師根據收集到的需求所做的工作，而非另一份客戶問卷。

針對選定的平台，將已確認的現有機制與設定、新技能／整合以及未驗證的能力分開。若方法需要領域專業知識，提出並標明明確狀態與領域負責人驗證；切勿以自信的提示取代缺失的知識。

## 6. 描述並檢查設計

使用 [architecture-contract.md](architecture-contract.md) 填入並驗證設計。初步草圖允許開放細節；已完成的套件必須符合該合約的實質就緒條件。展示一個填入資料從輸入到輸出的常見情境，以及一個重大失敗案例：中間資料、能力選取、能力輸出、控制與使用者成果。若無真實資料，使用明確標註的合成範例；切勿將模擬演練稱為已執行的執行。確保元件、圖表與合約描述的是同一個系統。

雙向檢查可追溯性：每個需求都有決策與驗收方法；每個元件都有需求或強制控制。移除未使用的提議元件並保留已接受的取捨。

最後，依據 discovery-protocol.md 分別說明知識、協議與交接狀態。切勿在測量前自動繼續進行撰寫程式碼或承諾未來系統的品質。

依據 [result-delivery.md](result-delivery.md) 格式化已完成的成果：架構 PDF、提議代理人的轉譯圖表、可編輯文字以及圖表原始碼。這是設計交付的一部分；不需要額外的匯出請求。
