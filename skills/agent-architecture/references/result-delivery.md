# 完成設計與診斷：PDF 與圖表 (Completing Design and Diagnosis: PDF and Diagram)

本合約適用於在使用者任務上使用 agent-architecture 的成果。關於開發／更新該技能本身的報告不能取代該成果。預設情況下，應以實際的本機產物完成，而非提議稍後匯出。明確要求其他格式或不需要檔案的請求具優先權。

## 依模式劃分的內容

| 模式 | 所需的最終 PDF 內容 | 視覺化說明的內容 |
|---|---|---|
| 設計 | 目標／需求與狀態；選定的決策／替代方案；領域能力、方法、情境；適用合約、限制、授權；填入資料的範例；驗收／待決限制 | 提議的代理人、職責／資料邊界、主要執行路徑 |
| 稽核或診斷 | 物件／版本／審查範圍；實際佐證；依優先順序排列的發現；失敗鏈／假設；最小修正／關閉檢查；未知項／結論限制 | 實際路徑、首個可觀察的差異、遺漏該問題的控制機制；明確標記的提議變更 |
| 後續審查 | 先前發現的狀態、檢查過的 diff／新佐證、已關閉與仍未知的項目 | 受影響的路徑或控制變更，無需重新進行完整重新設計 |

依任務調整規模：小型案例可提供精簡報告。PDF 包含實質成果，而非僅僅連結至不存在架構的摘要。若 PDF 明確說明其目的與決策連結，詳細的表格／佐證可作為附錄或隨附的可編輯文件。保留來源連結／版本以及「需求／提議／假設」與「已設計／已檢查／已驗證」的狀態。報告日期不能取代佐證日期。排除機密資訊與敏感原始資料。

## 針對兩類讀者的結構

以簡要的**負責人決策頁**開頭：變更內容、第一／推遲範圍、選用的做法與原因、誰使用／支援／接受、期限／資源（或其未知狀態）、重大取捨、負責人決策以及下一步動作／負責人。針對診斷，以以下內容取代產品計畫：檢查了什麼、主要結論／後果、第一步動作以及何者仍未證實。此頁面不能取代技術實質內容，也不得要求以單一「是」全面核准整份文件。

接著以穩定的順序建立成比例的技術套件：

1. **依據與邊界：** 帶有來源／ID 的需求、涵蓋範圍圖、假設、推遲的範圍。
2. **決策與結構：** 元件、領域方法／技能、輸出合約、現有平台能力／新增項目；圖表、替代方案、選型原因。
3. **端對端工作：** 填入資料的正常／重大失敗案例、資料／狀態／授權、人工路徑、控制／通知範例。
4. **控制與驗證：** 適用預算與設定後果、失敗／復原、驗收條件／佐證；需求 → 決策 → 檢查。
5. **交接：** 獨立的核准／就緒狀態、阻礙／負責人、第一範圍實作／驗證順序。此計畫不授權撰寫程式碼。

針對稽核，維持相同的可讀性原則：依據／範圍 → 實際系統 → 發現／因果鏈條 → 修正／驗證計畫 → 結論限制。包含已檢查路徑的涵蓋範圍；區分已執行的檢查與未來的檢查。切勿以新設計取代稽核報告。

小型案例可合併章節；切勿建立空白章節。大型案例可使用詳細合約附錄。單一套件應能讓負責人評估決策，並讓開發者理解方法而無需憑空捏造缺失的核心工作。實體名稱、需求 ID 與狀態必須在摘要、表格與圖表之間保持一致。封存檔、安裝程式、平台設定檔與數十個範本檔案並非強制的架構交付物。

## 圖表選型

實質性地納入適用的新合約：價值及其驗證、人工決策、驗證迴圈／Evidence Bundle、檢查點／交接、複合版本與停用。設計中：決策／未來檢查；診斷中：實際佐證、未知項、關聯關閉檢查。不需要為每個名稱都建立獨立章節；切勿新增空白的不適用章節。文件與清單必須指向相同的當前成果版本。

- 針對小型代理人、工作流程、狀態與事件順序，使用 Mermaid 流程圖、狀態圖或循序圖。
- 針對系統邊界、外部參與者、應用程式／儲存庫與職責，在合適層級使用 C4：Context 或 Container；僅在有助於決策時使用 Component。C4 是檢視表模型；Mermaid 可作為其標記法。切勿僅為了湊齊完整集合而新增 C4 層級。
- 在診斷中，實際失敗順序通常比理想系統圖更有用。若展示修正，請使用標籤／標記法區分「現狀」與「提議」，而非單靠顏色。切勿將無法存取的內部細節繪製為已確立的事實。若無追蹤記錄，視覺化已知部分並標記未知區段或展示假設。

針對驗證迴圈，顯示相對於外部副作用的配置；針對延續性，顯示檢查點、交接與下一個允許的步驟；針對重大競爭／歸檔，顯示佇列、監督者以及帶有復原目標的狀態載入；針對停用，顯示觸發來源與進行中操作的命運。顯示適用的儲存庫、預算與非同步審查決策。選擇一個最有用的檢視表，或在需要時選擇數個，而非一套完整的正式圖表集。

圖表代表正在考量的特定代理人／失敗，而非此技能的一般工作流程。使用一致的元件、動作與狀態名稱。在 PDF 中插入帶有可讀標籤的**轉譯後**圖表；以 Mermaid 程式碼區塊取代影像並未完成視覺化。在旁邊保留 `.mmd` 原始碼或其他使用的 C4 格式以供編輯。

## 建立與驗證

1. 完成實質內容並選擇允許的輸出目錄：約定的任務目錄或環境的一般產物位置。切勿將使用者報告儲存在已安裝的技能內部，或覆寫無關檔案。本機匯出是完成的一部分；外部上傳／發布需要其專屬授權。
2. 從單一當前實質成果準備可編輯文字（通常為 Markdown）、圖表原始碼、SVG/PNG 與 PDF。待決問題不會阻礙匯出：識別影響／就緒度。切勿為了另一場訪談或追求完美格式而延遲報告。
3. 若有 PDF 技能可用，閱讀／使用它；否則使用現有的本機 PDF 產生器與圖表轉譯器。匯出輔助指令碼是允許的，且不屬於被審查代理人的實作。切勿將流程繫結至單一提供者、作業系統或特定主機路徑；未經許可切勿將資料傳送至公開轉譯器。
4. 產生後，開啟 PDF，檢查文字、頁數、實質結論以及圖表／文件的一致性。轉譯頁面並以視覺方式檢查西里爾文字、表格、標籤、換行、裁剪與圖表可讀性。修復發現的缺陷。成功的產生命令不能取代成果驗證。
5. 最終回答以主要結論／工作狀態開頭，然後依環境規則提供對 PDF、可編輯文字與圖表／原始碼的存取。僅回報實際執行的檢查。當工具可用時，切勿以「我可以準備 PDF」作為結尾。

若無法建立或轉譯 PDF，交付已完成的實質內容、可編輯文字與圖表原始碼；指明確切缺失的機制以及何者仍未建立／未驗證。切勿將 Markdown 稱為 PDF、宣稱套件已完全就緒，或重啟需求收集。此後備方案保留了成果，但不能算作成功匯出。
