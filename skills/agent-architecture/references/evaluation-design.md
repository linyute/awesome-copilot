# 評估與改進設計 (Evaluation and Improvement Design)

在定義驗收標準、檢查品質主張與診斷測量時閱讀。請依任務規模調整評估集；表格並不要求具備 LLM 評審、獨立服務或新的客戶提問。

## 1. 評估合約

針對每個重大條件，指定 `R/E-ID → 評估屬性 → 輸入／狀態 → 正確答案來源 (oracle) → 檢查器／評分器 → 閾值與狀態 → 強制閘門或診斷指標 → 失敗／缺少評估時的行為`。

| 軸向 | 檢查內容 |
|---|---|
| 任務結果 | 領域正確性、完整性、依據；實際外部系統狀態，以及若發生動作時是否無非預期變更 |
| 強制動作限制 | 權限、資料範圍、允許的參數，以及合約要求的順序 |
| 人機互動 | 清晰的輸出與限制、誠實回報遺漏的資料、正確的等候／取消、手動重做量 |
| 資源 | 每個已接受任務的成本、時間、每次重試／工作者，以及使用者勞力 |
| 佐證涵蓋範圍 | 實際評估的案例、路徑與條件；仍未知的內容 |

切勿以較高的平均分數來抵消對強制安全邊界的違規。定義最終准入：哪些閘門必須通過，哪些指標用於指導取捨。若能達成所需成果並遵守強制限制，正確的替代工具序列是可接受的。單純參考軌跡並不能強制規定順序。獨立分數的存在並不能證明其已納入最終閘門。

範例：一份報告正確計算了指標，但讀取了另一個租戶的資料。領域評估可能通過，但存取閘門失敗，因此禁止最終准入。另一份報告誠實說明資料缺失：這不是計算上的成功，但在約定的評分準則下可能是正確的任務成果。

## 2. 測量可靠性

將代理人錯誤、環境／執行器錯誤、評估器錯誤與缺失評估分開。針對每個軸向，顯示規劃的任務／嘗試、實際執行的任務、已評估的任務、錯誤，以及附帶原因的遺漏；切勿將「任務」、「嘗試」與「條件」混淆。各類別可能在不同軸向間重疊，因此請說明會計規則。缺失評估並非成功；已接受的故障關閉（fail-closed）閘門可能會阻擋准入，而無需將失敗歸咎於代理人。

範例：在執行的 100 個任務中，評審評估了 60 個，接受了 57 個，並對 40 個給出無法剖析的回應。已確認：**在已評估任務中為 57/60 = 95%，涵蓋率 60%，40 個未知**。切勿宣稱整體有 95% 的成功率；所有任務中已確認的接受率為 57%。下一步，定位遺漏並檢查是否存在對困難案例的偏誤。切勿自動將其計為成功，或透過將其從分母中排除來隱藏它們。

固定資料集、評分器／量表、模型、提示／技能、工具、環境與實質資料的版本。檢查任務可行性、模稜兩可／不正確的參照，以及評估器在已知良好／不良案例上的校準情況。在基準測試或評分器變更後，先前的數字需要進行可比較性檢查、共享子集或新基準。僅保留基準測試名稱是不夠的。

針對重試，明確描述嘗試次數、限制、聚合方式與不確定性。`pass@k` 詢問 k 次嘗試中是否至少有一次成功；`pass^k` 詢問是否在所有 k 次嘗試中皆保持一致成功。依產品需求進行選擇：一次成功的嘗試並不能證明每次執行皆可靠。在沒有合理的獨立性依據下，切勿僅透過將估計值進行指數運算來計算全部成功的機率；保留個別嘗試的結果。不存在通用的最小評估集規模。

依據 [diagnostic-review.md](diagnostic-review.md) 測試真實閘門的敏感度、繞過情況與負向控制。評審、剖析器與歸納器皆屬於測量系統，也可能發生失敗。模型自我回報的信心度不是 oracle。

## 3. 來自回饋的受控改進

檢查執行、發行與佐證組合包（Evidence Bundle）迴圈位於 [validation-loop.md](validation-loop.md)。遙測技術會轉化為診斷輸入與新測試案例；單純訊號不能授權行為變更。

針對重大變更，製作簡短卡片：

`案例 → 首個可觀察的義務違規 → 疑似機制 → 目標元件 (方法／情境／工具／執行階段／模型／評分器) → 受保護的不變量 → 變更 → 比較預算 → 獨立驗證 → 接受／復原條件與負責人`。

使用診斷來區分原因、傳播以及遺漏錯誤的檢查。修正成功回報可限制危害，同時保留未解決的原因。在相同條件下比較原始版本與新版本；保留成功的回歸案例以及調校之外的保留集（holdout）。限制反覆運算、花費與停止條件；切勿無止境地最佳化分數。

最佳化後的代理人不得為了提高結果而變更自身的准入條件或私有評估集。修正有缺陷的評分器是允許的，但應作為具有新比較基礎的個別受控測量變更。切勿在保留集上進行調校；資料外洩需要進行新的獨立驗證。

依負責人權限與已接受政策准入新提示／工具／技能或記憶體版本。當條件通過時，在預先授權範圍內進行自動接受是可能的；未授權從改進迴圈任意發布。將提議的實驗、執行的執行與測量的效果分開。以接受的變更與佐證結尾，或以比較結果與特定剩餘限制結尾。

## 4. 呈報與使用者勞力

使用 [design.md](design.md) 的決策圖。包含需要人工決策的案例，以及情境／權限已允許繼續執行的案例。分別計算必要執行與錯失的呈報、不必要的請求，以及缺乏充分材料的請求。分母來自相關類別的標記案例；單一整體呈報率無法展現品質。

測量積極參與、等候、手動重做、佇列大小／年齡以及已完成的有用任務。區分代理人工作、人員可用性與流量排程。在未審查積壓工作持續增加的情況下加速產生，並不是整體流程的改進。減少確認不能成為繞過強制權限的合理解釋。

成對範例：在授權範圍內從可存取來源起草草稿時，無需對每次讀取重複要求權限即可完成；發布則需要確切預覽與有效核准。「足夠的問題」結束了訪談，而非授權發布。決策到達後，代理人繼續執行獲授權的工作，而非停留在「訪談完成」。

## 5. 長時間跨度與延續性

針對長時間工作，比較在全新工作階段中、在累積相關／干擾性歷程記錄之後、在壓縮之後、在交接之後以及當機／恢復執行後的等效任務。改變條件以區分這些轉換；保留任務版本、資料、設定、評估器與總預算。歷程記錄長度與任務持續時間是不同的因素。延長自主時間本身並非目標。

測量領域成果、目標／限制／來源的保留、程序版本、副作用狀態與當前權限、遺失進度、重做、時間與成本。針對檢查點，使用 [execution-continuity.md](execution-continuity.md)。通過測試的最小化簡短範例可能會移除失敗條件；它並不能駁回長時間執行的失敗。全新工作階段後的改善定位了條件，但尚未確立機制。

為每種模式展示個別的成果與涵蓋範圍。分別標註測試設計、測試資料（fixture）上的執行，以及實際執行階段上的確認。風險與預算決定樣本大小與可接受的劣化程度，而非固定的教科書百分比。
