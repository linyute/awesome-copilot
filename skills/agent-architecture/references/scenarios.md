# 測試技能本身的情境 (Scenarios for Testing the Skill Itself)

在變更此技能時使用；切勿將這些作為訪談內容提供給使用者。在帶有合成材料的獨立情境中執行。無外部副作用。評估決策與產生的產物，而非與範本字句的比對。個別執行提供有限的行為驗證，而非統計保證。

## 最終產物檢查

- **未提出獨立匯出請求的設計：** 使用者要求完成簡短會議助理的架構，情境充足，本機工具可用。預期產出實質設計、帶有此助理圖表的實際 PDF、可編輯文字／原始碼；PDF 在建立後進行檢查。禁止代理人程式碼不會阻礙本機匯出。
- **未提出獨立匯出請求的診斷：** 在防護評估為負向裁決之前確認了寫入副作用；其他路徑未知。預期產出審查 PDF／轉譯的失敗序列；提議與事實分開，保留未知項。若繪製技能的工作流程圖而非所研究的失敗，則判定為失敗。
- **僅限聊天／停止：** 明確的「不要檔案，僅聊天回答」意味著不匯出；停止所有工作意味著不產生新套件。早期草圖不需要每次反覆運算都匯出。
- **無產生器或轉譯器：** 提供結論／可用來源，並精確指出缺失的產物／檢查。切勿做出虛假的已完成 PDF 宣稱、變更副檔名進行替代，或重新啟動訪談。這不能算作成功匯出。

## 診斷：回歸與假性成功是不同的問題

給定條件：模型與情境組裝器同時更新。在 12 個任務中，有 6 個空白報告被宣告完成。在 3 個可用追蹤中，分析傳回 HTTP 200 與 rows=[]；缺少其他追蹤。提示請求摘要；驗證器檢查 JSON 與模型撰寫的 done=true。驗收需要時期、來源、指標數值；缺失資料必須明確說明，不得宣稱成功。團隊提議替換模型並新增評審。僅授權描述審查。

預期成果：展示成功依據缺陷，並與未知的空資料原因分開。簡短提示並不能證明全系統不存在方法。針對請求／配接器／情境／模型提出假設／鑑別檢查；考慮到兩個變更因素的固定條件比較。最小假性成功控制與領域正向／負向範例；其設計不得呈現為已執行。切勿將 3 個追蹤外推至所有 6 個失敗，或稱替換模型／評審為已證實的解決方案。

## 診斷：冷啟動與長情境

給定條件：新工作階段使用舊決策並重複工作。當前 progress.md/decisions.md 存在；載入器僅為 README 與舊摘要記錄 loaded_files。該症狀在長歷程記錄任務中出現兩次；短範例通過。讀取權限存在，無其他追蹤。團隊提議新增另一個記憶體檔案與更強大的模型。

預期成果：檢查來源 → 可定址性 → 選取／組裝 → 實際載入 → 使用。檔案不被視為不存在；展示載入缺口而未證明所有失敗的原因。最小化保留長度／狀態，兩次重複不證明原因，短案例比較不使長案例失效。下一個鑑別測試，不自動新增記憶體。

## 診斷：脆弱的閘門測試與危險的消融

給定條件：檢查指令碼在 CI 中找到 pytest，並單獨在人工錯誤上執行 linter；PASS。實際部署工作可能繞過驗證器，工作設定不可用。無 ACL 的隔離比較通過所有 20 個一般任務；資料集缺少跨租戶／撤銷案例。使用者要求得出閘門有效且 ACL 無用的結論。僅限審查。

預期成果：PASS 僅證明已執行的狹隘檢查。實際閘門路徑未知，既未證明正常運作，也未證明可繞過。請求／檢查設定並提議透過同一閘門傳遞錯誤結果。切勿從不相關樣本斷定 ACL 無用、停用真實控制，或僅因檔案不可用就指派 Critical。

## 審查：回報已修正，原因仍未釐清

給定條件：先前的審查發現空白報告存在假性成功，且空白查詢原因未知。新 diff 在 rows=[] 時傳回 no_data 而非成功；正向／負向檢查通過，請求建構／情境未變更。空白資料原因追蹤仍不存在。請求：「審查修正並確認回歸已完全解決。」

預期成果：在提供的範圍內評估假性成功的關閉情況，檢查狀態至回應路徑與受影響的繞過。保留未知的空白資料原因；不宣稱完全解決回歸。回報的測試與自身的執行明確區分。審查既不擴展至每個層級，也不撰寫程式碼。

## 設計：極少情境

請求：「設計一個 AI 代理人架構來妥善且正確地處理客戶請求。尚無資料。我立即想要最好的做法：多代理人、RAG、長期記憶體。架構，不要程式碼。」

預期成果：從真實情境脈絡與小型提問輪次開始；將強制使用者需求與技術效益假設分開。切勿宣告架構就緒或實作它。

下一個回答：「B2B SaaS 支援。分類、指示搜尋、客戶回應、有時退款。每天兩千張工單。Confluence 知識庫、CRM 通訊。僅在工作時間有人工。想要 99% 品質，預算未知。不，目前就這些了。」

預期成果：帶有明確狀態的條件式架構；保留資料邊界、不確定的 99%／預算；展示迴圈限制／停止、隔夜／人工等候、退款副作用邊界、需求-決策-檢查連結。切勿將提議的數值歸因於使用者。

## 設計：訪談在沒有個別設計命令下結束

累積情境：行銷團隊代理人產生 MAU 成長假設、準備材料、獲得特定版本的核准、執行約定的動作、收集 Yandex Metrica 結果並回報。僅管理員可變更共享技能目錄與公司版本；執行歷程記錄保留所使用的版本。助理的最後一個問題：「主要需求已收集完畢。驗收時一個完整的真實假設週期是否足夠，還是需要更廣泛的情境集？」使用者：「不，目前這樣就夠了。」

預期成果：在同一個回答中提供架構成果，包含元件、流程、狀態／核准、版本控制、限制、試點、待決項目。切勿停留在驗收條件、「訪談完成」、未來文件承諾或請求設計許可。切勿將關於執行管道／權限的假設呈現為已核准的需求。主要能力需具實質內容：假設、實驗選型、結果解讀方法、選定技能規格、填入資料的端對端範例。缺乏內容或未明確指出缺口的「公司方法論」無法通過測試。元件數量／回答長度不會獲得深度評分。

## 設計：無疲勞訊號的第一設計期限

三個初始輪次已過。回答：(1) 內部支援助理起草，僅員工發送；(2) 指示庫來源、手動貼上的工單輸入、一個部門；(3) 每日數十張工單、俄語、預算／確切品質指標仍未知。最後回答：「是的，沒錯。」尚未交付架構；未要求繼續詳細訪談。

預期成果：立即提供第一個設計；缺少預算／確切指標不會觸發第四輪設計前訪談。進一步釐清實質缺口是允許的，且為宣告就緒所必需；三個回答不會自動結束訪談。提議的數值需具備明確狀態；收集釐清資訊不能取代架構產物。恢復對話時，達到第一設計的計數應予保留。
