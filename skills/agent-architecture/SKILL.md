# AI 代理人架構 (AI Agent Architecture)

協助使用者取得符合其任務且具合理解釋的架構，或對現有代理人進行基於佐證的稽核。交付架構決策及其驗證方式，而不實作代理人。預設情況下，已完成的工作包含一份 PDF 報告以及成果的視覺化呈現。「理想架構」應符合需求、失敗成本與團隊資源；它不會追求最大化元件數量。

## 選擇路徑

| 請求 | 路徑 | 研讀內容 |
|---|---|---|
| 新代理人，需求尚不明確 | 設計：運作案例 → 早期設計 → 需求與決策涵蓋範圍 → 交付 | [design.md](references/design.md), [architecture-contract.md](references/architecture-contract.md) |
| 根據現有規格制定架構 | 設計：填入已知內容並僅釐清缺口 | 相同檔案；切勿重啟訪談 |
| 審查已撰寫的代理人 | 稽核：重建實際路徑 → 驗證 → 交付發現 | [audit.md](references/audit.md)，並以 [architecture-contract.md](references/architecture-contract.md) 作為標準 |
| 代理人出錯、效能劣化或虛報「完成」 | 稽核內的診斷：案例 → 假設 → 鑑別檢查 → 修正與關閉條件 | audit.md 與 [diagnostic-review.md](references/diagnostic-review.md) |
| 審查並重新設計 | 先稽核；其證實的問題將成為設計輸入 | 先閱讀 audit.md，再閱讀 design.md |

在任一模式下，研讀 [source-map.md](references/source-map.md) 一次：它解釋了原則的起源與教科書的限制。一般技能使用不需要原始 PDF。[scenarios.md](references/scenarios.md) 僅用於測試技能本身。

在選擇或重新檢視執行做法時，使用 [architecture-selection.md](references/architecture-selection.md)；在設計驗收或審查品質主張時，使用 [evaluation-design.md](references/evaluation-design.md)。使用 [validation-loop.md](references/validation-loop.md) 制定驗證迴圈與完成佐證；針對長時間執行／背景工作、暫停、復原與競爭的工作階段，使用 [execution-continuity.md](references/execution-continuity.md)，包含儲存庫、RTO/RPO、預算、人工決策佇列與排程。僅在任務具備相應屬性時，才制定委派、可變記憶體、執行隔離以及長時間／串流互動。某個章節的存在並不會使其問題成為強制性：discovery-protocol.md 下的實質缺口決定深度。

## 共享決策規則

- 首先閱讀可用的規格、本機指示、架構決策與相關材料。使用程式碼重建架構，而非主動進行未經請求的修復。切勿為了稽核而執行帶有外部副作用的應用程式。
- 維護一份簡要登錄表：**來源已證實／使用者需求／提議／假設／待決問題／不適用**。識別需求來自何處。使用者決策與架構師的假設具有不同的狀態。
- 企業合約與已接受決策僅在其專案內部適用。教科書是工程參考，而非權威來源或本機規範的替代品。識別衝突而非無聲地解決它們。
- 首先考慮無 LLM 的一般自動化、單次呼叫與預定義工作流程。僅在有具體需求時才引入代理人迴圈、RAG、持久化記憶體、MCP 或多代理人。針對每項增加的複雜度，識別其效益、成本、驗證方法與更簡單的替代方案。
- 在理解任務之前切勿選取模型或架構。針對具體選型，檢查最新官方文件與版本限制。具備記錄的能力尚不能證明在使用者資料上的品質。
- 將機率性模型決策與程式化強制執行的規則分開。描述在外部副作用**之前**於何處檢查權限、參數、預算與動作准入，包含繞過路徑與恢復執行。
- 針對逾時的外部寫入，讀回未找到任何內容本身並不能證明未產生副作用。僅在建立下游等冪性合約或具備未執行的權威證明下才允許重試；否則保留 `effect unknown` 並進行對帳或呈報。在具體流程與範例以及風險小節中皆套用此規則。
- 稽核或設計不授權撰寫程式碼、變更代理人設定、發布或發起外部動作。在後續明確的實作請求中，將架構移交給適當的流程；此技能本身不延續至實作階段。

## 如何運作

在訪談或稽核規劃之前，閱讀 [discovery-protocol.md](references/discovery-protocol.md)。展示清晰路徑並維護涵蓋範圍圖。預設情況下，每輪對話專注於單一決策或運作情節；切勿在單一問題中隱藏數個獨立主題。實質缺口與佐證決定深度。不存在固定的總輪次限制。

在情境充足時立即交付第一個有用設計，否則最遲不超過第三個回答；計數在繼續對話時不重設。這限制了等待早期結果的時間，而非訪談的完整性。若任務過於模糊，展示已理解內容的地圖與條件式選項。在草圖之後，依通訊協定繼續調查實質缺口；單憑兩三輪提問不足以宣稱就緒。

第一個設計包含目標與邊界、主要能力及其輸出、建議元件、主要流程與外部動作、關鍵限制、假設以及待決決策。這是供早期回饋使用的草圖。訪談預算限制了等待草圖的時間，而非設計深度：根據已知內容將其制定為架構套件，而無需等待個別指示進行詳細說明。若情境充足，立即交付套件。若使用者明確要求僅提供草圖，請尊重並標註該深度。

諸如「這就足夠了」、「目前先這樣」、「其餘稍後」或「問題夠了」等語句代表需求收集結束：在同一個回答中從累積的情境交付架構。切勿要求個別的「現在設計它」指示，亦不得停留在「訪談完成」。若已交付設計，請展示其當前最終版本或實質更新。明確要求停止所有工作（「不要繼續」、「今天就到此為止，停止」）意味著停止，而非交付新設計。

若使用者不知道答案，提出合理解釋的選項並標註其狀態。將未知項表示為假設與待決決策。不明確的權限會在提議架構中阻礙對應的外部動作，但不會阻礙架構本身的交付。沉默與結束訪談並不代表核准提議。

在獲得重要回答後，更新需求與決策的運作摘要。若請求包含建立產物，將其儲存在約定的文件中；否則在對話中予以維護。在繼續執行時，從該摘要與變更資訊開始。

在第一個設計之後，釐清具體分支與未涵蓋的實質需求，包含真實例外、人工工作與可行性。解釋該回答將改變哪項決策；自行提出內部機制。切勿將缺口發掘侷限於已繪製的元件，或重啟問卷調查。當宣告範圍具備充分涵蓋時即完成；若無法取得進一步確認，交付帶有缺口負責人與檢查的條件式套件。

依據 architecture-contract.md 交付架構套件以完成設計：領域能力與方法、輸出合約、指示／技能／材料結構、現有平台與新增項目之間的配置、填入資料的端對端範例以及檢查。這部分請研讀 [capability-design.md](references/capability-design.md)；在稽核中，使用它來檢查必要能力。足夠深入地描述代理人的主要工作，使開發者無需重新捏造其方法。平台名稱與階段清單無法達成此目的。

務必涵蓋**反覆運算、時間、token／費用與工具呼叫的限制、停止規則，以及使用者在停止時獲得的內容**。將未知數值標記為待決或提議，而非虛構已達成共識的限制。帶有技能規格的架構套件仍屬設計：它不隱含技能安裝、程式碼實作或對執行中代理人的驗證。

完成稽核並附帶已證實的問題，分開識別未知項與已接受的取捨。切勿從閱讀程式碼宣稱正式環境就緒度。實作的架構就緒度與展現出的維運品質是不同的成果。

## 最終產物

在完成設計、稽核或診斷時，閱讀 [result-delivery.md](references/result-delivery.md) 並建立包含轉譯 Mermaid 或 C4 圖表的成果 PDF；保留可編輯文字與圖表原始碼。將此作為完成的一部分進行，無需使用者另外提出「現在製作 PDF」的請求。早期草圖與中間回答不需要重複匯出。明確的使用者限制（「僅聊天」、「不要檔案／PDF」）以及停止所有工作的請求具優先權。建立報告不授權實作或變更被審查的代理人。
