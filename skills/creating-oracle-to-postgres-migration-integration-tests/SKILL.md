# 建立 Oracle 至 PostgreSQL 移轉的整合測試

為單一目標專案中的資料存取產物產生整合測試案例。測試以 Oracle 為目標，並擷取其行為作為權威基準。它們的撰寫方式具備邏輯可攜性 — 因此可以在階段 6 移轉中留存而無需重寫 — 但在此階段不會針對 PostgreSQL 執行。

## 先決條件

- 測試專案必須已存在且能編譯（分開建構框架）。
- 撰寫測試前請先閱讀現有的基底測試類別和種子資料管理器慣例。

## 工作流程

```
測試建立：
- [ ] 步驟 1：探索測試專案慣例
- [ ] 步驟 2：識別可測試的資料存取產物
- [ ] 步驟 3：建立種子資料
- [ ] 步驟 4：撰寫測試案例
- [ ] 步驟 5：審查決定性 (Determinism)
```

**步驟 1：探索測試專案慣例**

閱讀基底測試類別、種子資料管理器和專案檔案，以瞭解繼承模式、交易管理和種子檔案慣例。

**步驟 2：識別可測試的資料存取產物**

僅限於目標專案範圍。列出與資料庫互動的資料存取方法 — 存放庫 (repositories)、DAO、預存程序呼叫端、查詢建構器。

**步驟 3：建立種子資料**

- 遵循現有專案的種子檔案位置和命名慣例。
- 避免使用 `TRUNCATE TABLE` — 保持現有資料庫資料完整。
- 假設現有的商務資料列和查詢對照 (lookup) 資料列已存在；僅新增該情境所需、最小且能避免衝突的種子記錄。
- 不要認可 (commit) 種子資料；測試在會回復 (rollback) 的交易中執行。
- 確保種子資料不與其他測試發生衝突。
- 在斷言 (assertions) 依賴種子資料之前先載入並驗證該資料。
- 建立或重複使用測試 `LookupConstants` 類別，以取得跨種子建構器和斷言使用的穩定查詢對照 ID/代碼。

**步驟 4：撰寫測試案例**

- 繼承自基底測試類別以取得自動交易建立/回復功能。
- 確保範圍內每個涉及資料庫的方法至少有一個整合測試（或針對高風險行為分支有多個測試）。
- 斷言邏輯輸出（資料列、資料欄、計數、錯誤類型），而非平台專屬訊息。
- 斷言特定預期值 — 當可從種子資料取得具體值時，絕不斷言值僅為非 Null 或非空。
- 避免測試不存在的程式碼路徑或斷言不可能發生的行為。
- 避免針對相同方法的測試之間存在多餘的斷言。
- 對於文字參數，在適用的情況下納入空字串和 `NULL`/遺漏輸入的涵蓋範圍。
- 對於日期時間行為，納入驗證寫入和讀回值相符的斷言 — 使用 Oracle 資料欄的精確度（例如，對於沒有小數秒數的日期/時間資料欄僅使用秒），而不是假設任何特定的資料庫類型語法。

**步驟 5：審查決定性**

重新檢查針對非 Null 值的每個斷言。確認每個斷言針對植入的資料都具備決定性。修正任何依賴於測試控制之外的資料庫狀態的斷言。

## 主要限制

- **僅限階段 3** — 這些測試以 Oracle 為目標。請勿在階段 6 期間或針對以 PostgreSQL 為目標的專案叫用此 skill。
- **Oracle 是黃金來源 (Golden Source)** — 測試擷取 Oracle 的預期行為。
- **斷言可攜性** — 避免在斷言中使用平台專屬的錯誤訊息或語法，以便在階段 6 將測試專案移轉到 PostgreSQL 時，斷言無需進行任何變更。
- **僅針對 Oracle 植入種子** — 測試專案將在階段 6 移轉到 PostgreSQL；在此之前種子資料和基礎架構仍以 Oracle 為目標。
- **範圍限於單一專案** — 不要為目標專案以外的產物建立測試。
- **保留現有資料** — 絕不重寫或清除既有的商務或查詢對照資料列。
