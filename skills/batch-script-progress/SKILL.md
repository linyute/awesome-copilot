# 批次指令碼進度 (Batch Script Progress)

讓產生的批次指令碼在執行時具備可觀察性，同時不改變其處理合約。將啟動、定期進度、個別項目失敗和最終摘要輸出，與結果串流和結束狀態一起設計。單靠進度列函式庫無法建立此合約。

## 1. 確認既有合約

在編輯之前，請先閱讀指令碼、呼叫端和相關的測試。識別：

- 輸入單位、已知或未知的總數，以及列舉是否為延遲求值。
- 現有的 stdout 格式與取用者、執行階段版本，以及互動式與重新導向執行的差異。
- 遇錯繼續 (continue-on-error) 或快速失敗 (fail-fast) 策略、重試規則、略過規則、交易界限和取消行為。
- 現有的結束代碼，以及呼叫端視為成功條件的定義。

保留這些決策。請勿僅僅為了加入進度輸出而新增重試、平行處理、相依性或新的失敗策略。若部分失敗目前回傳零，請誠實回報部分結果，同時維持該結束合約。若合約缺失或互相矛盾，請詢問會改變行為的決策；切勿擅自做決定。

## 2. 在實作前定義輸出合約

選擇精簡、穩定的詞彙和欄位，在合適的情況下重複使用存放庫的記錄器 (logger)：

- **啟動 (Start)：** 操作名稱、總數或明確標註未知，以及初始計數器。在耗時的列舉之前發出；探索階段本身可能就需要進度。
- **進度 (Progress)：** 已處理、成功、失敗、略過、總數或未知，以及經過時間。僅在有用時才新增清理後的目前項目識別碼。
- **項目失敗 (Item failure)：** 安全的識別碼、失敗類別或清理後的原因，以及處理是否會繼續。在觀察到時立即發出，不受正常進度間隔影響。
- **摘要 (Summary)：** 已完成、部分完成、失敗或已取消；最終計數器；經過時間；可用的已知未處理計數；以及現有合約所需的結束狀態。

將已達到終止結果的項目定義為 `processed = succeeded + failed + skipped`。將進行中與未開始的項目分開。每個項目只計算一次；重試嘗試不是額外處理的項目。在項目完成所需的認可 (commit)、寫入或認可確認 (acknowledgement) 之前，請勿將其標記為成功。若交易已復原 (rollback)，請回報已復原的工作，而非宣稱持久成功。

對於未知總數，請回報計數，不要捏造百分比、預估剩餘時間 (ETA) 或剩餘計數。不要僅為了計數而將串流具體化 (materialize)。對於零個項目，發出計數為零的啟動與摘要；切勿除以零。

## 3. 選擇輸出串流與發送頻率

將 stdout 保留給已確立的機器可讀結果、管線物件或通訊協定。將進度與診斷放在獨立的通道上；stderr 是獨立 CLI 指令碼的可攜預設值。僅有 stderr 輸出並不代表失敗：呼叫端必須使用約定的結束代碼與結果合約。在更改其輸出之前，請先驗證是否包含將任何 stderr 視為失敗的呼叫端。若 stdout 已被保留且 stderr 不相容，僅在呼叫端已支援時使用現有相容的記錄器或接收器 (sink)。請勿將進度移至語意變更的 stdout 或其他串流。若不存在相容的通道，請停止並詢問是否允許變更輸出合約，或回報無法安全地加入進度。

使用有界限的發送頻率，例如每達到設定的項目數**或**經過的時間間隔，而非無條件地記錄每個項目。無論該頻率為何，都必須發出啟動、失敗與摘要。另外分開保留所需的個別項目稽核記錄。避免不受限的記憶體內失敗清單與重複的堆疊追蹤。在格式化之前遮罩認證、查詢參數、個人資料與機敏路徑；預設情況下不要傾印原始例外狀況或完整的輸入記錄。

將單調時間 (monotonic time) 用於間隔與持續時間。確保輸出已排清 (flush) 或清空 (drain)，以便在結束前送達通知。在重新導向時使用以換行分隔的一般記錄；僅在適當的 TTY 下啟用終端機重寫或顏色。在不同語言之間保持記錄欄位語意的一致性，但不一定要求其格式或函式庫完全相同。

**迴圈結尾的時間檢查無法在單一項目封鎖時發出輸出。** 對於耗時的項目，請使用現有的進度回呼、階段通知，或在執行階段允許的情況下使用安全整合的活動訊號 (heartbeat)。Node.js 計時器無法在同步事件迴圈封鎖期間執行；PowerShell 進度顯示並非持久性記錄。若無法在不變更執行語意的情況下新增項目中途進度，請在該階段開始前發出目前階段，並揭露通知的間隔缺口。切勿承諾實作無法提供的定期活動訊號。

## 4. 實作最小的相容變更

請閱讀所選執行階段的[語言注意事項與安全範例](references/language-notes.md)。這些範例是可執行的輸出合約探針 (probe)，而非正式環境處理常式；請將其發出器 (emitter) 與計數邏輯調整至現有程式碼，而非直接複製其失敗策略。

保持回報與處理決策分開。在並行程式碼中，透過協調器將回報序列化，並計算已完成的結果，而非提交數。在已處理的失敗或取消發生時，嘗試輸出最後一次摘要並保留原始結果；摘要寫入錯誤絕不能取代原始處理例外狀況。不要將取消當作一般項目失敗予以隱蔽 (swallow)。對於主機管理的取消（包括 PowerShell 主機停止），保留現有的主機行為；不要將停止例外狀況轉換為項目失敗，或在主機終止後承諾輸出最終摘要。使用 `finally` 進行適用的清理，但當正常取消為合約的一部分時，請在支援的主機中驗證實際的取消路徑。

請勿為了傳遞緩衝輸出而強制成功終止。在 Node.js 中，偏好設定 `process.exitCode` 並排清寫入，而非立即執行 `process.exit()`。在 PowerShell 中尊重現有的主機/函式庫語意：可重複使用的函式不應結束其呼叫端。強制終止、程序當機與中斷的輸出管道可能會阻止最終回報；切勿宣稱不會發生這種情況。

## 5. 在回報完成前進行驗證

請閱讀[驗證案例](references/verification.md)，然後使用無害的測試載體 (fixtures) 為已變更的指令碼執行聚焦測試。分別擷取 stdout 與 stderr 並檢查真實的結束狀態。驗證啟動/進度順序、單調計數器、清理後的失敗、在支援路徑上恰好有一次摘要，以及未改變的結果內容與處理策略。

透過**在子處理序仍在執行時**讀取其輸出來證明存活性 (liveness)，而非透過檢查結束後收集的輸出。在兩者皆支援時，同時檢查終端機與重新導向行為。進度事件後的受控暫停是有用的決定性探針：接收事件、確認子處理序尚未結束，然後釋放它。將此類閘道保留在無害的測試載體或測試控架中；請勿單純為了讓測試通過而向一般正式環境處理中新增 stdin 等待、休眠或取消勾點 (hooks)。偏好現有的回呼或可插入的處理界限。若不存在安全且決定性的接縫 (seam)，僅使用無害的輸入測試實際路徑，或將存活性回報為未驗證。看門狗 (watchdog) 可以使測試失敗；但絕不能製造成功的結果。

隨附的[跨語言驗證器](tests/verify-examples.mjs)使用正常、部分失敗、保留部分失敗結束代碼零、空白、未知總數、快速失敗、模擬取消與即時輸出案例，執行 [Python](examples/batch.py)、[PowerShell](examples/batch.ps1) 和 [Node.js](examples/batch.mjs) 探針。它僅檢查探針；並不能證明任意產生的指令碼或自動技能選擇能夠正常運作。

從此技能資料夾使用 Node.js 20 或更新版本執行它：

```text
node tests/verify-examples.mjs
```

它還需要 Python 3.9 或更新版本以及 PowerShell 5.1 或更新版本。有關可執行檔覆寫的資訊，請參閱語言注意事項。遺失執行階段是失敗項目，而非無訊息略過的涵蓋範圍。

## 交付成果

傳回已變更的指令碼、其輸出/結束合約，以及聚焦驗證結果。區分已執行的測試與檢查和未執行的案例。不要僅僅因為指令碼印出進度列或技能中繼資料通過驗證，就稱該指令碼已驗證。

## 常見陷阱

- 在記錄前進行計數可能會使探索階段無訊息地耗盡整個串流。
- 使用 PowerShell `Write-Output` 寫入狀態會將字串新增至成功管線。
- 僅在結束後測量緩衝輸出無法證明進度的能見度。
- 顯示 `completed` 的最終訊息會隱藏部分失敗，除非結果與計數器對其進行解釋。
- `finally` 並不是強制終止後仍會回報的保證。
