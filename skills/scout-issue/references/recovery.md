# 復原與備援方案

當管線無法正常繼續時，請使用這些路徑。務必說明限制所在，而非假裝某個工具或資料來源存在。

## 使用者取消

若使用者在任何階段輸入 `/cancel` 或說「cancel」：

1. 立即停止管線。
2. 確認已取消。
3. 返回一般對話模式。

## 使用者重新啟動

若使用者在過程中再次輸入 `/scout-issue`：

1. 從第一階段重新開始。
2. 再次詢問問題。
3. 捨棄先前的任何進度。

## 缺少工具

若 GitHub CLI 無法使用：

```bash
which gh
echo "GitHub CLI not available. Using git log for activity analysis."
git log --oneline -20
```

使用 git 歷史紀錄與網頁搜尋作為備援方案，縮小搜尋範圍，並說明哪些檢查無法完成。當關聯 PR 或維護者活動未經實際驗證時，切勿宣稱已驗證。

## GitHub CLI 未驗證

```bash
gh auth status
```

若未驗證，請說明受限的項目：

- 本機儲存庫檢視仍可運作。
- Issue 文字可能可透過網頁搜尋取得。
- 無法透過 API 驗證關聯的 PR 與維護者活動。

若使用者可以進行驗證，請要求他們執行 `gh auth login` 並繼續。

## 速率限制

```bash
gh api rate_limit
```

若 API 達到速率限制：

- 使用 git 歷史紀錄查看近期活動。
- 減少調查的 issues 數量。
- 優先使用單次批次 REST 分頁，而非多次針對個別 issue 的呼叫。
- 告知使用者缺少哪些證據。

## 找不到 Issues

若找不到合適的 issues：

- 說明哪些限制條件產生了束縛。
- 建議一次放寬一個限制條件。
- 提供替代方案，例如不同的貢獻類型或鄰近的子系統。
- 切勿為了填滿精選清單而降低證據標準。

## 儲存庫資訊有限

當儲存庫無法在本機取得時：

- 使用可用的 issue 文字與 API 資料。
- 註明信心水準限制。
- 建議手動驗證程式碼位置與測試。
- 優先選擇內文中已經指向特定檔案或子系統的 issues。
