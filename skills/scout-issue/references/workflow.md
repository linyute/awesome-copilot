# Issue Scout 工作流程

## 高階流程

```
使用者請求
    ↓
剖析意圖 → 內部規格
    ↓
檢視儲存庫 → 了解背景脈絡
    ↓
探索 Issues → 候選池
    ↓
篩選明顯不適合的候選項目 → 縮減後的候選池
    ↓
調查有潛力的候選項目 → 深度分析
    ↓
評分與排名 → 最終精選清單
    ↓
呈現結果 → 使用者決策
```

## 詳細步驟

### 1. 剖析使用者意圖

**輸入：** 自然語言請求

**流程：**
- 擷取明確限制（語言、時間、類型）
- 推斷隱含限制（經驗、偏好）
- 識別優先順序（最重要的項目）
- 建立內部規格

**輸出：** 結構化的內部規格

**範例：**
```
「幫我找一個我能在這個週末完成的 Rust issue」

→ 目標：週末專案
→ 語言：Rust
→ 範圍：4-8 小時
→ 偏好：清晰的需求、可重現的錯誤
→ 優先順序：範圍契合度 > 技術契合度
```

### 2. 檢視儲存庫

**輸入：** 儲存庫背景脈絡

**流程：**
- 識別主要語言／框架
- 了解專案結構
- 檢視貢獻指引
- 檢查 issue 範本與標籤
- 評估近期活動
- 識別測試基礎架構

**輸出：** 對儲存庫的理解

**關鍵問題：**
- 這是什麼專案？
- 它是如何組織的？
- 貢獻規範為何？
- 使用了什麼測試工具？
- 維護活躍度如何？

### 3. 探索 Issues

**輸入：** 儲存庫與限制條件

**流程：**
- 使用 GitHub CLI/API 列出 issues
- 套用廣泛篩選（開啟中；僅當使用者請求未認領的工作時才加上「未指派」）
- 考量標籤與里程碑
- 從高潛力類別著手

**輸出：** 候選 issue 池

**指令：**
```bash
gh issue list --state open --limit 100
gh issue list --label "bug" --state open
gh issue list --label "help-wanted" --state open
```

### 4. 篩選明顯不適合的候選項目

**輸入：** 候選池

**流程：**
- 移除已關閉／重複的 issues
- 僅當使用者想要未認領的工作時，才剔除已指派的 issues
- 僅當使用者想要未認領的工作時，才排除開啟中的競爭 PR；否則將其記錄為證據
- 篩選掉明確違反限制條件的項目
- 保留不活躍的 issues，除非有證據顯示已過時或使用者設定了近期性限制

**輸出：** 縮減後的候選池

**篩選器：**
- 狀態：開啟中，未關閉
- 指派：僅在要求時篩選未指派
- PR 連結：僅在要求時排除開啟中的競爭 PR；已關閉的 PR 作為證據
- 近期性：不自動排除過時項目；不活躍會降低活躍度證據分數
- 限制條件：符合使用者需求

### 5. 調查有潛力的候選項目

**輸入：** 縮減後的候選池

**流程：**
- 閱讀完整的 issue 描述
- 檢視留言與討論
- 檢查關聯的 PR 與提交
- 定位相關程式碼檔案
- 評估實作複雜度
- 驗證證據品質

**輸出：** 每個候選項目的深度分析

**調查檢查清單：**
- [ ] 已閱讀完整描述
- [ ] 已檢視留言
- [ ] 已檢查關聯的 PR
- [ ] 已識別程式碼位置
- [ ] 已找到測試位置
- [ ] 已評估複雜度
- [ ] 已記錄證據

### 6. 評分與排名

**輸入：** 深度分析

**流程：**
- 套用評分標準
- 依使用者優先順序調整權重
- 計算最終分數
- 依分數排名
- 識別最佳匹配

**輸出：** 附帶分數的排名精選清單

**評分維度：**
- 使用者契合度
- 技術契合度
- 範圍契合度
- 難度契合度
- Issue 品質
- 活躍度
- 貢獻可行性
- 證據品質

### 7. 呈現結果

**輸入：** 排名精選清單

**流程：**
- 格式化簡潔的輸出
- 解釋每個 issue 為何匹配
- 強調顧慮事項
- 提供明確的建議
- 為排名靠前的被拒絕 issues 提供拒絕理由

**輸出：** 供使用者參考的建議

**格式：**
- 附帶分數的前 3-5 個 issues
- 清晰的「最佳匹配」建議
- 每個項目的關鍵證據
- 註明重要顧慮

## 決策點

### 何時縮減候選項目（而非跳過檢查）
- 若使用者提供完整背景脈絡，**縮減候選池**（仍須檢視證據）
- 若候選池較小（<20），**縮減調查的候選項目** —— 對全部項目套用完整檢查
- **將深度調查集中於**快速掃描的前 3-5 名 —— 仍須驗證每個項目的資格

### 何時迭代
- 若使用者澄清限制條件，**重新排定優先順序**
- 若初始候選池不足，**擴大搜尋**
- 若使用者請求特定 issue，**深入調查**

### 何時停止
- 在完整資格檢查後找到**足夠的候選項目**（3-5 個強有力的匹配）
- 達到**時間限制**
- **使用者表示滿意**

## 邊界情況

### 找不到合適的匹配項目
- 解釋為何限制條件過於嚴苛
- 建議放寬限制條件
- 提供替代方案

### 過多合適的匹配項目
- 提高篩選嚴格度
- 優先考量最高分的項目
- 依類別分組

### 模糊的使用者請求
- 詢問澄清問題
- 做出合理假設
- 記錄所做的假設

### 儲存庫資訊有限
- 使用可用的資料進行處理
- 註明信心水準限制
- 建議手動驗證

## Scout 特定決策

在呈現結果前，請執行 `quick-reference.md` 中的調查檢查清單。證據與誠實規則位於 `SKILL.md`；以下決策專屬於偵察（scouting）流程。

### 未認領工作的關聯 PR 證據無法取得
若驗證、速率限制或時間軸 API 導致無法檢查關聯 PR：
- 切勿稱該 issue 為未認領。
- 將競爭工作關卡標記為**未驗證**、降低信心水準，並優先選擇狀態已驗證的候選項目。
- 若沒有剩餘的已驗證候選項目，請呈現最佳的未驗證選項，並附上明確警告以及來自 `quick-reference.md` 的手動關聯 PR 檢查步驟。

### Issue 狀態在執行過程中變更
在呈現結果前立即重新檢查狀態。若某個 issue 已關閉、已被指派或新增了開啟中的關聯 PR：
- 當變更違反硬性限制時，捨棄該項目。
- 否則保留該項目，並將該變更記錄為更新後的證據。

### 限制條件排除了每個候選項目
指出排除最多候選項目的限制條件，並提供一個具體的放寬建議。切勿為了產生匹配而私自捨棄硬性限制。

### 缺少程式碼或測試證據
保留該候選項目，但降低技術契合度與證據品質分數。說明無法驗證的項目並指向手動檢查，而非從標題推斷難度。
