# 反模式 (Anti-Patterns)

| 避免 | 偏好 | 原因 |
|---|---|---|
| 單一代理人擁有規劃、實作、測試與核准 | 保持 Producer、Dev 與可選的 QA 職責分明 | 獨立觀點可減少盲點，且無需為每項變更進行繁瑣儀式。 |
| 硬編碼工具或模型允許清單 | 繼承開發者已啟用的工具與所選模型 | 擴充套件與 MCP 工具在無需更新外掛程式的情況下仍保持可用。 |
| 對每項變更採用強制性流程 | 根據風險調整規劃、審查與 QA 的規模 | 小型變更保持敏捷；高影響力變更接受更多檢驗。 |
| 通用的 Git 指令配方 | 遵循儲存庫貢獻與分支政策 | 專案使用不同的遠端、保護機制與合併策略。 |
| 改寫共用歷史或捨棄未知工作 | 保留工作並協調破壞性操作 | 平行工作階段與貢獻者可能依賴現有狀態。 |
| 重複專案文件的大型計畫 | 僅記錄成果、限制條件、決策與後續操作 | 簡潔的上下文更容易維護與復原。 |
| 僅在聊天中保留錯誤與決策 | 使用儲存庫的議題追蹤器 (issue tracker) 與持久上下文 | 未來的工作階段可以發現它們。 |
| QA 修改應用程式原始碼 | QA 報告行為；Dev 實作修正 | 分工能保持獨立驗證。 |
| 將每個自動化建議視為必要條件 | 評估相關性、信心度、範疇與實際風險 | 審查應改善產品，而非無限制地擴大範疇。 |

## 角色職責 (該做 / 不該做)

- Producer
  - 該做：釐清成果、限制條件、驗收標準以及明確的排除項目；協調審查者與合併政策。
  - 不該做：實作或發佈應由 Dev 審查的程式碼變更。

- Dev
  - 該做：實作最小且完整的解決方案、執行列出的驗證、納入測試，並準備附帶驗證步驟的 PR。
  - 不該做：在缺少必要檢查、測試失敗，或未記錄風險與決策的情況下進行合併。

- QA (可選)
  - 該做：獨立驗證行為、提出可重現的議題，並在 Dev 套用修正後進行確認。
  - 不該做：將修改應用程式原始碼作為驗證失敗的捷徑 — 應提出報告並交還給 Dev。

## 決策記錄指引

- 在 DECISIONS.md 或儲存庫議題追蹤器中記錄重大決策，包含：標題、日期、擁有者、決策摘要 (1 行)、理論依據，以及相關 PR/議題的連結。
- 保持條目簡短且可搜尋；當決策推遲工作時記錄後續操作。
