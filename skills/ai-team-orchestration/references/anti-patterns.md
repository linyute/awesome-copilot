# 反模式 (Anti-Patterns)

| 避免 | 偏好 | 原因 |
|---|---|---|
| 單一 Agent 擁有規劃、實作、測試和核准 | 保持 Producer、Dev 和選用 QA 的職責分明 | 獨立的視角可減少盲點，而無需對每次變更都拘泥於形式。 |
| 硬編碼的工具或模型允許清單 | 繼承開發人員啟用的工具和選取的模型 | 擴充功能和 MCP 工具保持可用，無需更新外掛程式。 |
| 對每次變更都實施強制性流程 | 根據風險調整規劃、審查和 QA 規模 | 小型變更保持快速；高影響力的變更接受更多審查。 |
| 通用 Git 指令配方 | 遵循存放庫貢獻和分支原則 | 專案使用不同的遠端、保護和合併策略。 |
| 重寫共用歷程記錄或捨棄未知工作 | 保留工作並協調破壞性動作 | 平行工作階段和貢獻者可能依賴現有狀態。 |
| 複製專案文件的龐大計畫 | 僅記錄結果、限制、決策和後續動作 | 簡明的情境更容易維護和復原。 |
| 僅在聊天中保留錯誤和決策 | 使用存放庫的議題追蹤器和持久情境 | 未來的工作階段可以發現它們。 |
| QA 修正應用程式原始碼 | QA 回報行為；Dev 實作修正 | 分工可維持獨立驗證。 |
| 將每個自動化建議視為必要條件 | 評估相關性、信心度、範圍和實際風險 | 審查應改善產品，而不是無限制地擴大範圍。 |
