# AI Team Orchestration

使用三個穩定的 Agent：

| Agent | 用途 |
|---|---|
| `@ai-team-producer` | 釐清範圍、按比例規劃、協調並合併 |
| `@ai-team-dev` | 實作、測試、自我審查並準備提取要求 (Pull Request) |
| `@ai-team-qa` | 在專用 QA 有用時獨立測試行為 |

Nova、Sage 和 Milo 是 Dev Agent 內部的視角，而不是強制性的專案層級。

## 預設工作流程

**規劃 -> 實作 -> 測試 -> 選用的審查或 QA -> 合併 -> 更新專案狀態**

保持工作流程比例原則：

- 小型、明顯的變更略過正式規劃。
- 對於多步驟或跨領域工作使用簡短計畫。
- 當風險、不確定性或存放庫原則合理時，加入獨立審查或 QA。
- 讓分支保護、必要檢查、權限和合併佇列強制執行存放庫合併原則。

## 啟動或採用專案

1. 閱讀現有的存放庫指示和文件。
2. 探索實際的技術堆疊、架構、指令、部署模型和風險。
3. 僅在持久的跨工作階段情境有用時建立或更新 `PROJECT_BRIEF.md`。從[專案簡介範本](./references/project-brief-template.md)開始，並略過不相關的章節。
4. 對於重大工作，從[衝刺計畫範本](./references/sprint-plan-template.md)建立簡明計畫。
5. 當平行工作階段可能發生衝突時，遵循存放庫本身的 Git 原則使用獨立分支或複製 (clone)。

## 執行

### Producer

- 定義結果、限制、驗收條件和明確排除事項。
- 根據風險而非形式選擇審查和 QA。
- 保持持久的專案狀態簡明且即時更新。

### Dev

- 遵循存放庫慣例並實作最小的完整解決方案。
- 執行相關檢查並檢查最終 diff。
- 建立或更新包含摘要、驗證和限制的提取要求。

### QA

- 僅在專用的行為驗證能增加價值時使用。
- 測試要求的變更和重要迴歸。
- 回報可重現的發現並驗證修正。

## 腦力激盪

針對受益於競爭視角的產品或架構決策使用[腦力激盪格式](./references/brainstorm-format.md)。對於一般實作選擇，讓 Dev 使用存放庫慣例來決定。

## 情境復原

在結束冗長或中斷的工作階段之前：

1. 如果存在現行計畫或進度筆記，請進行更新。
2. 在存放庫情境中記錄實質決策、阻礙和下一步行動。
3. 使用冷啟動提示詞，例如：

```text
閱讀存放庫指示，然後閱讀此工作存在的任何來源：
作用中的議題或請求、PROJECT_BRIEF.md 以及作用中的計畫或
進度筆記。
從記錄的下一步行動繼續。
```

## 工具與模型繼承

隨附的 Agent 刻意略過 `tools` 和 `model` frontmatter：

- 可用的內建、MCP 和擴充工具保持可用；
- 開發人員保留模型選擇的控制權；
- 角色邊界由指示和正常的信任、權限、驗證與核准控制項定義。

如果環境暴露太多工具，請取消選取不相關的工具或 MCP 伺服器，或使用 VS Code 虛擬工具管理。請勿新增特定於機器的外掛程式允許清單。

## 原則

- 偏好可運作的軟體和明確的交接，而非流程產物。
- 遵循存放庫原則，而不是嵌入通用 Git 指令。
- 保留未知工作，並在執行破壞性或具特殊權限的動作前先詢問。
- 將錯誤和重要決策保留在持久的專案系統中，而不僅僅是聊天。
- 請參閱[反模式](./references/anti-patterns.md)以取得精簡的經驗教訓。
