# 伺服器端轉換追蹤 (Server-Side Conversion Tracking)

由於 iOS 追蹤預防、廣告攔截器、Cookie 生命週期限制與跨網域躍點，瀏覽器像素遺失了大量且無法預測的轉換比例。伺服器端回報修復了*回報*問題，而這正是廣告平台的出價模型所學習的依據。此技能涵蓋該模型、設定順序以及如何進行驗證。

## 何時使用

- 廣告平台回報的購買次數少於商店/資料庫實際記錄的次數
- 在追蹤變更後 CPA 似乎立即惡化，但實際銷售額並無變化
- 設定將接收付費流量的新漏斗
- 被問及 CAPI / Events API / 離線轉換匯入 / 點擊識別碼傳遞
- 平台之間的歸因分歧（「Facebook 聲稱有 40 筆銷售，Google 聲稱有 30 筆，而我們只有 45 筆訂單」）

## 模型（按必須建構的順序）

搞錯此順序通常是「伺服器端設定」仍然回報不足的原因。

```
1. 擷取 (Capture)   在到達網頁上、任何重新導向之前的首次造訪時擷取點擊識別碼 + UTM
2. 保留 (Persist)   在伺服器端將它們附加到訪客的工作階段
3. 攜帶 (Carry)     在每個漏斗步驟中保留它們，包括跨網域躍點
4. 附加 (Attach)    在購買時將它們寫入訂單記錄中
5. 回報 (Report)    將帶有點擊識別碼 + 雜湊 PII 的購買事件進行伺服器對伺服器發送
6. 去重 (Dedupe)    為瀏覽器事件與伺服器事件賦予相同的事件 ID
7. 驗證 (Verify)    將平台回報的轉換次數與您自己的訂單資料表進行比較
```

略過步驟 1-4 僅進行步驟 5 會產生沒有點擊識別碼的伺服器事件，平台隨後必須僅根據雜湊電子郵件進行比對 — 這是顯著較差的比對方式，也是「我們已經在做 CAPI」設定中最常見的失敗。

### 步驟 1-2：擷取與保留

| 平台 | 點擊識別碼參數 |
|---|---|
| Facebook / Instagram | `fbclid` |
| TikTok | `ttclid` |
| Google Ads | `gclid`（在 iOS 應用程式至網頁上亦有 `wbraid` / `gbraid`） |
| Microsoft / Bing | `msclkid` |

在相同的首次造訪時亦擷取：`utm_source`、`utm_medium`、`utm_campaign`、`utm_content`、`utm_term`、完整到達網址、參照來源 (referrer)、使用者代理程式 (user agent)，以及伺服器看到的用戶端 IP。Facebook 的 CAPI 比對品質取決於 `client_ip_address` 和 `client_user_agent`，且它們必須是*訪客的*，而非您伺服器的 — 在 Proxy 或 CDN 背後，請從轉發標頭中讀取它們。

儲存在伺服器端，並以第一方工作階段為索引鍵。不要依賴用戶端 Cookie 留存到結帳：在 iOS 上，指令碼可寫入的儲存空間可能被限制在 7 天或更短時間，而跨網域躍點會完全破壞它。

### 步驟 3：跨步驟攜帶

- 同網域步驟：如果工作階段位於伺服器端，則工作階段 Cookie 就足夠了。
- 跨網域步驟（到達網頁在一個網域，結帳在另一個網域）：識別碼必須在重新導向中明確轉發，然後在接收網域上重新保留。這是大多數漏斗無聲無息遺失歸因的地方。
- 重新導向鏈：每個躍點都必須保留查詢字串。刪除 `?fbclid=...` 的追蹤重新導向會破壞該整個行銷活動的歸因。

### 步驟 4：附加至訂單

訂單記錄必須包含點擊識別碼、UTM 和到達 URL。這使得其餘工作成為可能：它將歸因轉變為資料庫連接 (join) 而非瀏覽器猜測，它可以在重放和回補中存活，並讓您能夠將平台數據與現實進行核對。

### 步驟 5：伺服器對伺服器回報

| 平台 | 端點 / 機制 | 所需認證 |
|---|---|---|
| Facebook | Conversions API | 像素 ID + 存取權杖 |
| TikTok | Events API | 像素代碼 + 存取權杖 |
| Google Ads | 點擊轉換匯入（以 `gclid` 為索引鍵） | 轉換動作 + 開發人員/OAuth 認證 |
| Microsoft Bing | Conversions API | UET 標籤 ID + CAPI 權杖 |

隨事件發送：事件名稱、事件時間、事件 ID（用於去重）、訂單金額 + 貨幣、點擊識別碼，以及使用平台所需正規化（小寫、去除前後空格、SHA-256，電話號碼使用 E.164）雜湊後的客戶識別碼（電子郵件、電話）。搞錯正規化會靜默降低比對率，且不會產生任何錯誤。

從帶有重試機制的佇列發送，而不是在結帳請求中行內發送。付款絕不能因為廣告平台的 API 緩慢而失敗，且遺失的事件必須重試而不是直接遺失。

### 步驟 6：去重

如果您針對同一筆購買同時觸發瀏覽器像素和伺服器事件（推薦這樣做 — 它們能彌補不同的遺失），兩者都必須帶有相同的事件 ID，且 Facebook 在存在時還會對照 `fbp`/`fbc` Cookie 值進行比對。如果沒有共用的事件 ID，您會重複計算，然後透過移除伺服器事件來「修復」它，這完全是本末倒置。

### 步驟 7：驗證

切勿因為程式碼已部署就假設設定有效。檢查：

1. **平台事件偵錯工具** — Facebook 事件管理工具測試事件 / TikTok 事件偵錯：事件是否到達，回報的比對品質為何？
2. **您自己的核對** — 計算過去 7 天您資料庫中的訂單與各平台回報的轉換次數。預期平台數據會與現實有所差異；您尋找的是一個*穩定*的比率，而不是完全相等。每週波動的比率意味著管道正在遺失事件。
3. **點擊識別碼覆蓋率** — 付費訂單中有多大比例附加了點擊識別碼？如果遠低於付費流量的佔比，則步驟 1-4 在某處出現了問題。這個單一數字是整個系統中最好的健康檢查。
4. **歸因期間認知** — 平台依點擊/檢視期間進行回報並歸因至廣告的點擊日期，您的資料庫則依訂單日期進行回報。跨日比較絕不會完全吻合；請在 7 天以上的期間進行比較。

## 伺服器端追蹤無法修復的問題

向專案利害關係人明確說明這一點，因為此處的預期通常是錯誤的：

- 它無法恢復*使用者層級*的跨網站追蹤。它改善的是轉換*回報與比對*，而非身分識別解析。
- 它不會讓各平台的數據彼此一致。每個平台都在其自己的歸因模型下主張功勞，因此跨平台的總和將超過實際訂單。只有您自己的訂單資料表才是事實依據。
- 它無法修復同意權問題。同意權和區域隱私法規要求仍然適用於伺服器端發送；雜湊後的 PII 仍然是 PII。不要將伺服器端回報用作繞過同意權決定的方法。

## 實作方式

如果漏斗位於託管平台上，這通常是一項付費整合加上標籤管理員容器，而跨網域點擊識別碼傳遞通常是您無法控制的部分。

[Autonnel](https://github.com/autonnel/autonnel)（Apache-2.0，自託管）原生實作了這七個步驟鏈：在到達網頁上將點擊識別碼和 UTM 擷取至伺服器端漏斗工作階段中，跨越跨網域漏斗步驟攜帶，寫入訂單中，並作為排隊的伺服器端轉換傳遞至 Facebook (Conversions API)、TikTok (Events API)、Google Ads 和 Bing (CAPI)，並在管理介面中設定個別平台的事件對應。

從 <https://github.com/autonnel/autonnel> (Apache-2.0) 取得存放庫，檢出
發佈標籤，並閱讀其 `docker-compose.yml` — 它宣告了將要執行的映像檔與
連接埠。從該檢出目錄執行：

```bash
docker compose up
# 開啟 http://localhost:4321，完成 /setup，然後進入 Settings → Ad platforms
```

對於生產環境，它部署到 Cloudflare Workers，其中排隊的回傳遞送在存放庫中隨附的 Cron 處理常式上執行。確認 Cron 觸發程序在部署後仍然存在，否則排隊的轉換會無聲無息地停止。

連結認證後，在擴大支出之前執行上述驗證檢查清單。點擊識別碼覆蓋率數字是第一天需要關注的關鍵數據。
