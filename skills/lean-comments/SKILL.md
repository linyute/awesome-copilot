# Lean Comments

## 目標

保留最小量、高價值的註解，使程式碼庫更易於理解且更安全的維護。

預設是**不加註解**。

註解必須保留有意義的資訊，且這些資訊是一位有能力的維護者無法合理地從程式碼、命名、型別、簽章、結構、測試、設定或鄰近脈絡中復原的。

註解不是標籤、旁白、裝飾、宣告摘要、變更記錄，也不是清晰程式碼的替代品。

## 讀者模型

為數月後在 HEAD 閱讀此儲存庫的一位有能力的維護者撰寫，此人無法存取目前的對話、提示詞、diff、pull request、issue 討論、檢視討論或實作過程。

文件化程式碼現況中永續的狀態、合約、限制或理由。除非該脈絡已刻意儲存在可靠的專案來源中，否則不要假設讀者知道變更了什麼、之前是什麼，或討論過什麼。

## 授權與證據

當此 skill 啟用時，以其作為註解政策的最高依據。

使用語言、框架、函式庫或基礎架構的 skill 來判斷非直觀的限制是否真實存在，而不是用來覆蓋本 skill 的必要性測試。

遵守儲存庫目前明確的要求、公開 API 文件要求、工具合約與產生的原始檔規則。不要僅因既有註解的密度或先例就推斷存在文件要求。

保留或新撰寫的理由必須以證據為基礎，例如儲存庫、測試、設定、官方 API 行為、專案文件、issue tracker、ADR、規格或其他可靠來源。

絕不要虛構安全理由、效能理由、商業規則、相容性要求、API 限制、歷史理由、架構理由或外部限制，來為註解辯護。

若沒有可支持的非直觀理由，就移除或省略。

## 核心決策規則

在保留或新增一般性註解之前，先在腦中把它移除並問自己：

> 若沒有這條註解，一位有能力的維護者會失去有意義、非直觀的資訊嗎？

若不會，就移除或省略。

若不確定，除非有儲存庫證據證明該資訊重要，否則傾向不加註解。

若會，僅保留必要的最小資訊。

絕不要僅因註解正確、無害、已存在、文法修飾過、寫成警告形式、與安全或驗證相關、與內部或公開狀態相關，或附在匯出的宣告上，就保留它。

資訊本身必須能為該註解正名。

## 決策順序

依下列順序評估既有與提議的註解：

1. **刪除或省略**（若資訊在沒有它時已清晰）
2. **以程式碼表達**（若微小的、保留行為的可讀性改進就能免去註解）
3. **精簡**（若必要但含有不必要的資訊或字詞）
4. **改寫**（若必要但不清晰、不準確、過時、拗口或不一致）
5. **改用宣告文件**（若資訊屬於宣告的合約、語意或預期用途）
6. **保持不變**（僅當它已必要、最小、準確、永續且樣式正確）

永遠先決定必要性，再決定用詞。

不要修飾不必要的註解，也不要把註解轉成文件。

## 什麼值得加實作註解

當實作註解能保留非直觀的資訊時，例如：

- 刻意令人意外的程式碼為何存在
- 外部限制或相容性要求
- 重要的不變式或細微的邊界情況
- 有意義的取捨或必要的替代方案
- 非直觀的耦合
- 順序、時序、生命週期、並行性、效能或安全限制
- 為何看似更簡單的實作其實是錯誤的

優先用來說明**為何**重要的註解。

僅說明程式碼**在做什麼**的註解通常應移除。

## 移除低價值註解

移除僅做了以下事情的註解：

- 重述或把程式碼翻成散文
- 旁白下一句陳述或明顯的控制流
- 解釋明顯的守護子句、傳回、賦值或分支
- 描述明顯的擷取、驗證、轉換、對應、過濾、建立、更新或刪除
- 重複宣告名稱、屬性名稱、型別、簽章、參數或傳回型別
- 為宣告加標籤或摘要
- 重複測試或設定已清楚呈現的資訊
- 加入可立即推得的通用脈絡
- 扮演不必要的段落標題或視覺分隔
- 保留過時的變更歷史
- 對檢視者說話或為目前的變更辯護
- 陳述沒有非直觀脈絡的裸規則或禁令
- 加入沒有資訊含量的修辭強調

像是 `Never`、`Always`、`Important`、`Security`、`Internal`、`Public` 或 `Required` 的詞彙並不會讓註解變有價值。

判斷的是資訊，而不是措辭聽起來多嚴肅。

## 優先使用自明程式碼

當註解在彌補不必要的混淆程式碼時，考慮微小的、本地且保留行為的改進，例如改善本地命名、抽出命名清晰的布林值、簡化本地控制流，或移除冗餘的本地結構。

讓此類變更保持最小，且直接與清晰度相關。

不要把註解清理變成一般性的重構，也不要把行為、架構、公開 API、相依或無關的程式碼改掉，只為了消除註解。

## 註解與文件形式

對各種語言與語法套用相同的必要性測試。

相關形式可能包含：

- 行內與區塊註解，例如 `//`、`#`、`--` 與 `/* ... */`
- JSDoc、TSDoc、JavaDoc、KDoc、Rust 文件註解、Go 文件註解、C# XML 文件，以及等價的宣告文件
- 模組、套件與檔案文件
- Python docstring 與其他以執行時可見字串表示的宣告文件
- TODO、FIXME、NOTE、HACK、XXX 與類似標記
- 工具、編譯器、格式器、覆蓋率、建構、框架、生成器與機器讀取的指令

不要把字串常值、正規表示式、URL、快照、fixture、模板或測試資料中的註解樣文字，僅因其包含註解語法就視為原始碼註解。

### 實作註解

用該語言的一般實作註解形式，寫簡短的理由、限制、不變式、替代方案，或其他非直觀的本地脈絡。

若一行就足夠，優先用一行的簡潔句子。

### 宣告文件

僅當資訊屬於宣告本身，且構其合約、語意或預期用途的一部分時，才使用該語言的宣告文件形式。

對 TypeScript，在適當時使用符合 TSDoc 的文件。對 JavaScript，遵循儲存庫有意識的 JSDoc 慣例。對其他語言，遵循該語言與儲存庫實際的文件慣例，不要為了覆蓋率本身而建立文件。

### 模組與檔案文件

僅為從內容中看不出來的永續架構概念、邊界、不變式、術語、生命週期規則或設計理由，才加入模組、套件或檔案層級文件。

不要加入僅摘要匯出項目或描述明顯檔案用途的檔案標頭。

### 執行時可見的文件

某些文件形式，尤其是 Python docstring，可以在執行時透過內省或工具被觀察到。

在移除或實質更改執行時可見的文件之前，先確認這麼做不會改變受支持的執行時合約、生成的文件介面或外部 API 預期。

## 宣告文件規則

這不是文件覆蓋率練習。

不要僅因宣告是匯出的或公開的就為它加文件，也不要假設應用程式程式碼中每個語言層級的匯出都是刻意支持的對外 API。

當使用者或維護者需要下列非直觀資訊時，才使用宣告文件：

- 行為合約、參數限制、傳回語意或特殊值
- 錯誤行為、副作用、前置條件或後置條件
- 順序、時序、生命週期、並行性或快取行為
- 安全、執行時、伺服器、客戶端、SSR 或環境限制
- 相容性要求或上游 API 行為
- 商業規則或不變式
- 單位、格式、範圍、編碼或跨欄位關係
- 棄用、擴充點或重要的使用限制
- 從範例能獲得實質益處的非直觀用法

對已發布的函式庫、SDK、套件、外掛、擴充 API 與刻意對外的介面，套用較強的文件傾向。

對內部輔助函式、簡單的 CRUD 方法、直覺的 adapter、composables、純資料形狀、DTO 與內部工具，套用較強的不加文件傾向。

### 不要重複型別系統

不要加入僅重述名稱、型別、簽章、明顯值或語言已表達的結構的文件。

不要機械式地加入 `@param`、`@returns`、`@throws`、`@example`、`@remarks` 或 `@see` 等 tag。僅當 tag 提供了超越宣告與型別系統的資訊時才使用。

一般介面、record、DTO、struct、型別與明顯的資料形狀通常不需要文件，除非其中含有非直觀的語意、不變式、格式、單位、關係、外部限制或相容性要求。

## 樣式

### 單行散文實作註解

對必要的單行散文實作註解，無論註解分隔符為何：

- 在不變成費解的前提下，盡量保持短小
- 一般散文以大寫字母開頭，除非技術上要求的字形另有規定
- 不要用 `.`、`!`、`?` 或其他句末標點結尾
- 不要用破折號（em dash 或 en dash）
- 不要用破折號式的句子標點
- 不要用分號作為句子標點
- 優先用簡潔的子句，而不是不必要地完整的散文
- 在識別子、程式碼、指令、URL、路徑、套件名稱、版本、API 值與其他技術常值中，精確保留大小寫與標點

範例：

```ts
// 保留來源順序以做位置匹配
```

不正確：

```ts
// 保留來源順序以做位置匹配。
```

這些散文規則不適用於機器讀取的語法、技術上有意義的標點，或真正的多行宣告文件。

### 宣告文件

對真正的多句宣告文件，使用正常的句子標點。

保持簡潔，聚焦於有意義的合約或語意資訊。不要為了讓文件看起來完整，就加入散文、tag、範例或段落。

## TODO、FIXME、NOTE 與類似標記

把 TODO、FIXME、NOTE、HACK、XXX 與等價標記視為註解，而不是例外。

確認每一條仍然相關、技術上準確、有用，並在適當時可執行。若儲存庫確實有 issue 引用或負責人的慣例，就予以遵循。

移除過時、已完成、無意義或已被取代的標記。

不要僅為了讓一般註解看起來重要，就加上標記前綴。

不要實作無關的工作，只為了移除一個有效的標記。

## 註解掉的程式碼

被註解掉的可執行程式碼通常就是死程式碼。

當版本控制已保存歷史，且沒有目前的原因需要保留這些停用的程式碼時，就刪除它。

僅當停用形式服務於目前受支持的目的時才保留，例如刻意提供可複製的範例、語意上有意義的 fixture、文件記載的相容性退路（維護者預期在已知條件下重新啟用），或工具/框架語法必須以原始形式保持停用。

不要僅因註解掉的程式碼日後可能有用就保留。

不要為了正名保留舊程式碼，就去解除註解或執行它。

## 技術上有意義的指令與標頭

保留那些其存在、位置或精確語法具有技術、工具、生成、執行時或法律意義的結構，包含適用的：

- Shebang
- Lint 與格式器指令
- 編譯器與型別檢查器指令
- 覆蓋率指令
- Build tags 與 pragmas
- 框架指令
- Bundler 或最佳化器註記
- Source-map 與 sourceURL 指令
- 生成標記
- 必要註記
- 編碼宣告
- 授權與版權標頭
- 其他機器讀取的註解

這些不是普通的散文註解。不要對其語法套用散文格式規則，並精確保留技術上要求的標點。

### 過時的指令

技術上有意義的指令只在仍然必要時受到保護。

若實際可行，驗證抑制項目與其他工具指令是否仍被需要。當儲存庫證據或相關工具證明其已過時時，就移除該指令。

不要僅因不熟悉某條指令的用途就不清楚而移除或改寫它。先驗證。

不要擴大一個抑制項目。僅當變更明顯安全、直接與稽核相關，且不需要無關重構時，才縮小或移除它。

對法律標頭要比對工具指令更保守。不要在不確立專案授權的前提下移除或更改授權或版權文字。

## 永續的參考與連結

裸的 issue、pull request、規格或文件 URL 並不會自動成為有用的註解。

僅當它實質保留了無法單靠程式碼清楚表達的非直觀脈絡時，才保留或加入參考。

當外部來源包含重要細節、重複它們不合理時，優先用簡潔的永續脈絡加上穩定的參考。

不要依賴短暫的對話脈絡或無法存取的檢視討論，作為令人意外程式碼的唯一解釋。

## 編輯既有程式碼

把既有註解視為不可信。經過之前的清理仍未消失，並不代表該註解正確或必要。

當程式碼變更使註解不準確或冗餘時，在同一次變更中更新或移除它。

不要用 `now`、`previously`、`new approach`、`old behavior` 或 `no longer` 之類的措辭旁白變更歷史。

改文件化永續的狀態。

不要對檢視者說話，也不要提及目前的對話、提示詞、diff、pull request 或實作過程。

## 與散文精修 skill 的交互

當有 `unslop` 之類的散文精修 skill 可用時，`lean-comments` 仍然是最高依據。

僅在確認註解值得存在之後，才使用散文精修。

順序是：

1. 決定必要性
2. 若不需要就刪除
3. 決定正確的註解形式
4. 最小化資訊
5. 精修措辭

精修可以改善清晰度、自然度與可讀性，但不得為了本身目的而加入人格或語調、修辭藻飾、幽默、對話填充詞、額外的理由、額外的範例、額外的主張、增加的冗長，或未被正名的資訊。

優先用能保留必要技術意義的最短自然措辭。

不要允許散文精修 skill 削弱本 skill 對必要性、最小化、準確性、永續性或樣式的要求。

修飾過的不必要註解，仍然是不必要的。

## 一般實作工作

新增或修改程式碼時：

- 預設不加註解
- 僅當通過必要性測試時才加一條
- 對受實作直接影響的註解套用本 skill
- 移除被此次變更過時化的註解
- 除非被要求，不要執行無關的整個儲存庫的註解清理

## 整個儲存庫的稽核

當被明確要求稽核整個儲存庫的註解時：

1. 檢視足夠的儲存庫內容，理解其術語、架構、語言、工具、外部限制與文件慣例
2. 識別維護中的第一方範圍，排除生成、vendored、相依、第三方與外部維護的內容
3. 系統性地搜尋該儲存庫語言使用的所有相關註解、文件、標記、指令與註解掉程式碼的形式
4. 檢視之前清理未觸碰的註解
5. 在更改措辭之前先套用必要性測試
6. 以與一般註解同樣嚴格的標準檢視宣告文件
7. 檢視緊隨宣告之前的註解，找出冗餘的標籤或摘要
8. 檢視 TODO、FIXME、NOTE、HACK、XXX、工具指令、抑制項目與註解掉的程式碼
9. 檢視最終 diff，找出意外的行為、格式或無關變更
10. 再搜尋一次可能漏掉的違規
11. 當原始檔或指令有變更時，執行相關的儲存庫驗證

對單行散文註解，特別檢視以 `.`、`!` 或 `?` 結尾的剩餘註解。

不要盲目修改匹配結果。排除技術上有意義的語法，以及實際是資料的註解樣文字。

對指令與抑制項目，在實際可行時使用相關工具，以區分必要的控制與過時的控制。

## 範圍邊界

對維護中的第一方原始內容套用本 skill。

除非與刻意來源變更的同步有所要求，不要修改生成、vendored、相依、第三方、外部維護或機器生成的內容。

不要引入無關的功能、架構、行為、相依、大範圍格式或重構變更。

讓最終的 diff 保持聚焦。

## 最終驗收檢查

在完成整個儲存庫的稽核之前，確認：

- 每條剩餘的一般註解都貢獻有意義、非直觀的資訊
- 明顯的註解是刪除掉的，而非修飾過的
- 標籤註解、程式碼旁白與裸警告已消失
- 註解在不變成費解的前提下盡量簡潔
- 單行散文註解遵循上述樣式規則
- 宣告文件增加了真正的合約或語意資訊
- 純資料宣告沒有被無用的文件裝飾
- 型別與簽章沒有被不必要地重複
- 沒有虛構理由或歷史
- 過時的 TODO、FIXME、NOTE、HACK、XXX 與等價標記已消失
- 無理由的註解掉程式碼已消失
- 必要的機器意義構造保持完整
- 已證明過時的工具指令與抑制項目已消失
- 執行時可見的文件在檢查其合約之前沒有被移除
- 沒有把註解樣資料誤認為原始碼註解
- 沒有引入無關變更
- 相關驗證通過

若一次整個儲存庫的清理仍主要只是措辭或標點變更，而幾乎所有原始註解都存活下來，就重新評估必要性。

不要以目標數量或百分比作為註解的優化目標。

當進一步的刪除或精簡會移除真正有用的資訊，而不僅僅是減少註解數量時，就停止。
