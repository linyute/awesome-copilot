# 打包與部署

在變更部署排除項目、打包或部署之前為強制必讀。
基準：`logicapp` 1.0.0b1。打包屬於本機封存建立；核心 ZIP 部署則是
一項獨立且需獲授權的 Azure 變更操作。應保留既有受支援的存放庫／CI 部署
途徑，而非僅因本 Skill 包含 CLI 範例就將其取代。

## 確立實際邊界

識別存放庫根目錄、Logic Apps 主機根目錄、可部署的執行階段資產、專屬測試、
範本、本機狀態以及預期的套件目的地。專案可位於存放庫
根目錄或巢狀結構中；請勿強制要求方案根目錄 (solution-root) 的配置。

相對於實際的 `.gitignore` 位置合併原始碼控制排除規則。針對
專案位於根目錄的配置，常見的適用項目如下：

```gitignore
local.settings.json
.azurelogicapps/
workflow-designtime/
.logicapp-test-state/
*.log
```

針對巢狀專案，請調整路徑或在主機根目錄放置具範圍限制的規則。確保巢狀的
機密副本亦被忽略。新增實際產生的輸出目錄，而非假設
存在但實際並不存在的 `logs`/`artifacts` 目錄。保留無關的項目並驗證
有效的排除規則，包括現有已追蹤的檔案：新增忽略規則並不會
移除已被追蹤的機密，亦無法使其歷史記錄變安全。

**主機根目錄的 `.funcignore`** (而非 `.gitignore`) 定義了額外的部署排除規則。
合併適用的規則，例如：

```gitignore
local.settings.json
cloud.settings.json
.azurelogicapps/
.logicapp-test-state/
workflow-designtime/
.vscode/
.git/
.gitignore
*.code-workspace
*.log
*.trx
```

針對包含 `.funcignore` 的主機根目錄內的測試、受測物、請求範例、文件、
設定範本、報告、產生的套件及其他非執行階段內容，調整／新增其相對於主機根目錄的精確位置。
例如，若主機位於 `repo\App`，要在 `repo\App\.funcignore` 中排除
`repo\App\fixtures`，應使用 `fixtures/` 而非 `App/fixtures/`。
主機根目錄以外的資料夾本就已在套件來源之外。請勿使用廣泛的
二進位檔排除規則，以免誤刪必要的執行階段組件。

僅含預留位置的設定範本屬於選用項目。請載明執行階段並不會
讀取該範本；本機／雲端設定應透過適當流程進行設定。即使該範本
可安全納入追蹤，也應將其排除於部署之外。它絕不可包含真實秘密。
請勿將 `.gitignore` 覆蓋至 `.funcignore`，亦不可全面替換既有的使用者規則。

## 打包前先進行驗證

在發佈打包之前，立即要求嚴格且已完成的完整專案驗證：

```azurecli
az logicapp workflow validate --path App --all --fail-on-warning
```

當工作／存放庫要求進行執行階段驗證時，先確立就緒狀態，並
針對預期目標完成具備執行階段支援的驗證格式。回報實際的受阻原因；
請勿停用警告，亦不可宣稱 HTTP 202 已接受的驗證即代表已完成。
檢視現有的驗證失敗問題，切勿無提示地削弱發佈關卡要求。

在可行情況下選擇位於主機根目錄之外的輸出路徑。位於目前目錄的目的地
(例如 `App.zip`) 是在子層級 `App` 主機之外；若主機位於 `"."`，請選擇明確的
外部目的地或已驗證的排除項目。僅建立實際要求的輸出父目錄。

```azurecli
az logicapp deployment package --path App --output-path App.zip
```

選用的 `--manifest MANIFEST_PATH` 用於選取資訊清單的目的地。封存檔與資訊清單
必須為不同檔案，包括正規化後的路徑／別名在內。`--force` 僅授權替換
經審查的輸出；絕不可用它來繞過無效的輸入或排除項目。
無法讀取、非檔案或無效 UTF-8 的 `.funcignore` 屬於錯誤，而非空政策。

打包程式會不區分大小寫地排除 `local.settings.json` (包括巢狀副本)、
專屬且已識別的原生測試／狀態內容，以及原始 TRX。它會拒絕模糊且混合的
測試／執行階段根目錄，而非直接捨棄執行階段檔案。專屬原生測試的意圖
是從專案宣告中識別，而非僅依賴檔案名稱或狀態目錄標記。
請勿依賴機密資料掃描來辨識每種可能的秘密或自訂產物。

## 檢查實際的 ZIP 與資訊清單

必須包含所有要求的工作流程目錄、`host.json`、需要時的 `connections.json`、
被參考的 `parameters.json`／執行階段檔案，以及必要的組件／產物。
確認 ZIP 根目錄即為主機內容，而非多包一層專案目錄。

必須確保排除下列項目：

- 本機設定、認證、已簽署的 URL／金鑰或帶有秘密的匯出內容；
- 設定範本與非執行階段的受測物／測試；
- 原生私有快取、測試狀態、原始 TRX 以及測試建構輸出；
- 記錄、編輯器／工作區檔案、存放庫 Metadata 與執行階段狀態；
- 產生的套件、巢狀封存檔以及不當的診斷報告。

使用適合該作業系統的唯讀封存工具進行檢查。資訊清單排除項目是
實用的佐證，但無法取代對封存檔本身的檢查。一般的執行階段二進位檔
可能是必要的；請勿不加區別地排除所有 `bin`、`.dll` 或 `.exe` 檔案。

**檢查關卡：** 嚴格驗證通過；精確檢查了封存檔／資訊清單；僅保留
可部署的內容。打包成功本身並不等於已部署或不含秘密的證明。

## 僅在經授權的範圍內部署

確認租用戶／訂用帳戶、資源群組、Standard 應用程式、環境／位置、部署
途徑以及外部影響。Azure 服務可能會產生費用。此預覽版並非
已具備生產就緒狀態的保證。請勿將建立基礎結構當作未經要求的副作用。

先決條件：

1. 應用程式與所需資源已存在，且具備相容的代管／部署組態。
2. 透過經授權的佈建預設啟用受控識別；已驗證所需的
   本機／雲端主體、連接器存取政策以及資料平面授權。
3. 所需的應用程式設定／參數與受控連線配置已完成設定且未公開數值。
   防止觸發程序啟動不完整的外部相依性。
4. 套件與驗證關卡皆通過；相關測試與部署核准皆已完成。
5. 部署／復原遵循既有的存放庫政策，包括協調多個寫入者。

若提供了現有管線，請使用既有管線。針對經授權的直接 CLI ZIP 部署，
核心 Logic Apps 命令可獨立於擴充功能打包流程之外使用：

```azurecli
az logicapp deployment source config-zip --resource-group GROUP --name APP --src App.zip --subscription SUBSCRIPTION_ID
```

此為核心命令，而非擴充功能所擁有的 `deployment deploy` 命令。請勿憑空捏造
此類命令。核心應用程式管理／設定命令亦與擴充功能的
執行階段 API 有所區別。它們的存在並不會將個別預覽命令的支援範圍擴大到
Consumption、混合式主機或部署位置 (deployment slots)。請先檢查特定目標的支援情況。

完整的應用程式部署會發佈共用檔案並新增雲端工作流程。
`workflow set` 僅是在可寫入目標上對單一既有工作流程進行個別核准的替換；
它無法取代設定或新應用程式的部署。
請勿繞過從套件執行或唯讀代管的限制。

## 分開驗證部署結果

在確認部署完成後：

1. 檢查部署結果與實際的工作流程清查清單。
2. 需要時，針對已部署的執行階段驗證本機編寫的專案：

   ```azurecli
   az logicapp workflow validate --path App --all --fail-on-warning --with-runtime --resource-group GROUP --name APP --subscription SUBSCRIPTION_ID
   ```

3. 檢查已部署的連線配置與所需的驗證／存取權限。
4. 執行經明確授權的代表性工作流程並驗證輸出／影響；
   使用實際受支援的執行識別碼，並在具備歷史記錄時診斷失敗動作。
5. 使用適當的唯讀檢查確認已排除的本機檔案／秘密未被部署，
   且不印出秘密內容。

在進入這些階段之前，請先使用從 `SKILL.md` 選取的強制性連線／線上作業程序。
執行階段範本驗證並不等於已部署檔案一致、連線認證通過或
商業邏輯執行成功；請將各種類型的佐證分開記錄。

若部署僅部分完成、驗證失敗、資源殘留或影響不明，
請回報實際狀態。請勿盲目重試、啟動不完整的相依性、刪除
保留的資源，或聲稱具備保證的復原機制。

**檢查關卡：** 符合預期的雲端內容／組態、完成所需的執行階段驗證、
驗證過經核准的情境、排除佐證，以及明確列出剩餘的受阻項目。
