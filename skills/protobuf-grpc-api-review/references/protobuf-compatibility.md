# Protobuf 相容性規則

當審查變更訊息、欄位、列舉、序列化或產生的 API 時，使用此參考資料。將其套用至涵蓋範圍內的實際編碼與執行階段。

## 變更分類

### 二進位傳輸不安全（wire-unsafe）

除非所有已序列化的資料與每個讀取端/寫入端都能不可分割地移轉，否則將下列情況視為破壞性變更：

- 變更現有欄位編號
- 重複使用已刪除或先前已發布的欄位編號
- 重複使用已刪除的列舉編號
- 將欄位移入現有的 `oneof`
- 在具有不同傳輸編碼的型別之間變更，例如 `string` 與整數

絕不要依賴表面上看似未使用的標籤而認為其沒有歷史資料。舊的二進位檔案、記錄、佇列與復原產物可能仍包含它。

### 二進位傳輸安全（wire-safe），但仍有其他面向需審查

- 新增具有新編號的欄位
- 移除欄位同時永久保留其編號；當重複使用名稱也不安全時，保留其名稱
- 新增具有新編號的列舉值
- 將一個具顯式存在性（explicit-presence）的欄位移入新的 `oneof`
- 將單一欄位的 `oneof` 變更為顯式存在性欄位
- 將欄位變更為具有相同編號與型別的擴充（extension）

這些仍可能破壞原始程式碼、商務邏輯、JSON 取用端、驗證或窮舉性列舉處理。

### 二進位格式相容但取決於推出流程

這些配對可以剖析相同的傳輸表示法，但可能會變更數值或遺失資料。優先考慮新增欄位。若移轉無可避免，請將寫入端限制在舊領域內，直到每個讀取端都已升級且復原期已關閉為止。

| 變更 | 必要條件或風險 |
| --- | --- |
| `int32`、`uint32`、`int64`、`uint64`、`bool` | 舊讀取端可能會截斷或重新詮釋數值；布林值語意特別具風險。 |
| `sint32` <-> `sint64` | 超出較窄範圍的數值在以 `sint32` 讀取時會改變。這些與一般整數編碼不相容。 |
| `fixed32` <-> `sfixed32`；`fixed64` <-> `sfixed64` | 正負號會改變應用程式語意。 |
| `string` <-> `bytes` | 對於 `string` 讀取端，Bytes 必須維持有效的 UTF-8。產生的 API 會變更。 |
| 內嵌訊息 <-> `bytes` | Bytes 必須始終包含該訊息編碼；產生的 API 會變更。 |
| 列舉 <-> 整數型別 | 未知列舉表示法與產生的行為因語言而異。 |
| 字串、bytes 或訊息的單一數值 <-> 重複數值 | 單一數值讀取端保留最後一個基本型別值或合併訊息；可能會遺失資訊。 |
| map <-> 其重複項目訊息 | Map 讀取端可能會重新排列項目並捨棄重複的鍵。 |

數值重複欄位通常會封裝（packed），不能與單一欄位安全地互換。將任何基數（cardinality）變更視為資料移轉而非程式碼清理。

## 刪除與替換模式

對於必須變更型別或語意的已發布欄位：

1. 新增具有新編號與相異名稱的新欄位。
2. 部署能理解這兩個欄位的讀取端。
3. 部署填入新欄位的寫入端，若復原需要則進行雙重寫入。
4. 在需要時回填已保存的資料。
5. 僅在舊二進位檔案與復原程序結束後，停止讀取與寫入舊欄位。
6. 移除舊欄位並保留其編號與名稱。

當欄位仍在宣告中時，不要保留舊編號。不要將舊編號重複用於替代欄位。

## 存在性、預設值與 `oneof`

- 將隱式純量存在性變更為顯式 `optional` 存在性在傳輸上相容，但會變更產生的 API 與預設值的語意。請檢查合併、修補（patch）、相等性與序列化行為。
- 隱式存在性純量無法區分「未設定」與其預設值。若在更新 API 中零、空值或 false 具有意義，請使用顯式存在性或欄位遮罩（field mask）。
- 將欄位新增至 `oneof` 通常是可剖析的，但是當舊用戶端設定已知成員並重新序列化時，可能會清除未知成員。審查「讀取-修改-寫入」路徑。
- 移除 `oneof` 成員會使新讀取端無法得知先前設定了哪個已移除的成員。請保留編號並規劃移轉。
- 絕不要新增必填（required）欄位。較舊的寫入端無法填入它，且部分推出或復原會變得不安全。
- 不要在 proto2 中變更顯式預設值；版本不一致的讀取端可能會對同一個缺少的欄位有不同的詮釋。

## 列舉

- 除非既有協定刻意使用其他零值，否則保留零值的 `*_UNSPECIFIED` 作為第一個值。
- 新增值在二進位層級安全，但可能破壞窮舉式 switch 或較舊的商務邏輯。請搜尋產生語言的取用端。
- 刪除值時，保留其編號，當名稱為協定的一部分時亦保留其名稱。
- 對於別名，在舊別名之後新增新別名。安全的重新命名需要在移除舊名稱之前分段推出剖析器與序列化器。

## ProtoJSON 與其他具名格式

獨立於二進位傳輸格式之外審查基於名稱的格式：

- 欄位與列舉名稱可以是已序列化的協定資料，因此重新命名可能破壞讀取端
- ProtoJSON 不保留未知欄位，這會限縮向前相容性
- 新增欄位或列舉值可能導致拒絕未知名稱的舊剖析器失敗
- 變更 `json_name`、整數/字串表示法、bytes 編碼或 `oneof` 形狀可能會改變公開 JSON 結構描述
- 即使內部傳輸是二進位 gRPC，HTTP 轉碼也可以公開訊息欄位與列舉名稱

詢問是否存在已儲存的 JSON。若有，請在相容性測試中包含歷史承載資料。

## 驗證矩陣

在行為可能因語言而異之處使用真實產生的執行階段：

| 寫入端 | 讀取端 | 需斷言的內容 |
| --- | --- | --- |
| 舊 | 新 | 數值、存在性、列舉處理與驗證保持正確。 |
| 新 | 舊 | 容許未知資料且已知數值不被重新詮釋。 |
| 舊 | 新 -> 修改 -> 序列化 -> 舊 | 未知欄位得以保留且已知欄位不被清除。 |
| 新 | 舊 -> 修改 -> 序列化 -> 新 | 新欄位或 `oneof` 成員不會以無訊息方式遺失。 |

此外，編譯描述項（descriptor）、執行存放庫的破壞性變更檢查工具、測試擴大/縮小數值領域的邊界值，並對任何支援的 JSON 表示法進行往返測試。
