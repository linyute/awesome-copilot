# Protobuf 與 gRPC API 審查

將 `.proto` 與相關 gRPC 變更視為長期協定進行審查。區分傳輸格式所允許的範圍，與產生的用戶端、JSON 使用者、已儲存資料以及混合版本部署所能安全容忍的範圍。

## 從相容性範圍開始

在判定變更是否安全之前，請確定：

- 舊的與新的結構描述，而非僅有最終檔案
- 承載資料使用二進位 protobuf、ProtoJSON、文字格式或多種編碼
- 訊息是否保存在資料庫、佇列、記錄、快取或事件中
- 用戶端是否存在於存放庫之外或獨立發布
- protobuf 語法或版本（edition）以及產生的語言/執行階段版本
- HTTP/JSON 轉碼、反映（reflection）、服務設定或結構描述登錄檔是否公開了該協定
- 部署順序、復原期以及混合版本運作的時間長度

若缺乏脈絡，請說明假設並降低信賴度。不要單憑新的結構描述就斷定變更具備回溯相容性。

## 審查工作流程

### 1. 盤點協定變更

透過完整符合規格的符號比較舊定義與新定義。記錄：

- 訊息欄位：編號、名稱、型別、基數、存在性、`oneof`、預設值與相關選項
- 列舉：值名稱、編號、別名、保留項目與零值
- 服務：套件、服務、方法、請求與回應型別以及串流模式
- 產生的 API 輸入：套件選項、外部類別名稱、命名空間與自訂選項

在確認格式變更不會改變描述項或產生的 API 後，忽略純格式變更。

### 2. 評估四個相容性維度

獨立評估每個受影響的符號：

1. **二進位傳輸** — 舊讀取端與新讀取端是否都能剖析舊位元組與新位元組且不損毀或遺失資料？
2. **具名格式** — ProtoJSON、文字格式、REST 轉碼或基於名稱的取用端是否仍能運作？
3. **原始程式碼與產生的 API** — 重新產生的用戶端是否能編譯並保留存在性、列舉與存取子行為？
4. **行為與維運** — 狀態碼、重試安全性、期限、授權、串流與資源邊界是否保留了 RPC 協定？

有關欄位、列舉、存在性、`oneof` 與序列化變更，請參閱 [protobuf 相容性規則](file:///mnt/d/linyute/Copilot/awesome-copilot-temp/localization/skills/protobuf-grpc-api-review/references/protobuf-compatibility.md)。當服務、方法或執行階段行為變更時，請參閱 [gRPC 協定審查](file:///mnt/d/linyute/Copilot/awesome-copilot-temp/localization/skills/protobuf-grpc-api-review/references/grpc-contract-review.md)。

### 3. 追蹤混合版本情境

針對每個非微小的變更，推敲這些路徑：

- 舊寫入端 -> 新讀取端
- 新寫入端 -> 舊讀取端
- 舊讀取端修改並重新序列化新訊息
- 新寫入端發出新值後的復原
- 移轉後讀取已保存的舊資料

對於條件相容的變更，識別確切的寫入端限制以及可放寬該限制的時間點。安全推出通常需要先部署讀取端再部署寫入端，並保留舊欄位或方法，直到不再需要復原為止。

### 4. 審查存放庫依據

可用時使用存放庫自有的工具：

- 使用專案的 `protoc`、Buf、Gradle、Maven、Bazel 或特定語言工作編譯描述項
- 執行已設定的破壞性變更或 lint 檢查
- 僅在存放庫慣例有提交產生的程式碼時，檢查產生的程式碼差異
- 搜尋呼叫位置以檢查窮舉式列舉 switch、存在性假設、JSON 欄位名稱、方法路徑、狀態處理與重試設定
- 在提出新機制之前尋找相容性測試資料或描述項基準線

除非你已實際執行，否則不要宣稱檢查已通過。若所需的工具或基準線不可用，請指明未經查證的風險。

### 5. 產生具體可行的審查

以單一判定開頭：

- **相容（Compatible）** — 在陳述的相容性範圍內安全
- **取決於推出流程（Rollout-dependent）** — 可剖析，但僅在明確順序或數值限制下安全
- **破壞性（Breaking）** — 導致傳輸、具名格式、原始程式碼或行為不相容
- **脈絡不足（Insufficient context）** — 舊結構描述、編碼、取用端或部署模型未知

然後僅提供有依據支持的發現事項。每個發現事項包括：

```text
[severity] 簡短標題
Location: 檔案與符號或變更行
Dimension: binary | JSON/text | source | behavior/operations
Change: 舊協定 -> 新協定
Impact: 具體的失敗混合版本情境
Remediation: 最小的安全結構描述變更或分段移轉
```

對於資料損毀、無法剖析的資料、標籤重複使用或無法避免的實際上線中斷使用 **blocker**；對於可能跨版本遺失資料或不安全的 RPC 行為使用 **high**；對於有邊界的相容性或維運風險使用 **medium**；對於不破壞協定的可維護性問題使用 **low**。不要將風格偏好誇大為相容性發現事項。

結論包含：

- 變更符號的精簡相容性矩陣
- 若需要移轉時的推出/復原順序
- 可證明剩餘假設的針對性測試

## 預設安全原則

- 即使在刪除後，也絕不重複使用欄位或列舉編號；保留已刪除的編號與通常也保留名稱。
- 將變更欄位編號以及將欄位移入現有 `oneof` 視為破壞性變更。
- 將型別與基數變更視為移轉，即使其二進位傳輸型別相容亦然。
- 記住新增欄位或列舉值仍可能破壞產生的程式碼或窮舉式取用端。
- 獨立審查 ProtoJSON：名稱與未知欄位行為使其相容性範圍比二進位 protobuf 更窄。
- 當向前相容性取決於未知欄位時，在「讀取-修改-寫入」路徑中保留未知欄位。
- 優先採用累加式演進：新增欄位或 RPC、移轉讀取端與寫入端、宣告舊協定已淘汰，然後僅在相容性期間結束後將其移除。
- 在建立等冪性或重複資料刪除機制之前，絕不建議對變更狀態的 RPC 進行重試。
- 對於實際上線環境的 RPC，需要切合實際的用戶端期限與具備取消感知能力的伺服器端工作。

## 避免偽陽性

- 不要要求每個服務都使用串流、重試、健康檢查或 HTTP 轉碼。
- 不要僅因舊用戶端忽略新選用欄位而將其標記為破壞性變更。
- 不要未檢查數值範圍與推出順序就稱傳輸相容的型別變更為安全。
- 當 JSON、文字格式、反映或產生的原始碼 API 為取用端時，不要假設重新命名欄位無害。
- 不要對從未發布的欄位要求保留；當該區別至關重要時，請詢問發布歷史。
