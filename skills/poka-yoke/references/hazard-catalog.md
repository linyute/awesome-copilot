# 危害目錄（Hazard Catalog）

依據找出這些危害的檢驗視角組織而成、經常重複出現且會引發失誤的形式。每個項目包含：尋找特徵（what to look for）、造成危害的原因（why it bites），以及消除該危害的裝置與其達到的階梯。

請將此目錄作為工作詞彙，而非由上而下逐一執行的檢查清單。視角提問才是真正的工具；此目錄則是這些視角通常會發現的內容。

## 接觸視角，錯誤的東西是否放得進去？

工廠的類比：一個只能朝單一方向裝入的零件。在軟體中，型別就是形狀。

### C1. 相鄰的同型別參數

**特徵**：兩個或多個連續相同基元型別的參數，`transfer(from: string, to: string)`、`resize(w: number, h: number)`、`slice(start: int, end: int)`。

**造成危害的原因**：將它們調換順序仍可編譯、能通過審查，並產生一個看似合理卻完全錯誤的結果。這是軟體中最常見的自傷陷阱（footgun）之一，也是最容易乾淨解決的陷阱之一 — 一旦兩種型別不同，錯誤的順序就無法通過編譯。

**裝置**：為每個概念建立不同的型別、品牌化型別（branded types）、新類型（newtypes）、數值物件（value objects），讓 `SourceAccount` 無法當作 `DestinationAccount` 傳遞。**控制（Control）。**
型別無法提供幫助時的替代方案：強制使用關鍵字／具名引數，讓呼叫者必須在呼叫處寫下名稱。**警告（Warning）**，但成本微乎其微，並能讓調換在審查中清晰可見。

### C2. 布林旗標參數

**特徵**：`createUser(name, true, false)`、`save(data, force=True)`，任何用於選擇行為而非攜帶資料的 `bool` 參數。

**造成危害的原因**：呼叫處難以閱讀，使得順序錯亂或遭到誤解的旗標變得隱蔽無形。新增第二個布林值會使情況呈指數級惡化。

**裝置**：每個維度使用一個列舉或常值聯集（`Visibility.Public`）、具有具名欄位的選項物件，或是兩個獨立的函式。對列舉而言屬於**控制（Control）**，因為錯誤的值根本無法拼寫出來。請注意例外情況：在支援關鍵字引數的語言中，若單一布林值的名稱在呼叫處閱讀起來很合理，則完全沒問題。

### C3. 邊界處的基元型別偏執

**特徵**：電子郵件、URL、路徑、權杖、租戶 ID、電話使用 `string`；百分比或持續時間使用 `int`，尤其在公開函式上。

**造成危害的原因**：每個下游函式都必須重新檢查或直接盲信。回傳布林值的驗證會丟棄證明，導致檢查被重複執行、略過，或執行得不一致。

**裝置**：剖析，而非驗證（parse-don't-validate）。在邊界執行一次 `parseEmail(s): Email | Error`，隨後下游簽章一律要求 `Email`。該型別永久帶有這項保證。**控制（Control）。**

### C4. 偏向字串型別的列舉

**特徵**：`status: string` 附帶列出所有值的註解；針對常值進行字串比對；數值以無結構描述（schema）的純文字跨越邊界。

**造成危害的原因**：打錯字仍可通過編譯。在其他地方新增的新變體永遠無法傳遞至此程式碼。沒有任何機制告訴你哪些值是合法的。

**裝置**：常值聯集、列舉或密封類別（sealed class），並配合窮舉比對（F1）。**控制（Control）。**

### C5. 隱含的單位與量級

**特徵**：`timeout: number`、`distance: float`、`retryAfter: int`：除了名稱或註解外，各處都沒有標明單位。同一個程式碼庫中的兩個系統對於秒與毫秒存在分歧。

**造成危害的原因**：相差 1000 倍的錯誤是無聲無息的，看起來就像當機或無窮迴圈。這類失誤曾聞名地摧毀了一具火星軌道探測器。

**裝置**：帶有單位的型別（`Duration`、`Milliseconds`），或至少在參數名稱中編碼單位（`timeoutMs`）。型別屬於**控制（Control）**。名稱屬於**第零階（rung 0）**：它能讓特意留心的讀者看到不符之處，但對於沒有留心的人則不會產生任何診斷資訊。值得一做；但不是裝置。

### C6. 以浮點數表示金錢

**特徵**：`price: float`、`amount: number`、使用二進位浮點數進行貨幣運算、對金錢進行 `==` 比較。

**造成危害的原因**：0.1 + 0.2 ≠ 0.3。錯誤在彙總過程中累積，對帳失敗且往往需要數天才能追查出原因。

**裝置**：在帶有貨幣標記的 `Money` 型別中使用整數最小單位（美分、分），或是使用十進位（decimal）型別。混合貨幣運算不應該通過型別檢查。**控制（Control）。**

### C7. 未驗證的外部輸入

**特徵**：`JSON.parse(body)` 轉換為 `any`、`request.json()` 轉換為裸字典、以逐個欄位方式取用沒有結構描述的第三方 API 回應、在邏輯深處讀取 `os.environ[...]`。

**造成危害的原因**：失敗發生在遠離邊界之處，表現為缺少屬性的令人困惑錯誤，此時格式錯誤的資料早已被部分處理或儲存。

**裝置**：在每個邊界使用結構描述：zod/valibot、Pydantic、`encoding/json` 轉入帶有驗證的具型別結構體、serde。剖析一次，隨後一律使用已剖析的型別工作。**控制（Control）。**
這同樣適用於*你自己的*服務回應；「內部」並非保證。

### C8. 一袋選用欄位的結構體

**特徵**：帶有數個選用欄位但只有特定組合才有意義的型別：`{ status, data?, error?, retryAt? }`、`{ isLoading, data, error }`。

**造成危害的原因**：N 個選用欄位宣稱有 2^N 個合法狀態。每個取用者都必須猜測哪些才是真實狀態，且彼此猜測不同。像「載入中且帶有資料的錯誤」等狀態變得可達，並且受到不一致的處理。

**裝置**：僅包含確切合法變體的標記聯集（discriminated union），使不可能的組合無法被表示。**控制（Control）。** 這是標準的「使無效狀態無法表示」手法。

### C9. 簡易日期時間

**特徵**：無時區的時間戳記、業務邏輯中散落著 `datetime.now()` / `new Date()`、日期以字串儲存、未考慮日光節約時間（DST）的運算。

**造成危害的原因**：在開發者的時區中是正確的，但在實際正式環境中是錯誤的，且在遵守 DST 的地區每年會出錯兩次。此外也很難測試，直接讀取時鐘的邏輯在沒有凍結或注入時間的情況下，無法在邊界條件下進行驗證。

**裝置**：各處一律使用感知時區的型別（timezone-aware types）、儲存時一律使用 UTC、注入時鐘使時間成為參數而非環境讀取。型別屬於**控制（Control）**，而注入時鐘帶來了可測試性，這是一項終於得以實現的偵測（Detection）階梯裝置。

## 固定值視角，不完整或大小錯誤的集合是否能通過？

工廠的類比：一個計數器，用於確認所有六顆螺絲都已裝上。

### F1. 非窮舉的分支

**特徵**：針對列舉的 `switch`/`match` 帶有毫無意義的 `default`，或是針對封閉值集合使用 if/else 鏈。

**造成危害的原因**：新增變體時，每個本應更新的地方都會無聲無息地走入預設分支。這個錯誤會在幾個月後，於沒有人測試過的那條程式碼路徑中爆發。

**裝置**：編譯器強制執行的窮舉性：TypeScript 中的 `assertNever(x: never)` 分支、Rust 中沒有萬用比對的 `match`、mypy 搭配 `assert_never`、Go 的窮舉 linter。**控制（Control）**，每個 switch 僅需一行，是回報效益最高的裝置之一。

### F2. 無限制的破壞性操作

**特徵**：由可能為空的篩選條件建構出的 `DELETE`/`UPDATE`；`rm -rf "$VAR"`；`.deleteMany(where)`；針對查詢結果進行批次發送／發佈；沒有上限的「清理」作業。

**造成危害的原因**：不可逆、立即生效，且與你的資料量成正比。空的篩選條件通常意味著「比對全部」。

**裝置**：拒絕空的謂詞（predicate）；針對全表操作要求明確的 `all=True`；限制受影響的資料列數量，超出上限時需要確認；預設採用列印出計數的 dry-run 試跑。在領域允許的情況下使用軟刪除（Soft-delete）。**控制（Control）。**

### F3. 掩蓋決策的預設值

**特徵**：為沒有安全預設值的項目提供預設值，例如 `retries=3`、`timeout=30`、`currency="USD"`、`tenant=None`、`region=default`。

**造成危害的原因**：呼叫者從不考慮該參數，而該預設值對其情境而言是錯誤的。這比報錯更糟糕，因為它會產生自信但錯誤的行為。

**裝置**：將其設為必要參數。僅在某個值對絕大多數情境皆正確，且對其餘情境雖不適用但無害時，才保留預設值。**控制（Control）。**

### F4. 執行階段才發現缺少的設定

**特徵**：在請求處理常式內部使用 `os.getenv("X")`；在首次使用時才延遲讀取設定；缺少的索引鍵產生 `None` 並繼續往下傳遞。

**造成危害的原因**：服務啟動並通過健康檢查，卻在需要該金鑰的那唯一一條程式碼路徑上失敗 — 通常是付款路徑，通常在凌晨 3 點。

**裝置**：在啟動時將整個設定剖析並驗證為具型別的物件，若有任何缺少或格式錯誤則以非零狀態碼結束。每個取用者一律接收具型別的物件。**控制（Control）**，它將凌晨 3 點的呼叫警報轉換為部署失敗。

### F5. 沒有交易的部分寫入

**特徵**：數個寫入按順序執行但沒有交易；寫入後緊接著外部呼叫，然後又是另一次寫入；「建立記錄然後發送電子郵件」。

**造成危害的原因**：中途失敗會使系統處於程式碼未建模且無法修復的狀態。

**裝置**：包裝在交易中；透過發件匣（outbox）將外部副作用移至交易之外；使序列具備等冪性，以便重播時能收斂。對交易而言屬於**控制（Control）**。

### F6. 僅在應用程式中強制執行的不變量

**特徵**：在 `INSERT` 之前透過 `SELECT` 檢查唯一性；在模型類別中強制要求不可為空但資料行未設定；依慣例維護外鍵關係。

**造成危害的原因**：該檢查在並行情況下會發生競爭條件，且會被任何其他服務、移轉、指令碼或手動使用 `psql` 的人員完全繞過。

**裝置**：將其推入結構描述：`NOT NULL`、`UNIQUE`、`CHECK`、外鍵、部分唯一索引。資料庫是所有接觸資料的事物共享的型別系統。**控制（Control）**，且具備獨一無二的持久性。

### F7. 未設限的輸入

**特徵**：沒有最大頁面大小的分頁；沒有大小限制的檔案上傳；由使用者提供的清單建構且未設上限的查詢；無限制的遞迴或重試。

**造成危害的原因**：與攻擊難以區分的資源耗盡事件，卻是由擁有龐大帳戶的普通使用者所觸發。

**裝置**：在邊界設定明確上限，盡可能由剖析型別強制執行。**控制（Control）。**

## 動作步驟視角，順序是否可能出錯？

工廠的類比：一個感測器，用於確認步驟 3 發生在步驟 4 之前。

### M1. 時間耦合

**特徵**：在呼叫其他方法之前必須先呼叫的 `init()`、`connect()`、`configure()`、`validate()`；包含「你必須先呼叫 X」敘述的文件。

**造成危害的原因**：沒有任何機制能強制落實。失敗的表現是 null 取值錯誤，或者更糟的是，半設定的物件無聲無息地產生錯誤結果。

**裝置**：建構函式或靜態工廠回傳完全就緒的物件；或使用型別狀態（typestate），使 `connect()` 回傳 `Connected` 型別，而其他方法僅存在於該型別上。**控制（Control）。**

### M2. 非等冪的可重試副作用

**特徵**：扣款、電子郵件、webhook 或外部變更可從重試、佇列取用者或 UI 按鈕觸達，但沒有等冪鍵（idempotency key），或僅有選用的等冪鍵。

**造成危害的原因**：至少一次遞送（at-least-once delivery）是常態而非例外。重複扣款是標準案例，既昂貴又人盡皆知。

**裝置**：**必要**的等冪鍵參數，並由 `(entity, key)` 上的唯一條件約束作後盾。**控制（Control）。** 選用的等冪鍵只是喬裝打扮的第零階。

條件約束是必要的，但單靠它並不充分。拒絕重複並不等於等冪：等冪鍵必須*在與副作用相同的交易中被保留*，並繫結至請求承載資料（payload），以便在重複使用的金鑰下傳入不同承載資料時會報錯，而非無聲無息地略過，並將儲存的結果重播給第二個呼叫者。重試並遇到條件約束衝突的呼叫者，根本無法得知第一次嘗試是否成功。

### M3. 非法的狀態轉移

**特徵**：實體的 `status` 欄位在多個地方被賦值變更；扣款前就可進行退款；「已取消」轉移回「待處理」。

**造成危害的原因**：每個指派該欄位的地方都必須了解整個狀態機，而其中某個地方可能並不了解。

**裝置**：提供單一轉移函式作為邁向新狀態的唯一路徑，並拒絕非法的轉移；或使用型別狀態（typestate）使非法的轉移無法通過編譯。**控制（Control）。**

資料列層級的 `CHECK` 在此處並不能提供深層防禦：它只能限制單一資料列的數值，無法得知該資料列原先處於何種狀態，因此它可以禁止 `status = 'refunded' AND total < 0`，但無法禁止 `shipped → pending`。在資料庫中約束狀態轉移需要觸發程序（trigger），或該資料列必須進行 join 的狀態轉移表。

### M4. 必須釋放的資源

**特徵**：將 `open()`/`close()`、`acquire()`/`release()`、`begin()`/`commit()` 作為獨立的陳述式，尤其在它們之間可能觸發 `return` 或 `throw`。

**造成危害的原因**：正常路徑運作良好，而錯誤路徑則發生洩漏。洩漏在高負載下表現為連線池耗盡，而這正是最承擔不起的時候。

**裝置**：範圍繫結的取得（scope-bound acquisition）：`with`、`defer`、RAII、`using`、try-with-resources。**控制（Control）。**

### M5. 先檢查後執行的競爭條件

**特徵**：`if (!exists(x)) create(x)`、在共享計數器上進行讀取-修改-寫入（read-modify-write）、檢查餘額隨後進行扣款、`if (!file.exists()) write(file)`。

**造成危害的原因**：在每次測試中都是正確的，但在並行環境下會間歇性出錯，且僅在正式環境中發生。

**裝置**：使其具備不可分割性（atomic）：唯一條件約束加上 `INSERT ... ON CONFLICT`、帶有預期版本的條件式更新、`SELECT FOR UPDATE`、比較並交換（compare-and-swap）。**控制（Control）。**

### M6. 發後不理的非同步

**特徵**：未等待（unawaited）的 promise、沒有錯誤路徑的 goroutine、未保留參照的 `asyncio.create_task`、沒有人進行 join 的背景寫入。

**造成危害的原因**：錯誤消逝無蹤。更糟糕的是，行程可能在工作完成前就結束，導致寫入無聲無息且非決定性地遺失。

**裝置**：將 `no-floating-promises` 設為 lint 錯誤、errgroup、結構化並行（structured concurrency）、保留並 await 該任務。來自 linter 的**警告（Warning）**，這是在 TypeScript、Python 和 Go 中的務實解法。Rust 則是幾乎唯一的例外：future 是惰性的且帶有 `#[must_use]`，因此未使用的 future 在無需任何 linter 的情況下就會產生編譯器警告。這是免費的**警告（Warning）**；加入 `#![deny(unused_must_use)]` 使建置失敗即可成為**控制（Control）**。

### M7. 依賴順序的移轉與部署

**特徵**：在包含程式碼變更的同一次部署中卸除（drop）或重新命名資料行的移轉；必須依特定順序上線但沒有任何機制強制落實的移轉與程式碼。

**造成危害的原因**：在發佈期間，舊程式碼會針對新結構描述執行。這是一場服務中斷事故，而不僅是單純的錯誤。

**裝置**：擴展／收縮（expand/contract）：新增、回填、雙重寫入、切換，隨後在稍後的部署中卸除，並搭配 CI 關卡阻止具破壞性的 DDL 與程式碼變更同時部署。透過關卡達成**控制（Control）**；該模式本身即是設計。

## 橫切關注點，被移除的裝置

其中好幾個是「移除帶來的危害」，即有人安裝了裝置而另一個人將其拆除。其他項目（X2、X5）則是無人刻意選擇的預設值：程式語言出廠時就處於錯誤設定，並且維持原樣直到有人察覺為止。
對待它們應比對待缺少的裝置更加懷疑，因為圍繞它們的程式碼是由明知該失敗可能發生的人所編寫的。

### X1. 吞噬錯誤

**特徵**：`catch {}`、`except: pass`、`except Exception: pass`、`_ = err`、`catch (e) { console.log(e) }` 且繼續執行、`.catch(() => null)`。

**造成危害的原因**：將大張旗鼓的失敗轉換為安靜無聲的錯誤答案：恰恰是防呆設計的反面。系統在毀損的假設下繼續運作。

**裝置**：處理錯誤，或讓它向外傳播。若吸收錯誤確實是正確的，註解必須說明預期會發生哪種特定失敗，以及為何繼續執行是安全的；僅捕捉該特定型別，而非所有錯誤。透過設為錯誤等級的 `no-empty` / 裸露 except（bare-except）lint 規則來強制落實。**警告（Warning）。**

### X2. 無聲無息的強制轉型與後備機制

**特徵**：在 `0`/`""`/`false` 為合法值的情境下使用 `value || default`；沒有基底（radix）或缺少 NaN 檢查的 `parseInt`；try/except 中回傳預設值的 `int(x)`；針對真實錯誤使用 `.unwrap_or_default()`；以傳入邏輯的 `undefined` 結尾之 `?.` 鏈。

**造成危害的原因**：從不良輸入產生看似合理的數值。錯誤在遠處浮現，而其肇因已難以察覺。

**裝置**：在零為合法值的情境下使用 `??` 取代 `||`；帶有錯誤分支的明確剖析；在邊界直接失敗而非進行替換。在剖析處屬於**控制（Control）**。

### X3. 被停用的測試

**特徵**：`it.only`、`describe.skip`、`@pytest.mark.skip`、`t.Skip()`、`#[ignore]`：尤其是在沒有說明原因的情況下。Linter 和型別檢查器抑制註解（`eslint-disable`、`# type: ignore`、`@ts-ignore`、`#nosec`）屬於 X4，偵測器也以相同方式將其分類。

**造成危害的原因**：關閉了偵測（Detection）階梯的裝置，通常是暫時的，最後卻成了永久的。測試套件保持綠燈，卻失去任何意義。

**裝置**：在 CI 中因聚焦（focused）／略過的測試而報錯失敗；要求每次抑制都必須附帶合理解釋的註解與 issue 連結；統計抑制次數並像棘輪般逐步減少該數量。**警告（Warning）。**

### X4. 型別系統中的脫逃機制

**特徵**：`any`、`as unknown as T`、`!` 非空斷言、帶有型別 switch 的 `interface{}`、`# type: ignore`、`unsafe`、`cast()`、以 `Object` 作為參數型別。

**造成危害的原因**：每一個都是型別系統保證失效之處。而且集中在最需要這項保證的邊界程式碼中。

**裝置**：在 lint 中以錯誤等級禁用它們，並提供狹窄且具合理說明的允許清單；改為在邊界進行剖析。**警告（Warning）**：根據 [method.md](../../../docs/method.md) 中的階梯，必要的 CI 關卡仍然屬於第 2 階：它宣告了失誤，而非消除犯錯的能力。唯有當未檢查的值根本無法被建構出來時，才達到**控制（Control）**。

### X5. 可變的共享預設值

**特徵**：Python 的 `def f(items=[])`、用作快取並被就地修改的模組層級字典、建構後被修改的共享設定物件、用作執行個體狀態的類別屬性。

**造成危害的原因**：狀態在呼叫、請求或測試之間洩漏。其症狀是依賴順序的行為，當你試圖重現它時卻又消失無蹤。

**裝置**：`None` 哨兵值搭配函式內部建構、凍結／不可變的數值型別、按請求獨立建構。ruff/flake8-bugbear 中的 `B006` 僅能強制落實引數預設值的情況；模組層級快取、共享設定物件與可變類別屬性則沒有 lint 規則，需要程式碼審查或使用無法被修改的型別。
**警告（Warning）**，或搭配凍結型別達到**控制（Control）**。
