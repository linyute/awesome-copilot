# 防呆（Poka-Yoke）：讓錯誤無法被表達

**人們總是會犯錯。這不是值得解決的問題。真正的問題是讓錯誤演變成缺陷。**

日本工業工程師新鄉重夫（Shigeo Shingo）於 1961 年在開關組裝線上發現了這一點。工人們總是忘記放彈簧。解決方法不是提醒：而是將工作拆分，讓工人先將兩個彈簧放在盤子裡，然後再從盤子裡組裝。盤子裡剩下的彈簧就是錯誤在單位放行前自動發出的警示。

盤子是一種裝置。「請記住彈簧」則不是。

## 發揮最大作用的一句話

> 註解、文件字串（docstring）、Wiki 頁面、審查檢查清單，或是指令檔案中寫著「不要做 X」的句子**都不是**防呆（poka-yoke）。那是培訓，而培訓會退化。裝置則不會。如果你的修復依賴於某人記住某件事，請繼續深入。

這同樣適用於你自己的指令。寫入設定檔的規則會與其中的其他所有規則競爭注意力，並且隨著檔案增長而逐漸失去約束力。但在建置時直接失敗的檢查則不會。

## 這對輸出帶來的改變

面對一項設計，模型很容易列出要修復的內容。但它們很少說明修復使什麼變得*不可能*，而這正是你贊同的建議與你可以信賴的限制之間的區別。這種習慣正是此技能的主要用途。

另一半則是拒絕接受非裝置性的修復。「新增驗證」、「小心處理這個函式」、「記錄不變量（invariant）」都屬於第零階。每一個背後都有一個真正的裝置，而指認出該裝置正是這項工作的核心。

## 維度 1：錯誤發生時會發生什麼事

將每個發現排在此階梯上，並說明目前的程式碼處於哪一階，以及你的修復達到了哪一階。

| 階梯 | 名稱 | 意義 |
|---|---|---|
| 1 | **控制（Control）** | 無法執行錯誤動作。型別錯誤、資料庫條件約束、缺少權限。 |
| 2 | **警告（Warning）** | 雖然可行，但發生時會主動宣告。Linter、執行階段斷言、無法略過的確認。 |
| 3 | **偵測（Detection）** | 它發生了，而你事後才發現。測試、記錄、監視、程式碼審查。 |
| 0 | **第零階（rung zero）** | 叫大家小心。文件、註解、「請記得要」。 |

偵測並非失敗；有時它是唯一可行的手段。但如果計畫僅止於偵測，應如實說明，而不是將其包裝成預防。

## 維度 2：裝置如何察覺

新鄉重夫的三個檢驗視角。它們是用於*尋找*危害的檢查清單，而非裝飾：

- **接觸（Contact）** — 錯誤的東西在實體上是否放得進去？相同型別的兩個相鄰參數可能會在無聲無息中被對調。應為四個值之一的 `string`。以浮點數表示金錢。
- **固定值（Fixed-value）** — 集合是否完整？沒有窮舉檢查的 switch。缺少索引鍵會默認視為「關閉」的設定。在五個地方中只處理了三個的列舉。
- **動作步驟（Motion-step）** — 順序是否正確，每個步驟是否都發生了？沒有交易的兩階段寫入。沒有等冪鍵（idempotency key）的重試。在某一條路徑取得卻在另一條路徑釋放的資源。

## 從源頭檢驗

捕捉錯誤成本最低的地方是在犯錯之處，而不是在錯誤浮現之處。在輸入層下方三層執行的驗證已經讓不良數值傳遞過去，且堆疊追蹤將指向錯誤的模組。請將檢查推至數值跨越的邊界。

## 設計全新事物

防呆在程式碼還沒有呼叫者之前成本最低。一旦有了呼叫者，每個裝置都是一次移轉；在有呼叫者之前，裝置是免費的。

從呼叫處著手。單獨閱讀時看似正常的簽章，在實際使用的地方往往顯得非常糟糕：

```python
# 錯誤是可以被表達的：沒有任何機制阻止針對從未付款的訂單進行退款
def refund(order: dict) -> Refund:
    return payments.refund(order["payment_id"])

# 錯誤不再能夠被表達
def refund(order: PaidOrder) -> Refund: ...
```

具體手法，大致按照其適用頻率排序：

**使無效狀態無法表示。** 將僅特定組合才合法的選用欄位集合，轉變成無法建構出非法組合的標記聯集（discriminated union）。

**剖析，而非驗證（Parse, don't validate）。** 在邊界將非結構化輸入轉換為帶有證明的型別一次搞定，而不是在九個不同地方重複檢查同一個字串。

**區分共享原始型別的概念。** `transfer(from: str, to: str)` 接受調換的引數。為這兩個概念建立不同的型別，或使用僅限關鍵字參數，讓調換成為編譯錯誤。

**對順序進行編碼。** 當呼叫必須依序發生時，讓每個步驟回傳下一步驟所需的型別，使錯誤的順序無法通過型別檢查。

**使破壞性路徑比安全路徑更狹窄。** 為刪除範圍提供必要且無預設值的引數。讓預設值代表「無」而非「全部」。

最後請說明該設計現在讓什麼變得不可能，而且同樣重要的是，**你刻意保留了什麼可能性以及原因**。未說明限制的設計將會被過度信任。

## 審查現有程式碼

你不是在尋找錯誤（bug）。錯誤是已經發生的失誤。你尋找的是**可用的失誤機會（available mistakes）**：容易犯下錯誤、無聲無息且看起來很正確的地方。

首先針對可透過文字偵測的特徵執行隨附的掃描程式，然後透過人工閱讀找出掃描程式無法察覺的項目：

```bash
python3 scripts/detect_hazards.py --paths .          # 整個樹狀目錄
python3 scripts/detect_hazards.py --staged           # pre-commit
python3 scripts/detect_hazards.py --diff --json      # CI，若有發現則以非零狀態碼結束
python3 scripts/detect_hazards.py --severity high
```

無依賴項目，因此可以在 CI 和 pre-commit hook 中執行，無需安裝步驟。它會回報掃描內容：對零個檔案的掃描會以非零狀態碼結束，而不是回報健康無虞，因為因拼寫錯誤而獲得的安全過關比沒有檢查更糟糕。

依照**爆炸半徑乘以犯錯容易度**對發現進行排序。未經檢查的值傳遞至寫入、刪除、付款或驗證決策，其優先順序高於僅能產生乾淨崩潰的值。針對每個發現，請說明：位置、失誤是什麼、後果是什麼、目前存在什麼裝置、什麼裝置可以消除它，以及達到了哪一階。

`references/hazard-catalog.md` 是特徵分類法及其 ID 和裝置。特定語言的模式請參閱 `references/lang-python.md`、`references/lang-typescript.md` 和 `references/lang-rust-go.md`。

## 事件發生後

區分三個容易混淆的概念，因為修復屬於第三個：

- **缺陷（Defect）** — 使用者所經歷的現象。
- **失誤（Mistake）** — 某人採取的具體錯誤動作。
- **危害（Hazard）** — 系統中使該失誤有機可乘的特性。

修復失誤只能解決單一案例。修復危害能解決整種類別。然後進行**全面清查（sweep）**：相同的特徵幾乎必然存在於其他地方，找出第二個和第三個實例是修補與吸取教訓之間的差別。

將原因歸咎於系統而非個人。這主要不是出於仁慈：因為「他們犯了錯」是一個聽起來很完整但無法預測任何事情也無法預防任何事情的解釋，而且它會讓調查過早終止。

## 優良輸出的樣貌

- **錨定到行號。** `orders.py:142, apply_discount` 是可供審查的；「折扣邏輯」則不是。
- **排序，並使排序一目了然**，這樣就算讀者只讀了一半，也能涵蓋重要的部分。
- **每個發現都有明確具名的裝置**，而不是「新增驗證」。
- **說明階梯等級**，包含改善前與改善後。
- **說明限制。** 修復不涵蓋的部分是讀者最需要且最常得不到的資訊。
- **規模實事求是。** 三個重要的發現勝過湊成整數的十一個發現。

## 應避免的事項

**接受第零階作為修復。** 如果提案是註解、文件或慣例，這項工作就尚未完成。

**將無人能繞過的裝置與無人會繞過的裝置混為一談。** pre-commit hook 可以用 `--no-verify` 略過；它需要 CI 在背後支撐才能成為真正的關卡。請明確說明你提議的是哪一種。

**對單一事件過度擬合。** 用於預防某個特定失敗的機制本身必須能被理解與維護。請自問該特徵是否普遍到值得建立該機制。

**將監視視為預防。** 偵測能降低失敗的成本；它不會降低發生的可能性。兩者都值得擁有，將它們混為一談意味著發生的可能性永遠得不到解決。

## 證據及其限制

此方法在六個模型家族中進行了 591 次盲測評分基準測試，評分基準是在執行前由評分員編寫的斷言，評分員從未看過是哪種設定產生的回應。它最穩定改變的行為是陳述設計排除了什麼：在 132 個評分判定中，**未經提示的回應有 45% 做到了這點，而在應用此方法後達到了 80%**。

該平均值隱藏了效果發生的領域。當明確要求設計介面時，模型本來就有 77% 的時間會這樣做；該技能只增加了 11 個百分點。顯著的增益出現在無人要求進行設計審查的任務中 — 編寫端點從 14% 提升到 79%，交付代理人功能從 33% 提升到 83%，建構表單從 29% 提升到 64%。

誠實說明，因為限制很重要：每次執行都是全新工作階段的第一輪，因此這衡量的是上限，而非在漫長工作階段中能夠留存的效果。比較的對象是完全沒有使用任何方法，而非另一種方法，因此不能確定是*此*方法帶來了增益。而且該方法需要付出可衡量的代價：回應在發現頁面上已經存在的特定缺陷方面變得稍微遜色，而在改變允許該缺陷發生的特徵方面變得更出色。如果你希望找出眼前的錯誤，請使用審查員。如果你希望該類別的錯誤不再能夠被表達，請使用此方法。
