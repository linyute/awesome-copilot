# MCP 發佈品管 (MCP Release QA)

測試使用者將執行的伺服器。結構描述審查或通過的單元測試
不是執行階段證據。

此技能補充了安全性審查。它專注於通訊協定行為、
已發佈協定漂移、傳輸正確性以及可重現的發佈
證據。

## 規則

- 對照從候選修訂版本建構的全新伺服器處理程序執行檢查。
- 將 `initialize`、`notifications/initialized`、探索和呼叫保持在
  同一個工作階段中。新的處理程序就是新的 STDIO 工作階段。
- 將原始碼註冊視為實作真相，並將公開文件視為
  必須與之相符的協定。
- 記錄確切的指令和原始回應。請勿將缺失的證據替換為
  「看起來正確」。
- 請勿針對生產環境資料呼叫具有變更能力的工具。使用測試載具 (fixtures)、沙盒，或
  停止並指出缺失的安全測試環境。
- 在每次執行時從候選原始碼推導預期的功能清單。

## 1. 建立發佈介面

識別：

- 候選認可 (commit) 與建構指令；
- 伺服器進入點與傳輸方式：STDIO、可串流 HTTP 或 SSE；
- 支援的 MCP 通訊協定版本；
- 註冊工具、資源、資源樣板和提示的原始碼檔案；
- 產生的目錄、資訊清單、README 表格和安裝說明；
- 現有的通訊協定、整合和冒煙測試指令。

優先選擇存放庫原生指令。在建立測試控管架構之前，先檢查 `package.json`、`pyproject.toml`、
`Makefile`、CI 工作流程和貢獻者說明。

## 2. 啟動乾淨的伺服器

建構候選版本，並使用具備測試安全性的設定啟動記錄在案的進入點。
擷取：

- 確切的指令；
- 認可 SHA；
- 環境變數名稱（值已編輯遮蔽）；
- stdout、stderr 和結束狀態；
- 用戶端使用的端點或子處理程序傳輸。

對於 STDIO，stdout 僅用於通訊協定。記錄、橫幅和堆疊追蹤屬於
stderr。對於 HTTP 傳輸，記錄狀態、相關的 MCP 標頭和
工作階段識別碼處理，而不印出憑證。

如果伺服器無法依據其記錄在案的說明啟動，請將其回報為
發佈失敗，並逐字保留啟動錯誤。

## 3. 執行一個完整的工作階段

透過真實的 MCP 用戶端或存放庫的整合控管架構執行此序列：

1. 使用伺服器聲稱支援的通訊協定版本進行 `initialize`。
2. 確認協商的版本與宣告的功能。
3. 傳送 `notifications/initialized`。
4. 呼叫 `ping`。
5. 呼叫每個受支援的探索方法：
   - `tools/list`
   - `resources/list`
   - `resources/templates/list`
   - `prompts/list`
6. 從每個宣告的功能類別中執行至少一個具代表性的
   唯讀項目。
7. 當清單方法進行分頁時，遵循分頁直到沒有游標 (cursor) 為止。

請勿透過單獨的單次處理程序傳送初始化後的請求。
這會意外測試數個不完整的工作階段，而非一個有效的
工作階段。

## 4. 證明清單對等性

從當前證據建立四個清單：

| 介面 | 證據 |
|---|---|
| 原始碼 | 已註冊的工具、資源、樣板和提示定義 |
| 執行階段 | 來自即時探索方法的結果 |
| 產生的 Metadata | 目錄、資訊清單或產生的索引 |
| 文件 | README、參考頁面和安裝輸出 |

依穩定識別碼進行比較。回報：

- 在執行階段缺失的原始碼項目；
- 在 Metadata 或文件中不存在的執行階段項目；
- 陳舊的名稱、說明、引數、URI 或提示參數；
- 無法啟動候選伺服器的記錄在案安裝指令。

使用存放庫本身的建構指令重新產生衍生檔案，如果
工作樹仍包含未解釋的產生變更，則判定失敗。

## 5. 檢查已發佈的協定

針對每個發現的項目，對照其原始碼驗證執行階段定義：

### 工具 (Tools)

- 名稱與說明穩定且具體。
- `inputSchema` 在需要時定義型別、必填欄位、列舉和邊界。
- 當工具協定關閉時，未知屬性會被拒絕。
- 變更、等冪性、唯讀和開放世界註解與行為相符。
- 發佈 `outputSchema` 時，成功的呼叫應符合該結構描述。
- 錯誤為通訊協定錯誤或結構化工具失敗，而非洩漏的堆疊
  追蹤。

### 資源與樣板 (Resources and templates)

- URI 和 MIME 類型與註冊的定義相符。
- 靜態資源可讀取。
- 樣板參數在解析前經過驗證。
- 缺失或禁止的資源會明確失敗。

### 提示 (Prompts)

- 必填與選用引數與探索輸出相符。
- `prompts/get` 為有效引數傳回可用訊息。
- 缺失的必填引數和未知提示名稱會明確失敗。

## 6. 測試失敗路徑

至少探測：

- 在初始化完成前的請求；
- 格式錯誤的 JSON 或無效的 JSON-RPC 信封；
- 未知方法；
- 不受支援的通訊協定版本；
- 重複初始化；
- 未知工具、資源和提示名稱；
- 缺失、額外、錯誤型別和超出邊界的引數；
- 處於記錄在案傳輸大小限制的請求，以及超出該限制的請求；
- 經過控制的內部失敗（憑證和堆疊追蹤已編輯遮蔽）。

驗證每個回應是否具有正確的請求 ID、有用的錯誤訊息，
且沒有成功的副作用。對於 STDIO，還要確認每行 stdout 都是
完整的通訊協定訊息，且健康的工作階段會使 stderr 保持乾淨，除非
伺服器明確記錄診斷輸出。

## 7. 冒煙測試安裝

當專案發佈安裝指令時：

1. 在原始碼檢出目錄之外建立臨時目的地。
2. 嚴格按照記錄在案的方式執行公開安裝指令。
3. 啟動已安裝的產物，而不依賴原始碼樹中的檔案。
4. 重複初始化、探索和一次唯讀呼叫。
5. 在保留指令輸出後移除臨時目的地。

僅經過檢查的安裝字串屬於未經驗證。

## 8. 回報證據

使用此格式：

```markdown
# MCP Release QA

Candidate: [commit]
Transport: [STDIO | Streamable HTTP | SSE]
Verdict: PASS | PASS WITH CAVEATS | FAIL

## Commands and results
- `[exact command]` — [exit status and result]

## Session transcript
- initialize: [result]
- discovery: [result]
- representative calls: [result]
- negative paths: [result]

## Parity
| Identifier | Source | Runtime | Metadata | Docs | Result |
|---|---|---|---|---|---|

## Findings
| Severity | Evidence | Impact | Narrowest fix |
|---|---|---|---|

## Missing evidence
- [check that could not run and why]
```

對於無法啟動、無法完成有效工作階段、保持傳輸可剖析或安全
拒絕無效輸入的伺服器，使用 `FAIL`。僅針對不歪曲危險
功能之有界限的文件或 Metadata 漂移使用 `PASS WITH CAVEATS`。
否則使用 `PASS`。
