# 搜尋引擎最佳化 (SEO)

針對讀者搜尋該問題的方式對文章進行最佳化。最佳化的深度取決於文章的最終去向，因此請先確定目的地。

這些規則屬於預設值。當網站自身的慣例或作者的口吻有明顯差異時（標題風格、標籤設定、連結習慣），請遵循網站與作者的風格，且僅在合適之處套用這些規則。

## 等級

| 等級 | 適用時機 | 套用範圍 |
| --- | --- | --- |
| `full` | 已發布的部落格或網站 | 下方列出的所有項目 |
| `light` | 純文字檔案，或尚未確定目的地的對話草稿 | 標題、說明、slug 與標籤。略過內部連結與結構化資料，以便文章在日後發布時保持可攜性。 |
| `venue` | gist 或其他無 front matter 的頁面 | 標題、說明、slug，以及完整力度的開頭段落。略過標籤、內部連結與結構化資料。外部連結依然適用。 |
| `internal` | 文件集 | 簡潔的描述性標題、程式碼自身的識別碼，以及在檔案清單中易於閱讀的標題。略過在文件中顯得突兀的關鍵字句式。 |

依據目的地挑選等級。使用者要求的等級（包括完全不套用）具最高優先權。

## 關鍵字來自技術，而非專案

從文章的通用化主題衍生搜尋詞彙：語言、執行時期、函式庫，以及程式碼所執行的任務。切勿將專案、客戶、組織、存放庫或內部產品名稱作為關鍵字、標籤或 slug。

- 使用中的語言與執行時期，例如 `powershell`、`node` 或 `python`。
- 問題領域，例如 `file-io`、`date-time` 或 `string-utils`。
- 來自程式碼自身 API 的術語（前提是它們屬於標準用法而非專案自創）。

挑選一個主要搜尋詞組與最多兩個次要詞組，以讀者習慣輸入的方式撰寫。

## 標題

- 以主要詞組開頭，讓問題在最初的三到四個字詞中顯現。
- 長度保持在 60 個字元以下，避免在搜尋結果中被截斷。
- 說明任務而非炫技：`Slugify Text in PowerShell` 優於 `A Neat Trick for Tidy URLs`。
- 每篇文章使用一個符合標題的 `H1`。
- 當作者的標題遵循明確模式時（請參閱 `references/voice-profile.md`），請保持該模式並在自然閱讀處融入主要詞組。

## 說明

單一文句，長度為 140 至 160 個字元，開頭說明讀者將獲得的內容。它同時作為 meta description，因此不得包含任何專案或工作上下文細節。

## Slug

- 小寫、連字號分隔、三到六個單字，衍生自主要詞組。
- 不含日期、不含編號，亦不含缺乏搜尋權重的贅詞（stop words）。
- 先選定 slug，再從中構建任何檔案名稱：`slugify-text` 成為 `slugify-text.md`，或在 Jekyll 上成為 `YYYY-MM-DD-slugify-text.md`。平台要求的日期前綴屬於檔案名稱而非 slug，除非網站自身的慣例將其置於 slug 中。
- 在具有既定 slug 慣例的網站上，請遵循該網站。

## 標題標籤與內文

- 在前 100 個字中放入一次主要詞組，置於即使去除該詞組語意依然通順的句子中。
- 圍繞讀者所搜尋的內容（程式碼做什麼、如何使用、回傳什麼、何時不該使用）建立 `H2` 標題，以作者的標題風格措辭。
- 使用自然的變體，而非重複同一詞組。超過兩次自然使用以上的重複會顯得像灌水。
- 為每個程式碼區塊標註其語言，以確保其正確渲染並能作為程式碼搜尋結果呈現。
- 為所有圖片提供描述其內容的替代文字（alt text）。完全略過裝飾性圖片。

## 標籤

- 在部落格或網站上，遵循網站的標籤模式。在合適處重複使用現有標籤，且僅依網站現有文章的方式新增標籤。
- 其他情況下，從領域與語言中衍生二至四個標籤。
- 標籤保持小寫並以連字號分隔。

## 連結

- **內部連結**：僅在 `full` 等級下，當存在真實關聯時連結至同一網站上的一至兩篇現有文章。沒有連結勝過生硬牽強的連結。
- **外部連結**：連結至範例所依賴的任何語言功能或函式庫的官方文件。切勿連結至私有、內部或需要驗證的 URL。
- 撰寫具描述性的連結文字。切勿使用「點擊此處」。

## 結構化資料

在 `full` 等級下，若網站已輸出文章 metadata（JSON-LD、Open Graph 或等效格式），從 front matter 數值填入其預期的欄位。請勿新增網站原先未具備的結構化資料機制。
