# 交付 (Delivery)

如何根據文章的去向調整其形式。內容在各處都是相同的；變化的僅有外層包裝。

## 對話

當不寫入任何檔案時，回覆即為交付成果，因此它必須能夠在一次複製下完整保留且無需手動清理。

- **單一程式碼圍欄區塊。** 文章內部包含自身的三反引號（backtick）圍欄，因此外層區塊請使用四個反引號包裹。
- **不可穿插交錯。** 請勿將文章拆分為多個區塊並在其間穿插評論。備註說明請放在區塊之後。
- **僅在目標能解析時才包含 Front matter。** 對於託管編輯器、無 front matter 的發布管道或尚不明確的目標，請改用**無 front matter 的發布管道**之形式交付。
- **在區塊後列出 metadata。** 當區塊不帶 front matter，或目標具有自身的標題、說明或標籤欄位時，在區塊後列出標題、說明、slug 與標籤，確保資訊不遺漏。僅在已確定目標完全無處容納標籤時才省略標籤。
- **不寫入檔案。** 除非被要求，否則切勿儲存複本。以單行文字提議儲存。

## 無 Front Matter 的發布管道

gist、Discussions 貼文、wiki 頁面或託管 git 服務上的程式碼片段可發布為獨立且易讀的頁面，但並非部落格：沒有靜態產生器、沒有 front matter，也沒有訂閱 feed。

- **切勿在頂部留下 front matter 區塊。** 不支援解析它的發布管道會將原始的 `title:` 與 `description:` 行直接顯示為內文。
- **標題成為第一個標題標籤 (H1)**，或在該管道具備標題欄位時填入其中。
- **說明成為內文的開頭第一行**，或填入該管道的說明欄位中。
- **標籤無處存放。** 捨棄它們，或將重要的一兩個標籤作為普通單字融入開頭句子中。

### 範例：gist

gist 具有兩處可供探索的文字，且完全沒有 front matter。

- **Gist 說明**：承載文章說明。這是讀者在清單與搜尋結果中看到的那一行，因此應包含主要搜尋字詞。單一文句，不含專案細節。
- **檔案名稱**：承載 slug 並設定語法醒目提示。`slugify-text.md` 會渲染為 Markdown 並將主要字詞保留在 URL 中。
- **檔案內文**：符合標題的 `H1`，接著是逐步解說內容。

保持單一檔案。包含多個檔案的 gist 讀起來像專案，而非文章。

## 託管平台

當使用者手動張貼至託管部落格平台或任何與帳戶綁定的網站時，只有使用者本人能存取最終發布管道。

- **為該平台量身打造文章形貌。** 有些平台在貼上時接受 front matter 區塊；多數平台則不支援。
- **僅在使用者指定的路徑中暫存檔案。** 發布管道名稱（例如平台、刊物或帳戶）絕非檔案路徑。若無指定路徑，請在對話中交付。
- **在文章後附上交接摘要**：發布管道、寫入的檔案（若有），以及標題、說明、slug 與標籤，並標註各項內容應填入的欄位。
- **指明剩餘的任何手動步驟**：例如清除草稿旗標、選擇 canonical URL，或從固定清單中挑選標籤。

## 絕不執行

切勿直接建立 gist、開啟討論串、編輯 wiki、上傳、發布、提交或推送。每一項都是獨立的動作，需要使用者個別提出請求。
