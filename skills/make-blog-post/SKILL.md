# 製作部落格文章 (Make Blog Post)

將目前工作階段的程式碼轉換為部落格文章，讀起來就像其作者親筆撰寫：針對單一函式、指令碼、類別或工具進行一次深入逐步解說，圍繞著通用化範例與使用範例建構。

本技能僅在使用者要求撰寫文章時執行。最適當的時機是在輪次結束、程式碼運作正常之時：輸入 `/make-blog-post`，後續可選填要涵蓋的內容、文章存放位置，以及作者過往文章的連結或檔案。

## 何時使用此技能

- 使用者要求撰寫、草擬或將程式碼轉換為部落格文章、專文、教學課程、逐步解說或 gist。
- 使用者叫用 `/make-blog-post`，無論是否有指定主題、目的地或寫作樣本。

請勿將其用於 API 參考文件、README、變更記錄或版本資訊，或需要多個不相關範例或多檔案逐步解說的文章。

## 範例

```text
/make-blog-post
/make-blog-post the retry helper in src/http.ts
/make-blog-post the slugify function, as a gist
/make-blog-post put it in the blog, match https://example.com/posts/one and https://example.com/posts/two
```

## 工作流程

請依序完成各步驟。在步驟 5 中草稿獲得核准前，不會向磁碟寫入任何內容。

### 1. 挑選主題

- 使用使用者指定的項目：函式、檔案、選取範圍、程式碼片段或主題。貼入對話中的程式碼亦在範圍內。
- 否則，採用本工作階段中所撰寫或修改的程式碼。當有多處程式碼符合資格時，列出最多三項，每項附上一行用途說明，並詢問要撰寫哪一項。
- 檢查主題是否適合作為獨立文章。它應當具備：
  - 解決一個明確、通用的問題。
  - 能容納於單一獨立自足的範例中。
  - 不依賴無法被替換為替代物的專案特定狀態、服務或設定。
  - 不可過於瑣碎。單行包裝器或單一標準函式庫呼叫不符合資格。
- 當檢查未通過時，說明哪一項未符合並建議可行切入角度，例如程式碼背後的技術。若使用者堅持，仍可繼續處理原始主題。

### 2. 解析目的地

僅考慮使用者所述內容、目前工作區以及使用者提供的路徑。請勿假設存在任何資料夾，也不要在父目錄或同級目錄中漫步尋找。

1. **使用者指定了目的地**（本機路徑、目前工作區存放庫、gist 等發布管道，或「直接顯示給我看」）：直接使用它，切勿因為另一處更符合慣例而將文章移至他處。若使用者指定了另一個存放庫，請詢問其本機簽出路徑；切勿在遠端複製或修改。例如「the blog」這類不完整名稱僅針對目前工作區解析。若工作區並非該部落格，請詢問路徑。
2. **工作區本身為部落格或網站**：從產生器自身的設定中取得文章資料夾，並符合現有文章的資料夾、副檔名、檔案命名與 front matter。有關偵測方式與各產生器的約定，請參閱 [references/blog-platforms.md](references/blog-platforms.md)。
3. **其他情況**：不寫入任何檔案。在對話中交付文章，並主動詢問是否儲存至使用者指定的路徑。

使用者自訂指示中記錄的預設目的地或語音設定檔亦視為由使用者指定。這是保留個人工作流程的地方，例如封存所有文章的資料夾。

寫入至指定路徑時：

- 在既有根目錄下建立缺失的子資料夾。若根目錄本身不存在，請進行詢問，而非直接建立可能包含錯字的目錄樹。
- 若路徑違反偵測到的產生器約定（集合的錯誤資料夾、缺少日期前綴），請以一行文字說明會導致何種錯誤，提供相容的路徑，並詢問要使用哪一個。
- 若請求與網站慣例相衝突，提示一次後遵循使用者的請求。安全性規則與核准關卡依然適用。

### 3. 學習作者口吻

讀起來像通用說明的文章並非作者自身的文章。在起草之前，依序從以下來源收集三到五篇作者本人的寫作樣本：

1. 請求中指名的樣本：檔案、資料夾、URL 或貼上的文字。
2. 使用者在請求中或其自訂指示中指定的已儲存語音設定檔。
3. 當步驟 2 解析出部落格存放庫時，採用其文章資料夾中該作者最新的文章。

當這些來源提供的樣本少於三篇時，詢問一次以取得足夠連結或檔案補足至三篇，除非使用者已表明沒有更多樣本。接著根據現有資料進行處理：

- **三篇或以上**：建構完整的設定檔。
- **一篇或兩篇**：僅根據這些樣本所證實的模式建構精簡設定檔，並提供參考文件中的三個快速問題以填補空缺。
- **無**：提供三個快速問題，或以樸實、中立的語氣撰寫。

已儲存的設定檔計算為其所記錄的樣本數量。在計畫檢查步驟中說明適用哪種情況以及設定檔基於多少個樣本。切勿將精簡或中立的草稿粉飾為完全契合。

使用 [references/voice-profile.md](references/voice-profile.md) 建構簡短的設定檔：人稱與稱呼方式、正式程度、節奏、開頭、標題、程式碼的引入與解說方式、結尾，以及拼字與標點習慣等細節機制。樣本僅作為風格的依據。其內容（句子、軼事、名稱、連結）絕不放入新文章中，也不會捏造個人經驗以符合某種模式。

### 4. 檢查計畫

起草之前，以簡短數行呈現以下內容並等待使用者確認同意：

- 文章主題與所涵蓋的單一用途。
- 目的地的完整路徑，涉及產生器時附上解析所依據的設定檔，或標註為「僅在對話中顯示」。
- 語音來源（哪些樣本或設定檔，以及所依據的樣本數量），並以三到五個重點摘要其風格。精簡設定檔或根據問答建構的設定檔標註為部分契合，中立語氣標註為無契合。
- 暫定標題、slug 與 SEO 等級。
- 任何待確認問題（若有），例如個人開頭背後的真實故事，或目的地已存在相同主題的文章（更新它、採用新角度或停止）。

若使用者拒絕，請停止且不寫入任何內容。當文章預定在對話中交付時，由於不儲存檔案，可省略額外往返確認：將計畫置於附帶草稿的回覆頂部，以一次核准涵蓋兩者。

### 5. 起草並取得核准

依據**建構文章**指引起草文章，完整呈現並邀請使用者提出修改意見。持續修訂並再次呈現，直到使用者核准為止。沉默或模糊的回應不代表核准。在對話中起草並呈現文章不需要核准，但在獲得明確同意前，不得將任何內容儲存至檔案、發布、提交或推送。

### 6. 交付

- **檔案**：以網站的格式寫入已確認的路徑，使用主機的路徑分隔符號與存放庫的換行符號。以 slug 命名獨立檔案（`slugify-text.md`），該名稱應描述程式碼的功能而非專案名稱。核准即為關卡，因此寫入的文章應處於可隨時發布的狀態。若使用者要求儲存為草稿，請使用平台的草稿機制（請參閱 [references/blog-platforms.md](references/blog-platforms.md)）並在報告中註明。
- **對話**：遵循 [references/delivery.md](references/delivery.md) 中的複製貼上規則。
- **由使用者手動張貼的 gist、討論區、wiki 頁面或託管平台**：依據 [references/delivery.md](references/delivery.md) 組織文章形貌並列出其欄位值。

報告已寫入的內容與位置。提交、推送、上傳或發布屬於獨立動作，需要個別的請求。

最後以最多兩項單行主動提議作結：

- **從文件中連結該文章**：當文章具有已發布的 URL 或本存放庫內的路徑可供指向，且存放庫已有記錄此程式碼的文件時。這包含 README 章節、文件頁面，或說明程式碼功能的 docstring、JSDoc 等文件註解。普通的內嵌註解或僅提供內部脈絡的註解不在此列，僅限內部的程式碼也不予提議。將連結以單行形式緊鄰該文件放置，例如 `Walkthrough: <post URL or path>`。請勿僅為了放置連結而建立文件檔案。
- **儲存語音設定檔**：當設定檔來自樣本時，使用 [assets/voice-profile-template.md](assets/voice-profile-template.md) 儲存於使用者選擇的位置，以便下一篇文章重複使用。

## 建構文章

文章將程式碼的特定單一用途解釋為資訊型的逐步解說。它包含：

- 指明程式碼所解決問題的標題。
- 說明程式碼功能與所涵蓋單一使用案例的簡短開頭。
- 置於單一程式碼區塊中的通用化函式、方法或工具。
- 附帶典型範例資料與預期輸出的最小使用範例。
- 針對限制或邊界情況的結尾備註（當有值得說明之處時）。

實作與其用法視為一個完整的範例，在語言特性自然支援時可共用一個區塊。第二個無關的範例或需要多個檔案的逐步解說均超出範圍。

語音設定檔決定這些部分的措辭、排序與標題設定。它絕不刪除必要部分，且絕不覆蓋安全性規則。

依據 [references/seo.md](references/seo.md) 套用符合目的地的 SEO 等級：已發布部落格為 `full`，純檔案或尚未確定目的地的對話草稿為 `light`，gist 風格頁面為 `venue`，內部文件集為 `internal`。使用者要求的等級（包括無）具最高優先權。當網站自身的慣例或作者的口吻與 SEO 預設值有明顯差異時（標題風格、標籤設定、連結習慣），以網站與作者為準。

### 預設文章配置

僅在 YAML front matter 被讀取為 metadata 且沒有網站自訂欄位的情況下使用此配置，例如儲存於使用者指定路徑的獨立 Markdown 檔案，或在貼上時接受 front matter 的平台：

```markdown
---
title: <文章標題>
description: <單一文句，140 至 160 字元，開頭說明讀者將獲得的內容>
slug: <小寫連字號分隔的 slug>
category: <領域，例如 string-utils 或 file-io>
tags: [<標籤>, <標籤>, <標籤>]
date: <YYYY-MM-DD>
---

<Markdown 格式的文章內文>
```

- 網站自身的 front matter 優先於此配置：將這些數值映射至其已使用的欄位，並捨棄任何其未讀取的欄位。
- 不解析 front matter 的目的地絕不包含此區塊。這涵蓋 gist、Discussions 貼文、wiki 頁面、多數託管編輯器，以及目標尚不明確的對話草稿。請改用 [references/delivery.md](references/delivery.md) 中**無 front matter 的發布管道**之形式，它會將標題移至第一個標題標籤中，並將說明放入開頭第一行。

## 安全性與內容規則

無論目的地或口吻為何，這些規則均適用於放入文章的所有內容。

1. **嚴禁憑證或機密資料。** 不得包含 API 金鑰、權杖、密碼、密鑰、連線字串、私有 URL、內部主機名稱或 IP、帳戶識別碼、環境變數值、洩漏使用者或機器名稱的檔案路徑，或超出規則 6 允許的公開署名範圍之個人資訊。將程式碼所需的任何項目替換為顯而易見的預留位置，例如 `YOUR_API_KEY` 或 `https://api.example.com`。
2. **僅限使用典型範例資料。** 例如 `"Hello, World!"`、`Jane Smith`、`user@example.com`、`foo` / `bar` / `baz`、`123 Main St`、`42`、`Acme Corp`。當程式碼需要此清單中未列出的資料（例如帶有重音的文字或日期）時，請挑選同等通用的項目（`Café`、`2026-01-01`），絕不使用來自工作內容的值。
3. **不得包含來自工作上下文或樣本的偶發細節。** 除了署名之外的人名、專案、客戶與內部產品名稱、商業術語、內部檔案名稱以及來自對話的值均不得出現，來自語音樣本的內容亦同。使用者直接提供的程式碼或主題屬於文章主題而非偶發細節：應當在規則 4 通用化並遵循規則 1 的前提下使用。
4. **重寫而非照抄。** 將程式碼通用化為清晰的展示範例：重新命名專案特定的識別碼、去除無關邏輯，並移除內部依賴項。
5. **範例中的路徑遵循範例所屬環境。** PowerShell 或批次檔範例顯示 Windows 路徑，Shell 範例顯示 POSIX 路徑，跨平台範例同時顯示兩者或使用例如 `<config-dir>` 的標記。
6. **公開屬名與公開技術保留真實名稱。** 當目的地具有作者或署名欄位時，以作者現有文章在該處使用的值填寫，或使用使用者給予的名稱。切勿從工作上下文的其他地方取得（例如 git 設定或系統帳戶）。完整草稿會顯示此名稱，因此核准程序已涵蓋它。程式碼所使用的公開語言、框架、函式庫與工具（例如 Python、React 或 SQLite）照實稱呼。

## 限制事項

- 一篇文章、一個目的、一個完整實作範例。
- 完整口吻契合需要至少三個樣本。若少於三個，設定檔為精簡或中立，且計畫檢查時會予以說明。
- 本技能負責寫入檔案。它不負責發布、上傳、提交或推送。
