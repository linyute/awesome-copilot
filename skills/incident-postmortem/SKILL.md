# 事件事後檢討（Google SRE 格式）

引導團隊在正式環境事件發生後，依照 Google SRE 事後檢討範本的結構撰寫無指責事後檢討。產出內容旨在建立共識、在不指責的情況下找出根本原因，並產出具體的行動項目以防止再次發生。

文件中的所有內容皆來自使用者。切勿捏造時間戳記、指標、名稱或原因。若有未知事項，請在文件中將其列為開放式問題。

## 無指責原則

會出錯的是系統，而非人。目標是了解事件「如何」發生，而非「誰」造成的。避免使用「X 忘了」或「Y 應該要知道」等措辭。改用「系統未執行」、「流程缺乏」或「警示未觸發」。

## 使用時機

- 正式環境中斷或服務降級已解決
- 發生重大的驚險事件（若稍晚才發現就會成為正式事件）
- 發生面向使用者的錯誤、資料遺失或違反 SLA
- 團隊希望在脈絡淡忘前保留學習經驗

**不適用情況：** 在預備環境（staging）中發現的輕微錯誤、計畫內的維護時段，或沒有學習價值的事件。

## 輸入需求

在撰寫前向使用者收集以下資訊。逐節詢問任何缺少的項目，且在涵蓋前三組資訊前，切勿開始分析。

### 事件 Metadata
- 事件標題（簡短、具描述性）
- 作者／事後檢討負責人，以及事件指揮官或值班負責人
- 開始、偵測與解決的日期與時間（含時區）
- 嚴重性／影響等級（P1-P4 或同等分級）

### 影響範圍
- 受影響的服務與系統
- 面向使用者的影響（錯誤、緩慢、完全中斷）
- 估計受影響的使用者人數或百分比
- 資料遺失或損毀（是／否、範圍）
- 違反 SLA/SLO（是／否、超出多少）、營收或業務影響（若已知）

### 時間軸事件
- 首次出現症狀的時間
- 觸發因素（引發失敗的變更或事件，例如部署或組態推送）
- 警示觸發或以人工方式發現問題的時間，以及發現者
- 呼叫值班人員／宣告事件的時間
- 開始調查、確認根本原因的時間
- 套用緩解措施、確認完全解決的時間
- 發送客戶通知的時間（若有）

### 證據與背景
- 可引用的日誌、儀表板、警示、對話串或工單
- 近期變更（部署、組態、基礎架構、相依性升級）
- 先前的類似事件

### 輸出格式
詢問使用者希望的格式。預設為 Markdown。

## 流程

### 步驟 1 - 收集輸入
收集上述輸入。若使用者貼上原始資料（對話匯出、警示日誌），請擷取可用的資訊並列出仍缺少的項目。

### 步驟 2 - 重建時間軸
以 UTC 建立按時間順序排列的時間軸。針對每個事件，記錄時間、發生的事情（系統事件或人為動作）、觀察者或執行者，以及證據連結。

標記空白處：「我們不知道 14:32 到 14:47 之間發生了什麼事 —— 值得檢查日誌。」將**偵測時間（time to detect）**（從開始到偵測）與**緩解時間（time to mitigate）**（從偵測到緩解）分開記錄。

### 步驟 3 - 魚骨圖：腦力激盪候選原因
在進行任何 5 Whys 之前，先使用魚骨圖（石川圖）擴大搜尋範圍。問題陳述為「魚頭」（觀察到的失敗現象，例如：「結帳 API 持續 47 分鐘傳回 500 錯誤」）。針對每個類別詢問使用者：「這個領域中有什麼可能導致了這個問題？」：

| 類別 | 提示 |
|------|------|
| 程式碼與變更 | 近期部署、功能旗標、資料庫遷移、相依性升級、缺少回滾路徑 |
| 基礎架構與平台 | 容量、限制／配額、自動擴展、網路、節點或區域健康狀態 |
| 組態與資料 | 組態漂移、機密資訊／憑證過期、資料結構或資料量、結構描述 |
| 監控與偵測 | 缺少指標、警示閾值或路由、儀表板缺口、雜訊過多的警示 |
| 流程與工具 | 審查／測試缺口、部署檢查清單、執行手冊（runbooks）、值班交接、升級通報 |
| 相依性與外部因素 | 上游／下游服務、第三方廠商、流量尖峰 |

規則：
- 從使用者的證據中收集原因；提出提示，而非結論。將每個原因標記為**已確認（confirmed）**（有證據支持）、**疑似（suspected）**或**已排除（ruled out）**。
- 若某類別不適用，請留空，切勿硬湊內容。
- 子原因可向下巢狀一層（原因的原因）作為魚骨上的分支。

將結果呈現為縮排樹狀圖加上表格。確切格式請參閱 [references/fishbone-example.md](references/fishbone-example.md)。

### 步驟 4 - 對最強的分支進行 5 Whys 分析
選擇最能合理解釋事件的已確認分支（通常一到三個，若偵測緩慢，至少應包含一個來自「監控與偵測」的分支）。針對每個分支分別執行獨立的 5 Whys 鏈：

```
為什麼使用者會看到 500 錯誤？
-> API pods 處於 crash-looping 狀態。
為什麼它們會 crash-looping？
-> 超出記憶體限制。
為什麼會超出限制？
-> 一個新的查詢將完整的結果集載入記憶體中。
為什麼在部署前沒有發現這個問題？
-> 負載測試僅涵蓋 p50 情況，未涵蓋高基數帳號。
為什麼負載測試只涵蓋 p50？
-> 我們沒有大型帳號的測試 fixtures。
```

指引：
- 「五次」只是參考基準。當最後一個「為什麼」落在可修復的系統或流程缺口時即可停止。
- 「人為錯誤」絕不是終點；請持續追問為什麼系統允許該錯誤發生。
- 每條鏈都會得出一個根本原因。記錄它來自哪個魚骨圖類別。
- 區分**根本原因**（最深層的可修復缺口）、**觸發因素**（引發事件的導火線）與**促成因素**（使情況惡化的條件）。與單一線性鏈不同，此方法可合理地產出多個根本原因。

### 步驟 5 - 影響量化
協助使用者精確量化：持續時間（區分偵測與解決時間）、尖峰期與基準期的錯誤率、受影響的流量百分比、消耗的 SLO 錯誤預算、營收或業務影響。

### 步驟 6 - 行動項目
每個根本原因與促成因素都需要至少一個行動項目。依照 Google SRE 範本，為每個項目指定一個**類型**：

- **偵測（Detect）** - 能讓我們更早收到警示
- **緩解（Mitigate）** - 能減少影響或縮短復原時間
- **預防（Prevent）** - 能阻止事件發生

| # | 行動 | 類型 | 負責人 | 追蹤單號 | 到期日 | 優先順序 |
|---|------|------|--------|----------|--------|----------|
| 1 | 為超過 10k 筆記錄的帳號新增負載測試 fixtures | Prevent | @person | PROJ-123 | 2026-07-01 | High |

當偵測或復原緩慢時，請至少包含一個偵測（Detect）或緩解（Mitigate）項目，而不僅是預防（Prevent）項目。負責人必須是個人，而非團隊。諸如「改善監控」等模糊的行動必須拆解為具體的可交付成果（服務、指標、閾值）。向使用者詢問追蹤工單編號；若無則保留為 `TBD`，切勿自行捏造。

### 步驟 7 - 撰寫文件
填入 [references/postmortem-template.md](references/postmortem-template.md) 中的範本。各節遵循 Google SRE 順序：摘要（Summary）、影響（Impact）、根本原因（Root Causes）、觸發因素（Trigger）、偵測（Detection）、解決方案（Resolution）、行動項目（Action Items）、經驗教訓（Lessons Learned：做得好的地方、出錯的地方、幸運的地方）、時間軸（Timeline）、支援資訊（Supporting Information）。魚骨圖與 5 Whys 放在「根本原因分析（Root Cause Analysis）」中。

除非使用者指定其他位置，否則將 Markdown 儲存至 `docs/postmortems/YYYY-MM-DD-<slug>.md`。

### 步驟 8 - 其他輸出格式
務必先產出 Markdown 原始檔，僅在使用者要求時才進行轉換。

| 格式 | 方式 |
|------|------|
| Markdown（預設） | 步驟 7 產出的 `.md` 檔案 |
| HTML | 撰寫單一獨立的 `.html`（內嵌 CSS，無外部資產），包含相同的章節與表格；將魚骨圖樹狀結構呈現在 `<pre>` 區塊中 |
| DOCX | 使用儲存庫的 `md-to-docx` 技能：`node skills/md-to-docx/scripts/md-to-docx.mjs <file.md> <file.docx>`（需先在該技能的 `scripts/` 資料夾中執行一次 `npm install`） |
| PDF | 使用瀏覽器將 HTML 列印為 PDF，或使用本機可用的工具（如 Pandoc）。檢查已安裝的工具，若無適合工具請告知使用者，切勿私自安裝任何軟體 |

結束時向使用者確認輸出路徑。

## 常見錯誤

| 錯誤 | 修正 |
|------|------|
| 「Bob 忘了檢查組態」 | 「部署檢查清單未包含組態驗證」 |
| 根本原因是「人為錯誤」 | 繼續追問「為什麼」—— 人為錯誤永遠只是症狀 |
| 直接跳到單一 5 Whys 鏈 | 先畫魚骨圖，再深入分析最強的分支 |
| 將每個魚骨圖想法都列為根本原因 | 僅有證據支持的原因才進行 5 Whys 鏈；其餘標記為疑似或已排除 |
| 只有「預防」類型的行動項目 | 同時加入「偵測」與「緩解」項目 |
| 沒有負責人的行動項目 | 每個項目都需要具名的個人，而非團隊 |
| 憑記憶重建時間軸 | 在撰寫前先檢查日誌、警示、對話與呼叫紀錄 |
| 將「改善監控」列為行動項目 | 具體說明哪個服務、指標、閾值與日期 |
| 數週後才撰寫事後檢討 | 在脈絡仍清晰時於 48-72 小時內撰寫 |
| 用聽起來合理的細節填補空白 | 將未知事項標記為開放式問題 |
