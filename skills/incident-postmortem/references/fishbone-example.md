## 選擇進行 5 Whys 的分支

深入分析最能解釋影響與持續時間的已確認分支：

1. **程式碼與變更 -> 流程與工具**：為什麼不良的查詢會進入正式環境（解釋觸發因素）。
2. **監控與偵測**：為什麼花了 31 分鐘才發現（解釋持續時間）。

## 鏈 1：查詢進入正式環境（類別：程式碼與變更、流程與工具）

1. 為什麼使用者會看到 500 錯誤？ -> API pods 處於 crash-looping 狀態。
2. 為什麼它們會 crash-looping？ -> 超出記憶體限制（OOMKilled）。
3. 為什麼會超出限制？ -> 新的查詢將完整的結果集載入記憶體中。
4. 為什麼在部署前沒有發現這個問題？ -> 負載測試僅涵蓋 p50 帳號規模。
5. 為什麼負載測試只涵蓋 p50？ -> 沒有針對大型帳號的 fixtures，且發行檢查清單中也沒有要求。

**根本原因 1：** 發行流程中沒有要求對高基數帳號進行測試涵蓋。

## 鏈 2：偵測緩慢（類別：監控與偵測）

1. 為什麼花了 31 分鐘才發現？ -> 直到客戶回報錯誤前，都沒有任何警示觸發。
2. 為什麼沒有警示觸發？ -> 記憶體警示閾值為 90%，而 pods 在持續讀數達到該閾值前就已被終止。
3. 為什麼閾值會這樣設定？ -> 它是從另一個記憶體特性截然不同的服務複製過來的。
4. 為什麼從未重新檢視？ -> 警示閾值沒有審查負責人或審查週期。
5. 為什麼沒有負責人或週期？ -> 警示標準並未要求這一點。

**根本原因 2：** 警示定義沒有所有權或定期審查機制，且未監控 pod 重新啟動率。
