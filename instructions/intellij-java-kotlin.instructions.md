# IntelliJ IDEA Java 與 Kotlin 開發

針對在 IntelliJ IDEA 中開發的 Java 與 Kotlin 專案使用這些指引。請優先遵循存放庫專屬的慣例，並僅在相關時套用特定語言或架構的指引。IDE 操作是選用的開發者工作流程：切勿假設 Copilot 可以操作 IDE，或在缺乏工具佐證的情況下宣稱已執行操作。不要要求付費的 IntelliJ 功能或額外的 IDE 外掛程式。

## 專案模型與建構設定

- 將 Gradle 或 Maven 設定、存放庫文件與 CI 工作流程視為單一事實來源。在變更程式碼之前，先檢查建構檔案與現有的模組配置。
- 從其 Gradle 設定或 Maven 根 POM 匯入或重新載入專案。請在建構檔案中定義相依性、存放庫、原始碼集（source sets）、編譯器選項與測試任務，而非僅在 IntelliJ Project Structure 中定義。
- 存在時請使用存放庫的 Gradle 或 Maven wrapper。保留 wrapper 版本、相依性目錄、lockfile、父 POM 與相依性管理慣例；切勿將升級工具作為無關變更的副作用。
- 將 IntelliJ 專案 SDK、模組 SDK、語言層級、Gradle JVM 與 Maven 執行程式／匯入程式 JDK 與建構設定對齊。區分執行建構工具的 JDK 與編譯工具鏈以及目標位元組碼；它們可能刻意有所不同。除非存放庫要求，否則不要選取最新安裝的 JDK 或啟用預覽功能。
- 在建構變更後，重新載入 Gradle 或 Maven 專案並解決同步錯誤，然後再解讀 IDE 診斷資訊。在建構模型中修復遺失的相依性與原始碼根目錄，而非手動新增本機 JAR 或特定機器的路徑。

## 編輯、導覽與重構

- 遵循存放庫的 `.editorconfig`、格式化工具、匯入順序與檢查設定。僅在既有存在時使用已設定的檢查，例如 Spotless、Checkstyle、ktlint 或 detekt；避免無關的全檔案重新格式化或新增格式化工具相依性。
- 使用「前往宣告」（Go to Declaration）、「尋找用法」（Find Usages）以及型別或呼叫階層來理解變更。同時搜尋靜態 IDE 導覽可能會遺漏的設定、基於反射的查詢、序列化名稱與架構慣例。
- 當可用時，偏好語意上的重新命名、移動、變更簽章、擷取方法與安全刪除重構，而非文字替換。預覽受影響的用法並審查 diff，包含 Java/Kotlin 互操作性、公開 API、資源與測試。
- 將檢查與快速修復視為建議而非權威。對照已設定的語言層級與專案行為來檢查它們；切勿僅為了消除標示就全面抑制警告、放寬檢查或變更編譯器設定。
- 若無法使用 IDE 操作，請使用可用工具進行等效的原始碼／建構編輯，並從命令列驗證它們。切勿僅為了完成程式碼變更而新增 IDE 自動化或外掛程式。

## 執行、除錯與測試

- 將執行／除錯設定與預期的模組 classpath、JDK、工作目錄、JVM 選項、應用程式引數、環境與啟用的設定檔（profiles）對齊。將機密資訊保留在現有的環境或機密管理機制中，而非共用的執行設定中。
- 當專案依賴建構工具任務、產生的原始碼或自訂測試設定時，使用 Gradle/Maven 工具視窗或委派的建構／測試執行。僅在 IntelliJ 中編譯或綠色邊界測試不能替代 CI 命令。
- 使用中斷點、條件中斷點、監看式與例外狀況中斷點來調查失敗。謹慎評估運算式，因為方法呼叫可能會改變狀態；切勿僅為了簡化除錯而引入正式環境行為的變更。
- 在存放庫現有的架構、原始碼集、命名樣式與斷言慣例中新增或更新針對性測試。保留單元測試與整合測試之間的區別，包含所需的服務、設定檔、測試資料（fixtures）與測試探索規則。
- 除非存放庫明確共用，否則保持執行設定為本機。共用時，偏好專案相對路徑與具備記錄的環境需求，以便其他開發者重現執行。

## Kotlin 慣例

- 保留已設定的 Kotlin 語言／API 版本、JVM 目標與 Java 互操作性慣例。切勿接受需要較新編譯器或非刻意變更面向 Java 簽章的 IDE 轉換。
- 明確建立可為 Null 性（nullability）模型，特別是在 Java 平台型別邊界上。偏好安全呼叫、Elvis 運算式與明確驗證，而非引入 `!!` 或未檢查的轉型以消除診斷。
- 當使用協程（coroutines）時，遵循現有的範圍、分派器（dispatcher）與生命週期慣例。偏好結構化並行；切勿引入 `GlobalScope`、使用 `runBlocking` 阻塞協程執行緒，或吞掉取消例外狀況。
- 針對非同步測試，使用專案現有的協程測試公用程式與受控分派器，而非 sleep 或依賴時序的斷言。

## Spring Boot 專案

- 遵循現有的 Spring Boot 版本、相依性管理、套件配置、設定格式、設定檔與測試慣例。切勿向未使用的專案新增 Spring Boot。
- 偏好存放庫的建構函式注入模式。重構時保留元件掃描、設定屬性繫結、交易邊界與驗證行為。
- 針對 Kotlin Spring 或 JPA 程式碼，保留建構中現有的編譯器外掛程式設定（例如 `kotlin-spring` 或 `kotlin-jpa`），並檢查註解的使用位置目標。切勿僅為了滿足 IDE 警告而將每個類別設為 `open` 或新增無引數建構函式。
- 保持應用程式啟動與測試可透過現有的建構任務或可執行產物執行。Spring 專屬的 IDE 儀表板與檢查是選用的，絕非先決條件。

## 註解處理與產生的原始碼

- 在 Gradle 或 Maven 中設定註解處理器與程式碼產生，視情況包含現有的 `annotationProcessor`、KSP 或 kapt 設定。切勿僅在 IntelliJ 中啟用處理器，或在無任務需求的情況下在處理機制之間遷移。
- 針對未解析的產生型別，首先執行已設定的產生／編譯任務並重新載入建構模型。在將問題視為 IDE 快取問題之前，請先檢查處理器相依性、任務順序與產生的原始碼目錄。
- 將產生的原始碼視為輸出：改為編輯原始碼註解、結構描述（schemas）、範本或產生器設定。切勿手動編輯產生的類別或將其複製到一般原始碼根目錄中。
- 保持產生的原始碼註冊與相依性在建構中具備可重現性。IntelliJ 原始碼根目錄標記或註解處理設定必須反映該設定，而非取代它。

## 版本控制整潔度

- 尊重 `.gitignore` 與現有的追蹤政策。建構或測試專案不需要認可 `.idea/`、`*.iml` 或 `.run/` 檔案。
- 將使用者專屬狀態（例如 `.idea/workspace.xml`、本機歷程記錄、快取、絕對 SDK 路徑與認證）排除在認可之外。僅共用明確核准的專案設定，例如程式碼風格、檢查設定檔或可攜式執行設定。
- 除非存放庫明確要求，否則將產生的輸出（例如 `build/`、`target/`、`out/` 與 `.gradle/`）排除在版本控制之外。切勿將 `.gradle/` 快取與 `gradle/wrapper/` 下受版本控制的 Gradle wrapper 檔案混淆。
- 保留刻意追蹤的 wrapper 指令碼、wrapper 設定與必要的 wrapper JAR。在 IDE 同步後審查 diff，以避免認可附帶的 metadata 變動。

## 命令列驗證

- 執行與 CI 相同的 wrapper、JDK／工具鏈設定、任務或 Maven 階段、設定檔以及相關環境設定。先從針對性檢查開始，然後執行所需的更廣泛建構、格式化、靜態分析、單元測試與整合測試檢查。
- 針對提供這些任務的專案，針對性的 Gradle 範例為 `./gradlew test --tests 'com.example.ExampleTest'`，後續接 `./gradlew build`。在多專案建構中使用適當的模組任務，並包含 CI 執行的任何額外檢查。
- 針對使用標準 Maven 測試生命週期的專案，針對性的範例為 `./mvnw -Dtest=ExampleTest test`，後續接 `./mvnw verify`。調整模組選取與設定檔以配合存放庫，並驗證整合測試確實已設定且執行。
- 在 Windows PowerShell 中，使用帶有等效引數的 `.\gradlew.bat` 或 `.\mvnw.cmd`。若不存在 wrapper，請使用存放庫記錄的建構工具版本，而非在未達成共識前引入 wrapper。
- 透過比對 JDK、classpath、設定檔、產生的原始碼、工作目錄與環境設定來診斷 IDE/CLI 差異。切勿透過放寬 CI 檢查來修復僅限 IDE 的失敗。
- 回報執行的命令及其結果。若因缺少必要工具、服務或認證而無法執行檢查，請明確說明限制，而非宣稱成功。
